## 3. 관점별 의견

### DS-1 디자인 (시각 위계·영역 구분·사진 비율)
- 구분은 **면으로** 한다: 보는 것 = 옅은 종이 면(테두리 없음), 쓰는 곳 = 흰 면 + 굵은 테두리 **하나**. 상자를 더 그리는 대신 상자를 줄인다.
- 사진·AI 고지·따라 쓸 낱말은 한 덩어리(그림 낱말 카드처럼 '이 사진의 낱말'). 낱말은 입력 칸 카드에서 빼서 사진 아래로.
- 사진은 P4와 같은 `photoFrame`(원본 비율, contain, 잘라 내지 않음). 높이는 '입력 칸까지 첫 화면'을 지키는 만큼만(fit) — 사진은 ①에서 이미 크게 봤으므로 여기서는 보조.
- 입력 칸 테두리는 1.5 → 2(다른 상자가 없어지니 굵기 하나로 '여기'가 보인다). 포커스는 그대로 action 3.

### PL-1 기획 (이 단계의 목적)
- 목적은 '사진을 보고 낱말을 떠올려(3단계는 보고) 한 번 써 보는 성공 경험'. 성공 조건은 **입력 칸이 첫 화면에 있고, 무엇을 쓸지 한눈에 보이는 것**. 사진은 맥락(왜 이 낱말인지)이라 잘려서 무슨 장면인지 모르면 차라리 없는 편이 낫다.
- 우선순위: ① 입력 칸 첫 화면(#104 ②) ② 따라 쓸 낱말 ③ 사진. 작은 화면에서 셋 다 못 들면 사진을 접는 기존 규칙을 유지.
- 5단계 ④는 ②에서 고른 낱말이라 사진 낱말과 다를 수 있다 → 보기 판 낱말이 사진 이름표처럼 보여도 '떠올리신 낱말' 안내가 쓰기 칸 바로 위에 있어 어긋나지 않는다.

### WR-1 라이터 (문구·자리 말·writer.md 톤)
- 새 문장은 만들지 않는다(writer.md 1-2: 한 화면 안내 3문장 이하 — 지금 본문 안내 2문장 → 1문장으로 준다).
- 「보이는 낱말을 아래 칸에 써요」·「떠올리신 낱말을 아래 칸에 써요」는 입력 칸 **바로 위**로 옮기면 '아래 칸'이 정확해진다(지금은 사이에 낱말이 끼어 자리 말이 틀림). 문구 그대로.
- 「한 글자라도 쓰면 눌려요」는 버튼 상태 설명이므로 꺼진 버튼 바로 위 이유 줄로(#257에서 정한 「한쪽을 고르면 눌려요」와 같은 꼴, 같은 자리). 문구 그대로.
- 결론: **바뀐 문구 없음, 자리만 바뀜** → copy.ko.json·sync 변경 없음, 라이터 확정 대상 없음.

### QA-2 접근성 (200%·TalkBack·라벨·자판 가림)
- 읽기 순서: 단계 제목 → AI 고지 → 「따라 쓸 낱말, 단풍잎」 → 안내 → 「낱말 쓰는 칸」(힌트 '여기를 누르면 자판이 나와요') → 읽어 주세요 → 「다 썼어요」(힌트 「한 글자라도 쓰면 눌려요」). 사진 그림은 읽지 않는다(지금과 같음 — 고지 줄이 사진의 뜻을 말함).
- 이유 줄은 화면 읽기에서 숨기고 버튼 힌트로 한 번만 읽힌다(ds Button 규칙, TalkBack R8) — 지금 accessibilityHint와 같은 말이 같은 때 읽힌다.
- 입력 칸 라벨 「낱말 쓰는 칸」 유지. 보이는 이름표(안내)가 칸 바로 위에 붙어 보이는 것과 읽는 것이 가까워진다.
- 200%: 사진은 자리가 없으면 접힌다(fit < 바닥). 보기 판은 낱말만, 쓰기 칸이 접힘에 걸치면 R-15로 통째로 아래(지금 규칙).
- 자판 열림: 보기 판·안내는 접고 쓰기 칸 한 줄에 [낱말][입력 칸](지금 r1/7 H 규칙 그대로) — 보이는 창 약 75dp에 낱말과 칸이 함께 든다. 사진은 열림에서 보이지 않는다(지금과 같음, 가릴 것이 없음). 200% 열림 Dock 해제(리드 결정 b)도 그대로.

## 5. 결정

**안 B 채택.**
- 근거: 오너 요청(영역 구분)의 네 문제(P-2~P-5)를 새 문장 없이 자리·면만으로 푼다. 사진은 P4와 같은 `photoFrame`(원본 비율 contain)과 ②와 같은 '테두리 없는 사진 + 고지'로 세 화면이 일관된다. 입력 칸 첫 화면(#104 ②)·자판 열림 한 줄(r1/7 H)·200% Dock 해제(리드 결정 b)는 그대로.
- 사진 크기 규칙: 높이 = min(창 45%, 본문 폭 비율 높이, fit). fit = 첫 화면(접힘) − 보기 판 위 끝 − 판 여백·간격 − 고지 − 낱말 − 간격 − 쓰기 칸(안내 + 입력 칸) − 여유 2. **fit이 96 미만이면 사진을 접는다**(② 썸네일 64보다 크고, 그보다 작으면 다시 '띠'가 된다). fit은 사진 높이·유무와 무관한 실측값만 써서 측정 → 줄임 → 재측정 반복이 없다.
- 구현 중 실측으로 더한 것(에뮬레이터, 증거 README):
  - **보기 판 좌우 여백 0**(위아래 12만). 판 안쪽 12를 두면 고지가 288 폭에서 두 줄로 꺾여(본문 폭 312에서는 한 줄 — P4와 같음) 360×780에서 fit이 84로 바닥 아래 → 사진이 접혔다. 여백 0이면 고지 한 줄, 사진 142×114.
  - 고지는 사진이 있을 때만 그려 사진 전에는 잴 수 없다 → 판 폭으로 줄 수를 어림(306dp 글 폭 기준), 그린 뒤 실측으로 바꾼다. 실측이 크면 사진이 접힐 뿐 다시 펴지지 않는다(반복 없음).
  - **자판 열림에서는 이유 줄을 그리지 않고 힌트만**. 자판 위로 올라온 Dock이 한 줄만큼 커져 [낱말][입력 칸] 줄이 '더 있음' 띠에 가렸다(360×640 실측). 200% 열림(Dock 풀림, 리드 결정 b)의 본문 '다 썼어요'도 이유 줄을 떼고 힌트만 — 두 줄 이유가 버튼을 '더 있음' 띠 아래로 밀었다(320×640 실측, 옛 코드에도 있던 줄).
- 버린 안: A(영역 구분 요청에 답하지 못함), C(배율·낱말 길이마다 배치가 바뀌어 규칙이 둘, 사진이 썸네일로 작아짐). 그 밖에 '사진을 누르면 크게 보기'(P4 기능)는 ①에서 이미 할 수 있어 이번에 넣지 않음.

## 7. 자판 올라온 상태(입력 중)

- 보기 판·안내·사진은 그리지 않는다. 위 영역은 BackLink 한 줄(100%는 오른쪽 '넘어갈게요'), 본문 맨 위가 [따라 쓸 낱말][입력 칸] 한 줄. 보이는 창이 약 75dp(360×640 Gboard)라 사진을 둘 자리가 없고, 사진이 있으면 시스템이 입력 칸을 보이게 스크롤하며 낱말을 밀어낸다(r1/7 H 실측).
- 낱말·입력 칸이 자판에 가리지 않는지는 에뮬레이터 캡처(열림 100%·200%)로 확인 — 증거 README.

## 8. 남은 것
- 오너 S25 확인: 360dp대 100%에서 사진 크기(에뮬레이터 360×780 근사: 142×114, 원본 비율). 글꼴·기기 차로 고지가 두 줄이 되면 사진이 접힐 수 있다(그때는 바닥 96을 낮출지 다시 판단).
- 보기 전용(P5_P6_review) 썸네일 128×100 cover는 비율 1.28 — 콘텐츠 1.24와 거의 같아 잘림 약 3%. 동결 시안이라 이번에 손대지 않음.
