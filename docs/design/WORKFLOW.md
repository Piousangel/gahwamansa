# 디자인 → 리뷰 → 개발 반영 워크플로 (2026-11-17 제안)

사용자 제안: 디자인팀이 인벤토리 기준으로 Claude Design에서 작업 → 리뷰 → 개발자 반영.

```
[1 인벤토리]──[2 디자인]──[3 디자인 리뷰]──[4 개발 반영]──[5 구현 검수]
 SCREENS.md   Claude Design  체크리스트·사용자   app/ 수정       화면 대조·실기기
 (리드)       (디자인팀)      (리뷰어들)         (앱 개발)       (QA)
```

## 단계별 담당·산출물·통과 조건
| 단계 | 담당 | 산출물 | 통과 조건 |
|---|---|---|---|
| 1 인벤토리 | 리드 | `docs/design/SCREENS.md` | 사용자가 화면 목록·미정 항목을 확인 |
| 2 디자인 | 디자이너(화면·흐름), 에셋 디자이너(아이콘·캐릭터·그래픽) | Claude Design 캔버스(폴더 구조는 SCREENS.md §5) | §6 완료 기준 충족, 캔버스 링크 공유 |
| 3 리뷰 | 라이터(문구), 정책(의료 표현·동의 문구), QA(접근성), 개발(구현 가능성), **사용자(최종 승인)** | 리뷰 코멘트와 `docs/design/REVIEW-<날짜>.md` | 각 리뷰어 "통과" 또는 수정 사항 해소, 사용자 승인 |
| 4 개발 반영 | 앱 개발 에이전트 | `app/` 수정(+ 서버 요청 목록은 리드에게) | 승인된 시안과 화면별 대조 체크리스트 완료, tsc·lint·jest·통합 통과 |
| 5 구현 검수 | QA + 사용자 | 실기기 확인 결과 | 어르신 화면 접근성·크기 기준, 3가구 관찰 |

## 운영 규칙
- **시안이 승인되기 전에는 앱 화면 코드를 바꾸지 않는다.** 단, 이미 구현된 화면의 동작 버그는 별도로 고친다.
- 디자인 변경이 서버 계약(RPC 필드)을 바꾸면 리드에게 먼저 요청한다(REPO.md의 서버→앱 순서).
- 시안은 **캔버스가 단일 원본**이다. 삭제 사고에 대비해 승인 시점마다 `docs/design/mockups/`에 보관본을 갱신한다(이전에 캔버스가 사라진 일이 있었다).
- 문구가 바뀌면 `copy.ko.json`(라이터 소유)을 먼저 확정하고, 앱 사본을 갱신한다.
- 에셋 납품 기한(제안 11/26)을 지키지 못하면 빌드 1에는 자리표시 박스가 남지 않도록 **최소 세트**(런처 아이콘, 해님 기본 표정, 필수 UI 아이콘)만 우선 납품받는다.

## 우선순위 제안(빌드 1 기한 기준)
1. **빌드 1 필수 화면**: P1~P6, P3의 모든 상태, P9·P10, C0~C5, C8·C9, S1·S2, 앱 아이콘·스플래시. (11월 말 테스트 트랙 업로드 기준)
2. **빌드 2**: P7·P8(응원 도착), P12(알림 권한), C6, C7, 형제 초대(미정), 스토어 그래픽·스크린샷.
3. 앱 코드가 이미 있는 화면(P1~P6, P9·P10, C4·C5·C8·C9)은 **시안 승인 후 재스타일링**, 화면이 없는 것(C1~C3, P0, P7, P8, S1)은 **시안 승인 후 신규 구현**.

## 위험과 한계
- Claude Design 캔버스의 폰트·에셋 렌더링은 제가 화면으로 확인하지 못했다. 실제 앱 폰트(Jua, Nanum Pen Script, Noto Sans KR)의 번들·라이선스 확인이 필요하다(디자이너 제안 3번).
- 디자인팀은 Claude 에이전트다. 최종 판단(컨셉, 어르신에게 맞는지)은 사용자와 실제 어르신 3가구 관찰이 한다.
- 시안과 앱 코드의 차이는 개발 반영 단계의 화면별 대조 체크리스트로만 잡힌다. 자동으로 비교하는 장치는 없다.
