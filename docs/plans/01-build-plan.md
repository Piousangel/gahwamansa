# 구현 계획 01: 테스트 트랙 첫 빌드 → 공개 (2026-11-16)

검토 대상: SPEC.md, docs/team/dev.md. 시간은 모두 추정(실측 아님), 1인 개발 하루 약 6시간 가정(사용자가 본인 확인·테스터 모집도 병행).
검토 방식: /plan-eng-review를 줄인 형태로 진행(아래 "검토에서 줄인 것" 참고).

## 원칙
- 크리티컬 패스: 테스터 12명이 설치해 연결·하루 코스를 돌릴 수 있는 첫 빌드를 11월 말 전후에 테스트 트랙에 올려 14일 시계를 먼저 돌린다.
- 빌드 1(테스트 트랙 업로드용)과 빌드 2(테스트 중 업데이트)로 나눈다. 테스트 중 빌드 업데이트가 14일 요건에 영향을 주는지는 미확인이므로 Play Console에서 확인한다.

## 계획에 반영한 설계 수정 (dev.md 대비)
1. `answers_insert` 정책에 동의 확인 추가 (dev.md §3). 자녀 조회를 동의로 제한하는 조건은 불필요(저장 자체가 없음).
2. 오늘의 콘텐츠 계산: `((today - course_start_date) % 30) + 1` → 콘텐츠 행 수 N 기준 `% N`. 14일분 시작 시 깨지지 않게(dev.md §5).
3. 형제 초대(오가닉 루프)는 첫 빌드에서 제외. 현재 `redeem_invite_code`는 익명 기기 전용이라 카카오 자녀가 합류할 경로가 없다. 별도 설계 단계에서 `join_family_as_child` RPC 등을 설계한다.
4. 앱 안 계정 삭제 경로(RPC와 화면)를 추가한다(Play 요건, 정책 담당 확인 근거).

## 미승인 제안 (사용자가 거부하면 제외)
- `PaymentProvider`·`FreeProvider`는 출시 시점에 쓰이지 않으므로 전환 때 추가. 지금은 `entitlements`와 `useFeature`(곧 유료 배지)만.

## 테스트 계획
- pgTAP(`supabase test db`): 가족 간 0행, 쓰기 거부, 동의 거부 시 answers 0행, RLS 활성 테이블 누락 검사(`pg_class.relrowsecurity`).
- RPC 통합(Jest + 로컬 스택): 만료·재사용·5회 잠금·동시 redeem·재연결, `record_session_step` 멱등성, KST 자정 경계(21:00 UTC 전후), N 기반 day_index.
- 단위(Jest): `resolveAccess`, reason → 어르신 문장 매핑, TTS 실패 폴백, 푸시 거절 no-throw.
- E2E(실기기 수동): 코드 입력 → 동의 → 코스 3단계 → 자녀 홈 반영(1분). 이 흐름은 자동화 비용이 커서 첫 빌드는 체크리스트로 확인.
- 각 단계마다 `npm run verify`(타입체크·린트·테스트, 스크립트명은 제안).

## 위험·미확인
1. 모든 라이브러리 버전·유지보수 상태 미확인(react-native-tts, kakao-login, FCM 래퍼). 1단계에서 확인.
2. Supabase의 카카오 id token 지원, 익명 로그인 IP 제한·CAPTCHA 설정값 미확인.
3. 테스트 중 빌드 업데이트가 14일 요건에 영향을 주는지 미확인.
4. 전역 실패 상한이 걸리면 정상 어르신도 막힌다(공개 전 재검토).
5. Android 자동 백업의 세션 복원, TTS 엔진이 없는 저가 기기 비율 미확인(실기기 필요).
6. 시간 추정은 모두 가정이며, 71.5h는 카카오 로그인 검증이 막히면 늘어난다.
