# 앱인토스(토스 인 앱) + Google Play 2트랙 분석 (2026-11-17)

사용자 지시: 토스 인 앱 + 플레이스토어 2개를 목표로 작업. 이 문서는 **공식 자료를 직접 읽어 확인한 것**과 **확인하지 못한 것**을 분리하고, 우리 설계에 미치는 영향과 결정 사항을 정리한다. 확인일 2026-11-17.

## 2. 확인하지 못한 것 (반드시 콘솔·문서에서 직접 확인 필요)
- 심사 기간, 현재 수수료(프로모션 종료 후 정책은 검색에서 최신 확인 못 함), 결제·푸시 등에 **사업자등록이 필요한지**.
- **익명(기기) 세션이 "자체 로그인"에 해당하는지**: 가이드는 자체 로그인을 금지하지만 "로그인 없는 사용"은 다루지 않음. 콘솔 검수에서만 사전 판단 가능하다고 안내됨.
- 서버 API가 **mTLS** 인증이라고 안내되어 있어, Supabase Edge Function만으로 호출이 가능한지(클라이언트 인증서 보관·사용) 미확인.
- 푸시 발송 API 세부 명세, 연결 해제(unlink) 콜백 방식과 시점.
- Toss RN SDK(Granite)에서 우리 RN 앱의 어떤 부분을 재사용할 수 있는지, WebView에서 음성 읽기(Web Speech)·큰 글자 접근성이 동작하는지.
- 토스 사용자 중 60~80대 비율(어르신이 토스 앱을 쓰는지). **이 앱의 어르신이 토스 앱 사용자라는 근거는 없다.**

## 3. 우리 설계에 미치는 영향
| 영역 | 영향 | 심각도 |
|---|---|---|
| **로그인** | 토스에서는 카카오 로그인을 쓸 수 없다. 토스 버전은 **토스 로그인(인가 코드 → 서버에서 검증)** 이 필요하고, Supabase 계정과의 연결(매핑) 설계가 새로 필요하다. 어르신의 코드 연결(익명 세션)이 허용되는지는 미확인 | 높음 |
| **결제** | 토스에서는 토스페이(또는 인앱결제)만. 기존 계획(토스·네이버·카카오 외부 결제)은 Play 트랙 전용으로 분리. 두 트랙의 `entitlements`를 통합해야 구독이 어느 채널에서든 인식됨 | 중간 |
| **교차 유도** | 토스 미니앱 안에서 Play 앱 설치·이동을 유도하면 안 된다. 두 트랙은 **서버만 공유하는 독립 제품**처럼 운영하고, 연결은 사용자가 코드를 전달하는 방식으로만 해결해야 한다 | 높음 |
| **클라이언트 코드** | 현재 RN CLI 앱은 카카오 SDK·FCM·TTS 같은 네이티브 모듈을 쓴다. 토스 런타임(WebView/Granite)에서는 그대로 못 쓴다. **서버(Supabase)와 도메인 로직·문구·디자인 토큰은 공유 가능**, 화면 코드는 재사용 여부를 스파이크로 확인해야 한다 | 높음 |
| **디자인** | 라이트 모드 필수(우리는 이미 라이트), 앱인토스 네비게이션 바 사용, 자체 뒤로가기 금지, 로고는 등록 로고만. TDS 사용은 요구되지 않지만 "일관된 디자인" 원칙이 있다. 우리 디자인 시스템 유지 가능, **토스 앱 안에서 이질감이 크면 심사·이용자 모두에게 불리할 수 있어 확인 필요** | 중간 |
| **삭제·개인정보** | 토스 연결 해제 시 사용자 데이터 삭제 의무. 이미 있는 삭제 RPC를 연결 해제 콜백에 연결해야 한다. 가족 공유 데이터 모델과의 충돌(자녀 하나가 연결을 끊을 때 가족 기록) 정책 결정 필요 | 중간 |
| **일정** | 11월 말 테스트 트랙(Play)은 이미 빠듯하다. 토스 트랙은 신규 클라이언트와 로그인 연동이 필요하므로 **병행하면 Play 출시가 늦어질 위험**이 크다 | 높음 |
| **사용자 층** | 토스 사용자는 상대적으로 젊은 층이라 **결제 주체인 자녀(30~50대)에게는 유리**하지만 어르신 접점은 불확실. 토스 트랙은 "자녀용 입구"로 가는 것이 더 자연스러울 수 있다(가정) | 전략 |

## 4. 구조 옵션
| 옵션 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A (제안) | **서버·디자인 시스템 공유 + 클라이언트 2개**: `apps/android`(RN, 어르신+자녀), `apps/toss`(자녀 중심 미니앱, 어르신은 코드로 Android 앱 또는 미니앱 연결). 공통 `design-system`, 공통 Supabase | Play 일정 보호, 각 채널 정책 준수, 서버 투자 재사용 | 클라이언트 2개 유지 비용, 로그인 매핑 설계 |
| B | 토스 우선: 토스 미니앱(어르신·자녀 모두)을 먼저 만들고 Play는 나중 | 토스 유입(자녀) 큼 | 어르신이 토스 앱 필요(장벽), 이미 만든 RN 앱 활용 낮음, 일정 재편 |
| C | 하나의 코드베이스(Granite RN)로 양쪽 | 코드 재사용 | Granite가 일반 Android 앱으로도 배포되는지·네이티브 모듈 대체 여부 **미확인**, 위험 큼 |
→ 현재 근거로는 **A**를 권한다. 단, 토스 트랙 착수 전에 **기술 스파이크 1회**(약 1~2일, 추정)로 "Granite/WebView로 우리 어르신 화면 1개와 서버 호출이 되는지, 익명 세션이 허용되는지, 토스 로그인 → Supabase 매핑이 mTLS 문제 없이 가능한지"를 확인한다.

## 5. 결정이 필요한 것
1. 토스 트랙의 **대상 사용자**: (a) 자녀만 (b) 자녀와 어르신 모두 — 리드 추천은 (a)로 시작.
2. 일정 우선순위: Play 테스트 트랙 업로드(11월 말) 유지 + 토스는 스파이크 후 12월 착수.
3. 스파이크 진행(콘솔 워크스페이스 생성은 **사용자 계정 작업**).
4. 두 트랙의 **구독 통합** 방식과 결제 정책(토스에서는 토스페이/인앱결제만).

## 6. 사용자 선행 작업 (계정·계약)
- 앱인토스 콘솔 계정(워크스페이스) 생성, 사업자 등록 필요 여부 확인(공식 안내 확인 필요).
- 토스 로그인·푸시 등 서버 API 이용을 위한 인증서(mTLS) 발급 방식 확인.
