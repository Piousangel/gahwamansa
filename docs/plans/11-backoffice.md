## 0. 현재 구조에서 나온 사실
- 콘텐츠 = `content_photos`(사진·caption·**keyword=낱말**·recall_questions) + `content_questions`(prompt·A/B), `day_index` 1~30 상한, 지금 14일분. 날짜 발행이 아니라 **어르신별 순환** `mod(오늘 - course_start_date, n) + 1` → 콘텐츠를 추가해 n이 바뀌면 **이미 한 바퀴 이상 돈 어르신의 순번이 밀린다**. 날짜 차이로 순번을 계산하는 한 공식만 바꿔서는 못 고침
- answers 유일 조건은 0009부터 `(parent_id, question_id, session_date)` → 반복 출제 때 저장 문제 없음(같은 질문 두 번 표시는 C5 디자인 확인)
- 시드는 `on conflict (day_index) do update`로 문구를 덮어씀 → 게시 후 수정하면 과거 답 "A"의 뜻이 바뀜
- 사진: Gemini 생성 → `content/photos-raw` → 검수 → `upload-photos.mjs`(service role, **공개 버킷** `content-photos`) → `image_url`. 검수·AI 고지 체크 기록 없음, 공개 버킷이라 URL만 알면 열람 가능
- 사용자 글은 호칭 20자뿐(응원은 정해진 키) → 신고·차단은 빌드2. 앱 안 삭제 `delete_my_account`(0008) 있음, 웹 삭제 요청은 처리 경로 없음. `events` 0022, 푸시 기록 0024~0025 예정, 공지 테이블 없음

## 2. 개인정보 원칙
- **답 원문 기본 비노출**: 집계만, 문항 A/B 비율은 응답 20명 이상일 때만(비공개 테스트 동안 전부 숨겨지는 것은 의도). 가족별 답·응원 목록 화면은 만들지 않음
- 개별 조회는 삭제·문의 처리에 한정, 사유 입력 → `admin_audit`(누가·언제·무엇·사유), **보관 1년**(파기 배치 제외), 월 1회 점검. authenticated에 update·delete revoke + 변경 감지 트리거(postgres·service role은 기술적으로 지울 수 있으므로 "삭제 불가"라고 쓰지 않음). service role 스크립트는 감사 행을 직접 남김
- **2단계 인증**: Supabase 계정 MFA, 관리자 웹은 Auth MFA(TOTP)·`aal2`에서만 관리자 RPC 실행. service role 키는 서버·사용자 맥에만
- **역할은 owner 하나로 시작**, 운영자 2인 체제 때 editor/viewer 분리
- **본인 확인(웹 삭제 요청)**: 어르신(익명 로그인) → 앱 설정의 "삭제 요청 코드" 발급 후 메일에 적기, 폰 분실이면 연결 자녀가 앱에서 삭제 / 카카오 자녀(이메일 미수집) → 앱 안 코드 / 구글·이메일 자녀 → 그 주소로 OTP 회신. delete-account.html §2 "확인 필요"를 이 결정으로 채움
- production 데이터 staging 복사 금지(09 §5), 관리자 계정은 앱 가족 계정과 분리
- **Studio 조건부 허용(빌드1)**: ① Supabase 조직 멤버 1명·계정 MFA ② prod는 테이블 편집기 대신 집계 뷰·저장된 SQL만 ③ 개별 조회는 수기 대장(날짜·사유) ④ 기간 = 관리자 웹 가동 또는 출시 후 8주 중 빠른 쪽
