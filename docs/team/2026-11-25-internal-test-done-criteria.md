# 내부 테스트 '진짜 완성' 기준 (PL-1 기획, 2026-11-25)

- **왜 이 문서가 있나.** 오너 결정(DECISIONS 2026-11-25 '오너 결정: gorhom 바텀시트 설치 · 테스트는 내부 먼저'): "테스터나 테스트는 나랑 우리 에이전트들이 하자. 어느 정도 진짜 완성되면 테스터를 모을게." 그런데 '진짜 완성'이 무엇인지 적힌 곳이 없었다. 이 문서가 그 기준이다.
- **목표와의 관계.** 목표는 출시 → Play 라이프스타일 1위(`docs/team/marketing/2026-11-24-store-number-one.md`). 테스터가 들어오면 그때부터 Play 비공개 테스트 14일이 돈다(같은 문서 6절 1행). 테스터 앞에서 크래시·빈 알림·자리표시가 보이면 14일을 다시 시작해야 할 수 있다. 그래서 기준을 '테스터 오기 전에 우리가 다 본 상태'로 잡는다.
- **기존 문서와의 관계.** 출시 관문 전체는 `docs/team/qa/release-gates.md`(G-INT·G-CLOSED·G-PUB)에 있다. 이 문서는 그중 **테스터를 모으기 전에 반드시 끝내야 할 것**만 골라 지금 상태를 붙였다. 화면 동작의 정답은 `docs/team/qa/FEATURE-MAP.md` 줄 번호(P1-3 같은)를 따른다.
- **기준 시점.** main `30fec3ec`(#257 병합) + `.claude/progress.md` 11-25 12시 기록까지.

## 0. '진짜 완성'의 정의 (한 줄)

> **3절 '테스터 모으기 전 필수' 목록이 모두 ✅ + 오너가 S25로 실서버에서 하루를 써 보고 "됐다" + 열린 '높음' 결함 0.**

- 판정 기호
  - ✅ 확인됨(근거 파일·PR이 있음)
  - ⚠️ 일부만 확인됨(에뮬레이터만, fake 모드만, 한쪽 경로만 등)
  - ❌ 안 됨 또는 아직 안 함
  - **확인 필요** = 이번에 근거를 찾지 못함. 추측해서 ✅·❌를 붙이지 않았다.
- '어떻게 확인하나' 칸에 적은 방법으로만 상태를 바꾼다. 말로 "됐어요"는 근거가 아니다(스승 원칙 '완료는 증거', DECISIONS 11-20).
- 줄 ID 앞 글자: E 어르신 · C 자녀 · L 연결 · F 3단계/5단계 · A 접근성 · S 성능·안정성 · N 푸시 · D 계정·삭제·동의 · G 법률 게시물 · T 스토어 · O 운영 · M 측정 · K 콘텐츠

## 4. 내부 테스트 진행 방법

### 4.1 역할

| 누가 | 무엇을 | 왜 그 사람이 |
|---|---|---|
| 오너 · S25(R3CY205BKTK) | 실손가락 동작(튕기기·미끄러짐), TalkBack 듣기, '읽어 주세요'·음악 소리, 알림 실수신, 카톡 공유, 카카오·구글 실계정 로그인, 삼성 자판 한글 | 에뮬레이터·jest로는 확인이 안 되는 것만 맡긴다(FEATURE-MAP §3 실기기 목록). 한 빌드에 **5개 이하** |
| 에이전트 · 에뮬레이터(한 번에 한 대, 리드가 순번) | 360×640 100% + 320×640 200% 캡처, Maestro 5흐름, 회귀 묶음(release-gates §5), 캡처 증거 폴더 | 반복·측정이 많은 일. 오너 시간을 쓰지 않는다 |
| 리드 | 빌드 만들기(`scripts/build-staging.sh` → S25 `adb install -r`), 오너 목록 보내기, 결과를 이 문서 '지금' 칸에 반영 | 한 곳에서 상태를 고친다 |
| QA-2 | 실서버 두 대 왕복 날(3.1 4·5번) 진행표 준비·기록 | 기록 양식 주인 |

- **두 대가 필요한 날**(3.1 4·5번): S25 = 어르신 폰, 자녀 폰은 [제안] 에뮬레이터를 staging 실서버로 띄워 쓴다. 자녀 이메일 로그인 인증번호는 오너 메일로 오므로 그날 한 번 오너가 번호를 불러 준다. 오너에게 두 번째 실기기가 있으면 그쪽이 낫다(카톡 공유까지 볼 수 있음).

### 4.2 매 빌드 확인 목록 형식 (11-25 S25 목록 1~4와 같은 꼴)

빌드를 S25에 깔 때마다 리드가 #gahwamansa 스레드에 아래처럼 보낸다. 오너는 번호마다 '잘됨' 또는 '이상함: 한 줄'로만 답한다.

```
[S25 확인] 빌드 <main 커밋 8자리> · staging release · <날짜 시각>
1. <무엇을> — <어떻게: 손가락 동작·글자 크기·TalkBack 켬/끔> (기대: <FEATURE-MAP 줄 번호>)
2. ...
(5개 이하. 에뮬레이터로 이미 본 것은 넣지 않는다)
```

- 예(11-25 실제): "1. 응원 시트 100%·200% 내용 빠르게 튕겨 닫기 10회 / 선택지 누르다 미끄러뜨리기 10회(닫히거나 잘못 보내지면 안 됨)" → 오너 답 "잘되는 거 같아"(progress 226).
- 한 줄 = 한 동작. "이것저것 봐 주세요"는 쓰지 않는다.
- '이상함'이 오면 리드가 캡처·영상 한 장을 부탁하고, 레인을 배정한다(오너에게 원인 분석을 묻지 않는다).

### 4.3 기록 위치

| 무엇 | 어디에 |
|---|---|
| 오너 S25 결과(빌드별) | `docs/team/qa/<날짜>-device-run.md` — 빌드 커밋, 목록, 오너 답 그대로, 이 문서 줄 ID(device-backlog 53줄의 기존 규칙) |
| 에뮬레이터 캡처 | `docs/team/qa/evidence/<날짜>-<주제>/` + README(크기·배율·FEATURE-MAP 줄 번호) |
| 두 대 왕복 날 | `docs/team/qa/<날짜>-device-run.md` 한 파일에 FEATURE-MAP §4 번호별 '했음/막힘(어디서)' |
| 상태 변경 | **이 문서 1절 '지금'·'근거' 칸** — 근거 파일·PR 번호를 붙여야만 ✅로 바꾼다 |
| 새 결함 | `.claude/progress.md` 대기열(번호) + 레인 PR. 높음이면 0절 정의에 걸리므로 이 문서 3.1에도 한 줄 |
| 결정 | `DECISIONS.md`(리드) |

### 4.4 언제 끝났다고 말하나

1. 3.1·3.2의 모든 줄이 ✅(근거 있음).
2. 오너가 S25로 실서버에서 하루(아침 알림 → 코스 → 응원 왕복 → 다음 날 아침)를 써 보고 "됐다".
3. 열린 '높음' 결함 0.

이 셋이 되면 리드가 #gahwamansa에 "테스터 모아도 됩니다"를 올리고, 오너가 테스터 모집을 시작한다(모집 글: `docs/team/store/play-console-draft.md` 9절).
