# 제품 회의(Board) 안건 · 부모님이 먼저 시작하는 흐름 (2026-11-17)

사용자 제안(원문 요지): "부모님이 먼저 가입하고 → 자녀에게 전달하는 플로우도 있으면 어떨까."
규칙은 `BOARD-2026-11-17.md` §0과 같다(r1 독립 의견 → r2 반박·표결 → 리드 종합, 최종 결정은 사용자).

## 지금 구조(사실)
- 자녀가 먼저: 자녀 로그인 → `create_family`(자녀만) → `issue_invite_code`(자녀만, 6자리·7일) → 어르신이 앱에서 번호 입력 `redeem_invite_code` → 어르신 동의 → 코스. 어르신은 가입 없음(익명), 자녀는 결제 주체(후속).
- 미연결 열람 모드가 생김(번호 없이 코스를 보되 답은 저장 안 함, `preview_content`).
- 토스 우선: 어르신·자녀 모두 토스 안에서(anonKey). 자사 앱 설치 유도 금지.

## 안건
| # | 안건 | 리드 초안(검증 대상) |
|---|---|---|
| A | 부모님 먼저 흐름을 **빌드 1**에 넣을지, 빌드 2로 미룰지 | 빌드 1에 "가벼운 판"으로: 어르신이 코스를 먼저 쓰다가(미연결 열람 확장) "가족에게 보여 주기"로 번호를 만들어 자녀에게 전달 |
| B | 어르신이 만든 번호를 자녀가 입력하는 **역방향 번호**(서버: 어르신의 `create_family`/`issue_invite_code`, 자녀의 redeem) 설계와 보안(사칭·피싱: 모르는 사람이 "자녀"로 연결될 위험) | 연결 후 어르신 화면에 "누가 연결됐는지" 확인 한 번, 번호 유효 24시간 |
| C | 어르신이 먼저 쓴 기록(미연결 동안의 답)을 연결 후 보여 줄지 | 이미 결정: 미연결 동안 답은 저장하지 않음. 부모님 먼저 흐름에서는 **처음부터 가족을 만들고 시작**하면 저장 가능(이 경우 동의는 연결 시점에) |
| D | 어르신의 번호 전달 방법(카톡 공유·말로 불러 주기·화면 보여 주기)과 어르신 화면 부담 | 큰 숫자 보여 주기 + 공유 버튼 하나 |
| E | 사업 영향: 획득 경로(어르신이 지인·복지관·토스에서 직접 발견), 결제 주체(자녀) 연결 지연, 자녀가 끝내 안 들어오는 가족 | 위원 의견 |
| F | 동의·개인정보: 어르신이 먼저 만든 가족에서 동의 시점·대상, 자녀가 여럿일 때 | 위원 의견 |
| G | 과한 것: 두 흐름을 다 두면 화면·테스트·문구가 두 배. 하나로 합칠 방법(예: 역할 선택 후 같은 "번호 만들기/번호 쓰기" 화면 재사용) | 위원 의견 |
