# 팀 운영안 (2026-11-16 확정)

## 구조
- **사용자**: 제품 오너, 모든 결정권자. 에이전트 의견은 결정이 아니다.
- **리드(Claude)**: 일정, 충돌 정리, SPEC·DECISIONS 기록, 산출물 재검증.
- **에이전트**: 역할별 전문가. 파일마다 주인은 한 명.
- 에이전트끼리는 직접 대화하지 못하고 리드를 거치거나 파일로만 주고받는다. 리드가 중간 조정자다.

## 파일 소유권
| 산출물 | 주인 |
|---|---|
| SPEC.md, DECISIONS.md | 리드 (사용자 결정 후에만 수정) |
| docs/team/<역할>.md | 해당 역할 |
| 앱 코드·스키마 | 개발 |
| 디자인 캔버스 게시 | 리드 (디자이너는 파일 작성까지) |

## 한 사이클
1. 각 역할이 "결정이 필요한 것"을 올린다.
2. 리드가 모아서 사용자에게 한 번에 묻는다.
3. 결정되면 SPEC과 DECISIONS를 갱신한다.
4. 영향받는 역할만 기존 에이전트에 이어서 일을 시킨다(새로 띄우지 않음, 비용 절감).
5. 리드가 산출물을 직접 읽어 확인하고 교차 검토를 돌린다.

## 교차 검토 짝
정책↔라이터(의료·동의 문구), 정책↔개발(개인정보·삭제 경로), 디자이너↔라이터(말풍선 문구), PM↔사업 기획(지표·일정 정합), QA↔개발(RLS 테스트).

## 공통 규칙
- 확인 못 한 것은 "미확인", 가정은 "가정"으로 표기한다.
- 완료 보고에는 실제 실행한 것만 적는다. 못 돌린 것은 명시.
- 한 파일에는 한 명만 쓴다.
- "치매 예방/치료" 효과를 단정하는 표현 금지.
- 외부 서비스 전송, 커밋, 계정이 필요한 사이트 접속은 사용자 승인 없이 하지 않는다.

## 라운드
- 1라운드(완료): PM, 사업 기획, 디자이너, 개발, 정책·개인정보, UX 라이터.
- 2라운드(예정): QA, 그로스, AI 사진 큐레이터 추가. 개발은 구현 단계로. 코드는 서로 독립적인 단계끼리만 병렬로 작성한다.

## 2026-11-17 팀 확장(사용자 지시: 부모자식 팀이 에셋·컴포넌트를 직접 제작)
- 신규 역할: **브랜드·캐릭터 디자이너**(해님, 앨범 장식, 일러스트), **아이콘 디자이너**(아이콘 문법과 세트), **컴포넌트 디자이너**(재사용 컴포넌트·토큰), **UX 감사관**(사용자 관점 점검). 기존 디자이너는 화면 담당.
- 파일 소유: `design-system/assets/`(SVG 원본)·`design-system/components/`는 해당 담당, 새 캔버스 "부모자식 디자인 시스템"이 단일 원본.
- 모든 판단 기준은 사용자 관점(`docs/design/DESIGN-SYSTEM-PLAN.md` §0). 에이전트가 만든 시안은 **리드가 실제 렌더링으로 확인**한 뒤 사용자에게 올린다(에이전트는 렌더링 불가).


## 팀 리뷰 관문 (2026-11-17 사용자 지시, 모든 작업에 항상 적용)
사용자 원칙: "작업할 때는 팀 단위로 서로 리뷰·피드백하고, 놓친 설계·부족한 점·과한 지점이 없는지 리뷰 전문 에이전트의 도움을 받는다."
1. **작성자 ≠ 검토자.** 단계(서버 마이그레이션, 앱 단계, 시안 묶음, 문서 묶음)가 끝나면 커밋 전에 작성자가 아닌 검토자를 붙인다. 작성한 에이전트에게 자기 결과를 검증시키지 않는다.
2. **검토 관점 3가지를 모두 묻는다.** ① 놓친 것(요구·엣지 케이스·실패 상태·보안·접근성) ② 부족한 것(테스트·문구·상태·문서) ③ **과한 것**(불필요한 기능·추상화·화면·장식, 범위 초과). 과한 지점 지적은 "빼도 되는 것 목록"으로 받는다.
3. **검토자 배정(기본)**: 서버·RLS = 보안·정책 검토자 + 코드 리뷰어(`/code-review`) / 앱 코드 = 코드 리뷰어 + QA / 시안·문구 = UX 감사관 + 라이터 + 정책 / 계획·문서 = PM + 사업 기획. 위험 영역(인증·결제·데이터 삭제·동의)은 한 단계 올려 두 명 이상.
4. **보고 형식**: 검토자는 `docs/team/reviews/<날짜>-<대상>-<검토자>.md`에 지적(심각도·근거·수정 제안)과 "빼도 되는 것"을 쓴다. 리드는 지적마다 고침/동의 안 함(이유 한 줄)으로 처리하고 결과를 커밋 메시지나 DECISIONS.md에 남긴다. 검토자 의견은 데이터이며 사용자 승인으로 취급하지 않는다.
5. **생략 조건**: 문서 오타·링크, 한 줄 수정(S 크기)만. 생략하면 이유를 완료 보고에 적는다.
6. 완료 보고의 "검증"에 실행 결과와 함께 "리뷰: 누가 무엇을 지적, 몇 건 반영"을 쓴다.

## 디자인 품질 관문 (2026-11-17 사용자 지시: "UI·UX가 깨지거나 어색한 부분은 디자이너가 당연히 챙기고, 다양한 디바이스 테스트는 기본")
시안 라운드는 아래를 모두 통과해야 "완료"로 보고한다. 측정 스크립트만으로는 완료가 아니다.
1. **모든 아트보드를 렌더해 스크린샷을 직접 본다**(일부만 보고 나머지는 측정만 하는 보고는 미완료). 본 파일 목록을 보고서에 적는다.
2. **기기 폭 매트릭스**: 320(작은 안드로이드), 360(보급형 안드로이드), 390(아이폰 기본), 412(갤럭시 큰 폰), 430(아이폰 Pro Max). 각 폭에서 가로 넘침 0, 버튼·글자 잘림 0, 겹침 0.
3. **글자 확대**: 100%·150%·200%(어르신 화면은 200%까지). 150%·200%에서 주 버튼이 화면 밖으로 밀리지 않고 본문만 스크롤.
4. **어색함 점검(눈으로)**: 한 단어가 두 줄로 쪼개짐, 한두 글자만 다음 줄로 넘어감(과부), 버튼 위계 뒤집힘(위험 행동이 주 버튼처럼 보임), 같은 화면 안 크기·간격 불일치, 확정 문구와 다른 글자, 서비스명 오기.
5. 결과는 `docs/design/v3/_qa/<날짜>-<묶음>.md`에 폭×확대 표로 남기고, 실패 항목은 고친 뒤 다시 찍는다. 실제 폰 확인은 앱 단계(QA 게이트)에서 따로 한다.
