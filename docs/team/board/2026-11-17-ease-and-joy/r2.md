# r2 · 반박·조정 (2026-11-17 연결 쉽게 + 완료감 회의)

참석: 기획(PM)·디자인팀·UX 감사관(73세)·정책·앱 개발. r1 원문은 `r1/`. 주재자가 쟁점별로 의견을 맞붙이고 표결(찬/반/조건부)을 받았다. 모든 위원이 같은 모델이라 쏠림 위험이 있어 소수 의견을 그대로 남긴다.

## 쟁점 1. 링크로 열었을 때 자동 연결까지 할까, 확인 화면을 둘까
- PM(r1): 탭 하나라도 줄이자 → 확인 화면 없이 연결 후 "연결됐어요".
- 정책 반박: T2(낯선 사람이 링크로 어르신을 자기 가족에 붙임). 누르기만으로 연결되면 사기 문턱이 0.
- UX 감사관 반박: "무엇이 일어났는지 모른다". 큰 버튼 하나는 부담이 아니라 안심.
- PM 수용: 확인 화면 [이 번호로 연결하기] 1탭 유지.
- **표결: 확인 화면 필수 5/5.**

## 쟁점 2. 확인 화면에 "누가 보낸 번호인지"를 보일까
- 정책: 호칭 미리 보기(peek)로 모르는 링크를 걸러낼 단서.
- 앱 개발: 서버 RPC 1개 + 3~4h, 번호를 가진 사람에게 호칭이 보임.
- 정책 재반박: 호칭은 낮은 민감도, redeem과 같은 시도 한도(5회/10분)로 묶으면 엿보기도 막힘. 손 입력 경로에도 같은 확인 화면을 쓰면 오입력(남의 가족 번호)도 걸러냄.
- UX 감사관: "아들이 보낸 거"라는 사람 단서가 핵심. 다만 "'엄마'라고 부르는 가족"은 어색 → "**어머니께 보낸 번호예요**"처럼 호칭+께.
- 디자인: 호칭이 기본값 "부모님"이면 단서 효과가 약함 → 그래도 같은 화면 구조 유지.
- **표결: 빌드 1 포함 4/5, 반대 1(앱 개발: 빌드 2로, 일정)**. 소수 의견 보존: 늦어지면 호칭 줄만 빼고 확인 화면은 유지.

## 쟁점 3. 링크로 들어오면 첫 화면 질문("이 휴대폰은 누구 거예요?")을 건너뛸까
- PM: 번호가 있으면 거의 부모 폰 → 건너뛰자.
- 앱 개발 반박: 자녀가 자기 폰에서 링크를 눌러 보는 경우(보낸 걸 확인), "한 기기 한 역할" 결정(어르신 익명 세션이 생기면 자녀 로그인 막힘)과 충돌. 잘못 건너뛰면 자녀 폰이 '부모 폰'으로 굳는다.
- 정책: 동의 화면(P2)은 어차피 거침.
- **표결: 건너뛰지 않음 4/5**(PM 소수: 첫 화면에 "가족이 보낸 번호가 있어요" 띠를 추가해 부모 버튼을 강조하자 → 디자인이 수용, 아래 결론에 반영).

## 쟁점 4. 손 입력: 6자리에서 자동 확인 vs "다음" 버튼 유지
- UX 감사관: 회색 "다음"은 고장처럼 보임. 단, 자동 확인 시 "확인하고 있어요"가 보여야 하고 틀리면 숫자를 지우지 말 것.
- 디자인: 자녀 인증번호와 같은 규칙(첫 화면 결정의 토스 패널). "다음"은 없애고 하단 고정은 보조 링크만.
- 앱 개발: 자동 확인 후 결과가 **확인 화면(쟁점 2)으로 이어지므로** 실수 연결 위험 없음.
- **표결: 자동 확인 5/5.** 6번째 숫자 후 300ms 멈춤 뒤 확인(마지막 숫자를 눈으로 볼 시간).

## 쟁점 5. 카톡 인앱 브라우저에서 번호가 사라지면 링크안은 의미가 있나
- 앱 개발: 1a(설치 경로 전달)는 스파이크 전엔 미확인.
- PM: 번호가 안 넘어가도 **링크 자체가 "앱을 어디서 받지?"를 없앤다**(지금 메시지엔 스토어 링크가 없음). 링크는 무조건 이득.
- UX 감사관: 번호가 안 넘어갈 때를 대비해 손 입력 화면에 "**카톡 메시지를 다시 보려면**: 아래 ▢ 버튼(최근 앱)을 누르세요" 한 줄 + 그림.
- **합의: 링크 + 손 입력 보조는 스파이크 결과와 무관하게 빌드 1. 스파이크(2~3h)는 1a 자동 채움이 카톡에서 되는지 판정, 안 되면 1b(이미 설치) 경로와 손 입력만으로 출시.**

## 쟁점 6. 지난 날(내 앨범) — 빌드 1인가
- PM: 사용자가 직접 요청, "완성도 > 출시일" 원칙.
- 앱 개발: 18~22h, 서버 마이그레이션 포함. 일정 부담.
- 정책: 30일·동의 거부·철회 조건만 지키면 찬성.
- **앱 개발이 스스로 낸 반전 논거**: 화면이 늦어져도 **"그날 받은 콘텐츠" 기록 컬럼은 빌드 1에 반드시** 넣어야 한다. 안 넣으면 출시 첫날부터의 기록이 사진 없이 남아 나중에 지난 날 화면을 만들어도 비어 있음(되돌릴 수 없음).
- 디자인: 진입은 탭이 아니라 P3 보조 링크(어르신 앱에 탭 바 신설 반대).
- **표결: 서버 기록 컬럼 빌드 1 필수 5/5. 지난 날 화면 빌드 1 포함 4/5(앱 개발 조건부: 디자인 동결 전에 시안이 나오지 않으면 첫 업데이트).**

## 쟁점 7. 달력 vs 목록
- 전원 목록(한 날 = 폴라로이드 한 장, 빈 날 없음). 달력은 빈 칸이 "안 한 날"로 읽힘(UX 감사관·정책). **5/5.**

## 쟁점 8. 완료 순간의 길이·진동·소리
- UX 감사관: 1초 넘으면 "멈췄나?". 디자인 반박: 첫 반응(도장 닿음·진동)은 180ms, 문구 500ms라 "멈춤"으로 느낄 틈이 없음. 나머지(도장 줄로 날아가기)는 P3가 이미 보이는 상태에서 진행 + 아무 데나 누르면 건너뜀.
- 진동: 단계 끝에는 없음, 코스 끝 도장 순간 1회만(5/5). 시스템 촉각 방식(시스템 진동 끄면 따라 꺼짐).
- 소리: 기본 **켜짐**(짧고 낮은 나무 도장 소리, 무음·진동 모드에서 안 남, 설정에 끄기) 4/5. 소수(UX 감사관): 기본 꺼짐 + 첫 완료 때 "소리도 들을까요?" 권유(배경 음악과 같은 방식). → 결론은 다수안, 실기기 3가구 관찰에서 "깜짝 놀람" 1건 이상이면 소수안으로 전환.
- 한 주 7칸 완성 특별 연출: **반대 5/5**(연속 보상 = 압박).

## 쟁점 9. 단계 카드 리듬 수정의 범위
- 디자인 D1~D10에 이견 없음. 앱 개발: 줄 높이 표는 전 화면 높이를 바꾸므로 **한 번에, 디자인 동결 전**. UX 감사관: D9 "모두 지움" 크기 동일이 체감 1순위.
- 정책: 해당 없음.
- **합의 5/5.** 단, 줄 높이 표의 여러 줄 본문 값(20→30 등)은 현행과 같아 위험 낮음, 한 줄 라벨(글자+8)만 실기기 200% 확인.
