# r1 법률 — 암호화 의무 대상 판정 (2026-11-19)

> **법률 자문 아님.** 「개인정보 보호법」 제29조, 「개인정보의 안전성 확보조치 기준」(개인정보위 고시, 2023-09-22 개정 제2023-6호로 통합) 제7조를 **2차 자료(itwiki 등)로 요약**한 것. 조문 원문(law.go.kr)·최신 개정 여부는 대조 전. 고위험 판단은 공개 전 KISA 118 무료 상담 재확인 권고(DECISIONS 11-19 Q-04).

## 1. 제7조 구조(2차 자료 요약)
| 항 | 대상 | 우리 해당 |
|---|---|---|
| ① | 비밀번호·생체인식정보 등 **인증정보**를 저장·송수신 시 안전한 알고리즘으로 암호화, 비밀번호는 일방향 | 이용자 비밀번호: 심사용 자녀 계정 2개뿐(GoTrue 해시 저장, 추정). 인증번호·refresh token: Supabase Auth가 처리 — 저장 형태는 미확인 → **질문 L-1** |
| ② | 이용자의 주민등록번호·여권번호·운전면허번호·외국인등록번호·신용카드번호·계좌번호·생체인식정보 저장 시 암호화 | **해당 없음**. 결제는 빌드 1에 없고 빌드 2도 Play·토스페이가 처리(우리 DB에 카드·계좌 없음) |
| ③ | 이용자 아닌 정보주체의 고유식별정보 | 해당 없음 |
| ④ | 인터넷 구간 송수신 시 암호화 | 앱↔Supabase·Firebase HTTPS(TLS 1.2/1.3, 공식) — 충족 |
| ⑤ | 개인정보취급자 PC·모바일·보조저장매체에 이용자 개인정보 저장 시 암호화 | 운영자 맥(FileVault), 내려받은 CSV·덤프. **FileVault 켬 확인을 대장에 기록**. 디스크 전체 암호화가 이 항을 충족하는지는 추정 → 질문 L-2 |
| ⑥ | 일정 규모 이상(대기업·중견·공공 10만 명, 중소 100만 명 이상) 암호키 생성·이용·보관·배포·파기 절차 수립 | **의무 아님**(규모 미달). 그래도 팀 정책으로 채택 권고 |

## 2. 컬럼별 법적 판정
- 이메일(auth.users), 카카오 회원번호, 구글 sub·이름·사진 주소: 개인정보이나 제7조②의 암호화 의무 목록 밖. 의무 없음.
- FCM 토큰, events.device_key: 개인정보(기기 식별·가명). 의무 없음.
- 고른 답(A/B)·코스 기록·응원 키: 개인정보이나 **민감정보(제23조) 아님**(건강·신념 등 아님 — 2026-11-18 개인화 회의에서 건강 정보 미수집 확정). 의무 없음.
- 호칭: 닫힌 목록 선택값. 의무 없음.
- admin_audit 대상 uuid·사유: 가명 식별자. 의무 없음. 단 사유에 메일 등을 적으면 "삭제 뒤 1년 보관"이 실명 정보 보관이 되어 방침 설명과 어긋남 → 서버 검사로 막자는 보안 위원 제안에 찬성.
- 초대 번호: 1회용 번호, 개인정보성 약함(data-safety 판단 유지).
- 결론: **법적으로 컬럼 암호화가 필요한 데이터는 없다.** 법이 요구하는 것은 ④ 전송 암호화와 ⑤ 취급자 기기 암호화, 그리고 제29조 전반의 안전성 확보(접근 통제·접속기록·파기)다.

## 3. 게시 문서 정정 필요
1. `publish-drafts/privacy.html` 11절 자리표시 `{확인 후 유지 또는 삭제: 저장된 데이터도 Supabase가 암호화해 보관합니다}` → 공식 근거 확인됨(Supabase security 페이지 "encrypted at rest with AES-256", DPA Schedule 1 디스크·백업 AES-256, data residency FAQ 백업 AES-256). **유지**하되 "데이터베이스와 백업은 Supabase가 AES-256 방식으로 암호화해 보관합니다"로 구체화.
2. 같은 문서 이용 기록 행 "로그인 번호를 되돌릴 수 없게 바꾼 값" → 해시 자체는 되돌릴 수 없지만 운영자는 계정 목록과 맞춰 볼 수 있다. 이용자가 "익명"으로 오해할 수 있어 **"로그인 번호를 그대로 쓰지 않고 바꾼 값(가명값)"**으로 정정 권고. 거짓 아님, 정확성 문제.
3. `internal-management-plan.md` §5 "저장: 확인 전(추정)" → 사실로 갱신 + 키 관리 정책(이번 SUMMARY) 링크. §3에 비밀값 대장·교체 이력 추가.
4. data-safety-form #19 "기기 밖으로 안 나감": Android 12+ 일부 제조사 기기 간 이전에서 allowBackup=false가 안 막는다는 공식 문서가 있으므로, 앱에서 이전 제외 규칙을 넣기 전까지는 사실과 다를 수 있음 → 앱 위원 조치 후 유지.

## 4. 유출 대응(제34조)
- 기존 내부관리계획 §9 유지(72시간 표현은 원문 대조 필요). 키 유출은 "개인정보 유출"과 별개로 **유출 의심 사고**로 대장에 기록하고, 키로 실제 데이터가 조회됐는지(Supabase 로그·감사)를 확인한 뒤 통지 여부를 판단.

## 질문(KISA 118·전문가 재확인용)
- L-1: 제7조①의 "인증정보"에 세션 refresh token·이메일 인증번호가 포함되는가, 포함되면 위탁사(Supabase) 플랫폼 저장 암호화(AES-256 디스크)로 충족되는가.
- L-2: 제7조⑤를 운영자 맥의 디스크 전체 암호화(FileVault)로 충족하는가.
- L-3: 최근 고시 개정안(행정예고 이력 있음, 2차 자료)이 ② 목록·적용 대상을 바꿨는가.

## 내가 틀릴 수 있는 이유
- 2차 자료끼리 항 번호·문구가 다르다(일부는 개정 전 제6조 체계). 원문 대조 전 판단이다.
- "이용자"·"정보통신서비스 제공자" 구분이 2023 통합 개정으로 바뀌어 ② 적용 범위가 넓어졌을 수 있다. 그래도 ② 목록 항목을 우리가 수집하지 않는다는 결론은 바뀌지 않는다.
