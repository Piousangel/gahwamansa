# r2 상호 반박·표결 — 저장 암호화·키 관리 (2026-11-19)

위원: 보안(S)·서버(B)·법률(L)·앱(A). 주재자가 r1 4편을 서로에게 보여 준 뒤 반박을 받고 안건별 표결. 4명이라 2:2면 "현행 유지 + 빌드 2 재논의".

## 반박 요지
- **B → S (카카오 큐 암호화)**: 키를 Vault에 두면 postgres·service_role 침해에는 효과 0, 막는 것은 "표 덤프 유출"뿐. 큐는 성공 즉시 지워지고 평균 체류 10분 이하(설계상). 키 분실 시 큐 처리 불가라는 새 장애점이 생긴다. 차라리 운영 SQL(metrics ⑧)이 회원번호를 출력하지 않는다는 지금 상태(사실: 출력 없음)를 규칙으로 고정하자.
- **S 재반박**: 30일 포기 행은 남는다. → **L**: 포기 행 30일은 방침에 이미 적은 예외(DECISIONS 11-18). 법적 의무 없음. S는 "포기 행이 생기면 운영자가 즉시 수동 처리하고 행을 지운다"를 06시 점검에 넣는 조건으로 철회 대신 소수 의견 유지.
- **B·L → S (device_key HMAC)**: uid는 무작위 UUID(122비트)라 sha256을 역산할 방법이 없다. 연결 가능한 사람은 auth.users를 이미 가진 사람뿐 → 그 사람은 events 없이도 다 안다. 이득이 거의 없고 키는 교체 불가 키가 된다. **문구 정정(가명값)이 실질 조치.** S 동의, 소수 의견으로만 남김.
- **A → S (D2D)**: S의 T6 동의, 조치는 data_extraction_rules. S·B 동의. L: 방침·데이터 보안 양식 문구를 사실에 맞추는 데 필요 → 빌드 1 필수.
- **S → A (세션 Keystore)**: 루팅 기기에서 refresh token을 빼 가면 부모님 가족의 답을 볼 수 있다. → **A**: 루팅 기기에서는 메모리·후킹으로도 뺄 수 있어 Keystore가 완전한 방어가 아님. 반면 키 무효화는 어르신 연결을 조용히 끊는다. **B**: 서버 쪽 피해 범위는 RLS로 그 가족 31일 답·날짜로 제한됨. S는 빌드 2 조사 조건으로 동의.
- **L → B (Edge 키 이행)**: legacy 키 폐기 시점 불명확은 위험을 키울 뿐 줄이지 않는다. production을 새로 만드는 지금(W3 말)이 이행 비용 최저. 찬성.
- **S → B (0046 범위)**: display_name 제거 시 0014 grant 목록을 다시 써야 하고 parent_family_list pgTAP이 이 컬럼을 참조함 → 테스트 수정 포함해 추정 유지(2~3h). B 동의.
- **A → 전원 (셸 기록)**: ops 스크립트가 키를 env에서만 읽어 사용자가 명령줄에 붙여 넣게 된다. 숨김 입력(readline, 화면 표시 없음) 대체 경로를 스크립트에 넣자. B 동의(서버 줄 소유 스크립트), 시간 1.5~2h.
