# r2 · 위원 ③ 차별화 전략가 (2026-11-19)

r1 문서 8개(A~H)와 r2-ballot.md를 읽었다. 웹 추가 조사는 하지 않았다. 반박에 필요한 근거는 모두 r1 문서와 저장소의 결정 문서에 있다. 코드와 git은 손대지 않았다. 시간은 모두 추정이고, 어르신 검증은 0회다.

## 1. 반박 (3건)

### 반박 1. V16 '고마워요' 신호는 새 독창성 안이 아니라 이미 채택된 F22다. V15와는 대체 관계가 아니라 층이 다르므로 병행한다
- **사실**: A의 1순위(A §4-1: CheerDialog에 "고마워요" 1탭 → 자녀 푸시, 자녀 화면에 '답장 없음' 표시 금지, 6~8h)는 기능 회의 빌드 2 상위 3위인 **F22 '응원 답장 1탭'(7h, 자녀 화면 '답장 없음' 상태 금지)**과 내용·조건·공수가 사실상 같다(feature-ideation/SUMMARY.md 빌드 2 상위 5, DECISIONS 11-17 기능 회의). 독창성 안건으로 따로 표결하면 이미 채택된 것을 다시 채택하는 셈이다.
- **독창성 판단**: A가 근거로 든 Aura 'love'와 みてね 반응(A §2-1 #1·#3)은 업계에서 흔한 방식이다. 바로 그래서 "있어야 할 기본기"이지 "남이 못 따라 할 해자"는 아니다. 내 r1 §1.4 기준(기능 단위는 모두 복제 가능)으로 보면 V16은 위생 요인이다.
- **두 안의 관계를 분명히 하면**:

| | V16 = F22 '고마워요' | V15 = H1 '어르신이 묻는 날' |
|---|---|---|
| 어르신이 보내는 것 | 감정 신호(내용 없음) | 질문(내용 있음, 자녀 답을 받아 옴) |
| 대화 소재가 생기나 | 아니다 | 그렇다. 자녀 답이 다음 날 어르신 화면에 도착한다 |
| 감시 위험 | 응원을 연 시각이 자녀에게 간접적으로 드러남(아래 조건 필요) | 물어보기 빈도를 자녀 리포트에 표시하지 않으면 낮음 |
| 서버 | cheers에 답장 행 1개 | F14 자녀 답 저장을 재사용 |
| 해자 여부 | 아님(기본기) | 위치 차별(카운터 포지셔닝, r1 §2 H1) |

- **결론**: **병행한다. 순서는 V16(F22)를 먼저, V15를 다음에 둔다.** V16은 싸고 이미 계획에 있으며, 어르신이 "보내는 사람"이 되는 첫 경험(1탭)을 만든다. V15는 그 위에 "묻는 사람"을 얹는다. 두 버튼을 같은 화면에 두지는 않는다. '고마워요'는 P8 응원 도착에만, '물어보기'는 P7 완료 뒤에만 둔다(H 레드라인: 같은 화면에 행동 셋 이상 금지, 어르신 버튼 3개 이하 SPEC 완료 조건 6).
- **V16에 붙일 조건 하나**: 자녀 푸시 문구에 **시각을 쓰지 않는다**("엄마가 고마워해요" ○ / "엄마가 오전 7시에 응원을 봤어요" ×). 누르지 않은 응원은 자녀에게 아무것도 보이지 않는다. 그래야 읽음 확인이 되지 않는다(A 자신의 '피할 것' 칸, Aura 행).

### 반박 2. V7 '연결은 코스 뒤에'(Duolingo식)는 우리 퍼널에는 맞지 않는다. 지금 구조(링크 번호 채움 + '코스 보기' 출구 유지)로 충분하다
- B의 근거 S1(Duolingo)은 **쓰는 사람과 가입하는 사람이 같은** 제품이다. 우리 앱은 자녀가 이미 가입하고 번호를 만들어 링크로 보낸 뒤 어르신이 앱을 연다(SPEC §2, ease-and-joy A). 링크로 들어오면 번호가 채워진 P1c에서 **1탭**이면 연결된다(D §1, `useConnectFlow.ts` 링크 번호 0ms). 연결을 미뤄도 줄어드는 마찰은 1탭뿐이다.
- 반대로 잃는 것이 크다.
  - ① 자녀가 돈을 내는 이유(첫 답 보기)가 늦어지고, 미연결로 남는 가구가 늘 수 있다(추정). 사업 모델의 분모인 "연결되어 첫 리포트를 본 자녀"(SPEC §1)가 줄어든다.
  - ② 미연결 기록을 연결 뒤 보여 줄지에 대해 동의 범위 정책이 새로 필요하다(B D-b 스스로 미해결로 둠). 31일 보관·동의 거부 결정(DECISIONS 11-16)과 얽힌다.
  - ③ 손 입력 경로(번호를 외워 와야 함, D §2 표 4행 '상')만이 실제 벽이다. 해법은 연결 순서가 아니라 D의 한 줄 안내와 '코스 보기' 이탈 측정이다.
- **결론**: V7은 반대한다. 단, '코스 보기' 출구는 유지하고 비율을 잰다(D 제안). 측정 결과 손 입력 가구의 이탈이 크면 빌드 2에서 다시 다룬다.

### 반박 3. V24 '앱을 열면 사진 먼저'(Komp식)는 Komp의 맥락과 다르고, 이미 정한 레드라인과 부딪친다
- A가 근거로 든 Komp는 A 표에서도 "어르신이 응답할 길이 없음(수신만), 단방향은 우리 목표와 다름"으로 정리돼 있다(A §2-1 #6 피할 것 칸). 받기만 하는 제품의 첫 화면을 응답·완료 의례가 핵심인 우리 P3에 옮기면, 도장·단계 행이라는 의례(H §2: "도장·앨범 같은 의례의 독창성은 좋다")가 스크롤 아래로 밀린다.
- H는 레드라인으로 "단계 3행 + 주 버튼이 스크롤 없이 보일 것"을 두었다. v4는 화면 높이 예산 때문에 이미 잘림 문제를 다루는 중이다(DECISIONS 11-19 v4). 큰 사진을 위에 얹으면 320·200%에서 이 레드라인이 깨질 가능성이 높다(추정).
- 같은 목적("숙제가 아니라 선물")은 더 싼 방법으로 달성할 수 있다. P3 '지금 할 차례' 행에 오늘 사진 작은 썸네일을 두고, 행 전체를 누를 수 있게 하는 것(V2와 묶음)이다.
- **결론**: V24는 반대한다. 대안은 V2와 썸네일을 묶는 것이다(디자인 판단은 동결 일정에 맡김).
