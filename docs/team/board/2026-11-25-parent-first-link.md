## 오너에게 보여 줄 한 장 요약

**결론**: 됩니다. 다만 아무나 그 번호로 부모님과 이어지지 않게, 마지막에 **부모님이 직접 '네'를 누르는 단계**를 넣습니다. 처음 출시에는 넣지 않고 바로 다음 업데이트에 넣는 것을 권합니다. 그 전에도 시설 홍보는 시작할 수 있습니다. 지금 앱도 부모님이 먼저 깔고 써 보시다가, 자녀가 나중에 보낸 번호를 쓰면 이어지기 때문입니다.

**부모님이 먼저 시작할 때 (1.1)**
1. 시설 선생님이 어르신 휴대폰에 앱을 깔고 '부모님 휴대폰이에요'를 누른다.
2. 번호 칸 아래 '번호가 없어요' → **'자녀에게 알려 줄 번호 만들기'**를 누른다.
3. 큰 글자로 번호 6자리가 나온다. 전하는 방법은 세 가지다.
   - [카톡으로 보내기]
   - [크게 보기]: 화면을 보여 주거나 종이에 옮겨 적는다.
   - 선생님이 가족에게 전화로 불러 준다.
4. 어르신은 그날부터 코스를 해 보신다. 고른 답은 연결 전이라 저장되지 않는다(지금과 같다).
5. 자녀는 앱을 깔고 로그인한 뒤 **'부모님이 알려 준 번호 쓰기'**를 누르고, 6자리와 '부모님께 보일 이름'(예: 딸)을 고른다.
6. 어르신 휴대폰에 **'딸이라는 가족이 연결하려고 해요. 내 가족이 맞나요?'**가 뜬다. 어르신이 직접 [네, 연결할게요]를 누른다.
7. 이어서 지금과 같은 '고른 답을 가족과 나눠요'(동의) 화면이 나온다. 이것도 어르신이 직접 정한다.
8. 자녀 휴대폰에 '연결됐어요'가 뜬다. 그날부터 고른 답이 보인다.

**지켜야 할 선**
- 연결과 동의는 어르신 본인이 누른다. 선생님이나 가족이 대신 누르지 않도록 화면에 안내한다.
- 시설은 어르신 정보를 받지도 보지도 않는다. 시설 계정이나 시설용 화면은 만들지 않는다.
- 모르는 사람이 번호를 쓰면 어르신이 '아니에요'를 누른다. 그 번호는 바로 버려지고 새 번호가 생긴다. 연결된 뒤에도 설정에서 그 가족과의 연결을 끊을 수 있다.

**작업량**: 큰 편(L)이다. 서버 약 3일, 앱 약 3일, 처리방침·약관 고치기 반나절, 시험 1일이다(추정). 출시 일정은 늦추지 않는다.

## 1. 화면 흐름 (PL-1)

### 1.1 원칙
- **FS는 바꾸지 않는다.** '부모님 휴대폰이에요' / '자녀 휴대폰이에요' 두 버튼 그대로 둔다. 역할(누구 휴대폰인지)과 방향(누가 번호를 만드는지)을 FS에서 한꺼번에 묻지 않는다. 방향은 각 역할의 **번호 화면 안에서** 고른다. 두 흐름이 한 앱에서 헷갈리지 않게 하는 가장 작은 방법이다.
- 번호는 두 종류지만 이름은 NAMES.md대로 **'번호'** 하나다. 구분은 **누가 어디에 쓰는지를 붙인 말**로 한다.
  - 부모님 화면: '자녀에게 알려 줄 번호'
  - 자녀 화면: '부모님이 알려 준 번호'
  - 지금 번호는 그대로 '가족에게 받은 번호'(P1)·'부모님께 보낼 번호'(C3)라고 부른다.
- 글자 200%: 번호는 **3자리 + 3자리 두 줄**로 쓰고, 한 자리 폭은 화면 폭의 12% 이상이다. 버튼은 모두 세로 한 줄로 두고 한 손 엄지 영역(아래 40%)에 놓는다. 끌기나 두 손가락 조작은 없다. 스크롤로 모든 버튼에 닿는다(FEATURE-MAP 3절 공통 규칙).

## 2. 연결 전 기록 (LG-1 + PL-1)

**권장: 지금처럼 저장하지 않는다. 연결과 동의 이후부터만 저장한다.** 리드 결정 없이 기존 결정(DECISIONS 11-17 152·329행)을 그대로 따른다.

| 안 | 내용 | 법적 근거 | 판단 |
|---|---|---|---|
| **A(권장)** 저장 안 함 | 번호를 만든 부모님도 연결 전에는 P3(연결 전)과 같다. 답은 서버로 가지 않고 이번 주 도장만 기기에 7일 남는다 | 새 처리 없음. 지금 방침 2절 "가족과 연결되기 전에 찍은 이번 주 도장 날짜 … 고른 답·낱말은 저장하지 않습니다"와 그대로 맞는다 | 동의 화면(P2)의 "보여 주는 것"이 처음부터 사실이다. 0057과도 충돌이 없다 |
| B 저장, 연결 뒤에도 안 보여 줌 | 부모님 본인 '지난 날'용으로만 저장 | 보여 주기 동의와 따로 '저장 동의'가 하나 더 필요하다(저장 목적이 다르다). 근거는 법 제15조①1호 동의, 또는 4호(요청한 기능 제공)로 볼 여지가 있으나 확인 필요 | 연결 전 부모님에게 동의 화면이 하나 더 생긴다. 프로필 없이 저장할 곳도 없어서 서버를 크게 고쳐야 한다. 이득이 작다 |
| C 저장하고 연결 뒤 소급해서 보여 줌 | 연결 전 답도 자녀에게 보임 | 동의 전에 모은 답을 동의 뒤 제3자(자녀)에게 보이게 하려면, 동의 화면에서 '지금까지 고른 답도 보여 줄까요?'를 따로 물어야 한다(policy r1 C) | 시설에서 선생님이 대신 고른 답이 섞여 있을 수 있다. 소급 공개는 그 답을 '부모님 답'으로 가족에게 보여 주게 된다. **권하지 않음** |

**0057과의 관계**
- A안에서는 부모님 프로필을 **P1q의 '네' 순간에** 만든다(§3). 그래서 번호만 만든 부모님 기기는 계속 '익명 + 프로필 없음'이고, **0057의 90일 정리 대상에 그대로 남는다.** 번호 행과 요청 행은 `auth.users`를 `on delete cascade`로 가리켜 같이 지워진다.
- 번호를 만들었는데 자녀가 오지 않고 부모님도 앱을 열지 않으면, 번호는 7일 뒤 쓸 수 없게 되고 계정은 90일 뒤 정리된다. 처리방침 4절 '가족과 연결하지 않은 계정' 행에 "만든 번호와 연결 요청 기록"만 더하면 된다.
- 앞선 보드(r1 dev)가 제안한 '번호를 만들 때 부모님 가족과 프로필을 먼저 만드는 안'은 쓰지 않는다. 그 안은 다음 문제를 만든다.
  - 프로필이 있어 0057 정리에서 빠지고, 자녀 없는 빈 가족이 생긴다.
  - 그 가족을 지울 규칙(0008 '마지막 자녀가 지우면')이 맞지 않게 된다.
  - 동의 전 저장 문제가 다시 생긴다.

## 3. 서버 계약 초안 (DV-2)

### 3.1 설계 선택
- **새 표 두 개.** `invite_codes`를 고쳐 같이 쓰지 않는다. 이유는 세 가지다.
  - `family_id not null`·`created_by → profiles`가 연결 전 부모님(프로필 없음)과 맞지 않는다.
  - 열을 nullable로 풀면 지금 RPC 4개(issue·peek·redeem·purge)와 RLS `codes_read`에 모두 종류 조건을 더해야 해서 회귀 범위가 넓다.
  - 심사용 재사용 번호 트리거(0025)와도 엮인다.
- **부모님 프로필과 가족은 부모님이 '네'를 누를 때 만든다.** 자녀가 번호를 쓰면 '요청'만 생긴다. 요청 단계에서 자녀는 부모님에 대해 아무것도 받지 않는다(호칭도 안 받는다).
- 번호 생성은 지금 식을 그대로 쓴다(`gen_random_bytes(4) % 1000000`, 5번 다시 시도). **두 표 사이에서도 쓰지 않은 번호가 겹치지 않게** 두 발급 함수가 같은 잠금 줄(`7002`)을 잡고 상대 표를 확인한다.

### 3.2 표 스케치
```sql
-- 부모님 휴대폰에서 만든 번호(연결 전 익명 기기만)
create table public.parent_link_codes (
  id uuid primary key default gen_random_uuid(),
  code char(6) not null check (code ~ '^[0-9]{6}$'),
  parent_uid uuid not null references auth.users(id) on delete cascade,   -- 0057 정리 때 같이 지워짐
  created_at timestamptz not null default now(),
  expires_at timestamptz not null default now() + interval '7 days',
  used_at timestamptz,                                                     -- 자녀가 쓴 시각(요청 생성)
  used_by uuid references auth.users(id) on delete set null
);
create unique index parent_link_codes_active on public.parent_link_codes (code) where used_at is null;
create index on public.parent_link_codes (parent_uid, used_at);

-- 자녀가 번호를 써서 생긴 연결 요청(부모님 '네' 전까지 아무것도 공개하지 않음)
create table public.parent_link_requests (
  id uuid primary key default gen_random_uuid(),
  code_id uuid not null references public.parent_link_codes(id) on delete cascade,
  parent_uid uuid not null references auth.users(id) on delete cascade,
  child_uid uuid not null references auth.users(id) on delete cascade,
  child_label text not null check (child_label in ('son','daughter','daughter_in_law','son_in_law','grandchild','family')),
  parent_title text check (parent_title in ('엄마','아빠','어머니','아버지','할머니','할아버지','부모님')),  -- 자녀가 고른 호칭(0012·0019와 같은 닫힌 목록)
  status text not null default 'pending' check (status in ('pending','accepted','rejected','expired','cancelled')),
  created_at timestamptz not null default now(),
  decided_at timestamptz
);
create unique index parent_link_requests_one_pending on public.parent_link_requests (parent_uid) where status = 'pending';
create index on public.parent_link_requests (child_uid, status, decided_at);
-- 두 표 모두 RLS on, 정책 없음(클라이언트 직접 접근 0) — notification_queue와 같은 방식. 접근은 아래 definer RPC로만.
-- profiles에 child_label text null 열 추가(같은 check). P16 목록·P1q '이 가족에는 n명' 표시용.
```

### 3.3 RPC (모두 `security definer`, `search_path=''`, authenticated만 실행, anon·public revoke)

| RPC | 누가 | 하는 일 | 돌려주는 것 · 이유 |
|---|---|---|---|
| `issue_parent_link_code(p_new boolean default false)` | 부모님 기기: **익명** + **프로필 없음** | 잠금 7002를 잡는다. 쓰지 않은 번호가 있고 기간 안이면 그 번호를 그대로 돌려준다(화면을 열 때마다 바꾸지 않음). `p_new`면 옛 번호를 지우고 새로 만든다. 대기 중 요청이 있으면 번호 대신 요청을 알린다 | `{ok, code, expires_at}` · `not_parent_device`(비익명) · `already_linked`(프로필 있음, R-3) · `pending_request`(→ 앱은 P1q) · `code_generation_failed` |
| `redeem_parent_link_code(p_code, p_label, p_title, p_request_id uuid)` | 자녀: **비익명** + (프로필 없음 또는 `role='child'`) | 잠금 7001(지금 redeem·peek와 같은 줄). `redeem_attempts`의 uid 한도(10분 5회)와 전체 한도를 지금과 같이 쓴다. 번호를 찾고, 기간을 보고, 요청을 만든 뒤 번호를 사용 처리한다. 같은 `p_request_id`로 다시 오면 같은 결과를 준다(0059 재시도 규칙) | `{ok, status:'pending', request_id}` · `child_login_required`(익명) · `not_child`(부모 프로필) · `invalid` · `expired` · `used` · `wrong_side`(쓰지 않은 `invite_codes` 번호와 같음) · `rate_limited`+`retry_after_sec` · `busy` · `blocked`(§4.3) · `already_family`(이 부모님이 이미 내 가족) |
| `parent_link_status()` | 부모님 기기 | 내 번호와 대기 중 요청을 보여 준다 | `{state:'none'}` · `{state:'code', code, expires_at}` · `{state:'pending', request_id, child_label, family_size}` · `{state:'linked'}` |
| `respond_parent_link(p_request uuid, p_accept boolean)` | 부모님 기기(요청의 `parent_uid` = 나) | **accept**: 잠금 7001 → 요청이 아직 pending인지, 기간 안인지, 내 프로필이 없는지 다시 본다 → 자녀 프로필이 없으면 가족(`created_by`=자녀) + 자녀 프로필 + entitlements(`create_family`와 같은 값)를 만든다 → 자녀 가족에 부모 프로필(`parent_title` = 요청의 호칭, `consented_at` null)을 만든다 → 자녀 `child_label`을 기록한다 → `notification_queue` 'parent_connected' → 내 남은 번호를 정리한다. **reject**: 요청을 rejected로 바꾸고 새 번호를 만들어 돌려준다 | accept `{ok, family_id, profile_id}`(→ 앱은 약관 확인 기록 → P2) · reject `{ok, code, expires_at}` · `not_found` · `expired` · `already_linked` |
| `child_parent_link_status()` | 자녀 | 내 최근 요청 하나를 보여 준다 | `pending` · `accepted` · `not_connected`(거절·만료·취소를 **구분하지 않는다**. 거절 사실이 상대에게 압박이 되지 않게) |
| `cancel_parent_link_request(p_request)` | 자녀 | pending을 cancelled로 바꾸고, 부모님 번호를 다시 쓸 수 있게 되돌린다(`used_at` null, 기간 그대로) | `{ok}` |
| `parent_remove_child(p_child uuid)` (§4.4) | 연결된 부모님 | 같은 가족 자녀 한 명의 연결을 끊는다 | 범위는 §4.4 |

**지금 함수에 더할 것**
- `issue_invite_code`: 잠금 7002를 잡고, 번호가 `parent_link_codes`의 쓰지 않은 번호와 겹치면 다시 뽑는다.
- `redeem_invite_code`·`peek_invite_code`: `invite_codes`에 없고 `parent_link_codes`의 쓰지 않은 번호와 같으면 `wrong_side`를 돌려준다(실패로 기록). 연결에 성공하면 내(부모님 기기) 번호와 pending 요청을 정리한다.
- `purge_expired_data`: 쓴 지(또는 기간이 지난 지) 30일 지난 `parent_link_codes`, 결정된 지 30일 지난 `parent_link_requests`를 지운다.
- `log_event` 허용 목록(0053): §1.5 이벤트 4개를 더한다.
- 이벤트 `purpose` 정규식에는 손대지 않는다.

### 3.4 같은 6자리 칸에서 어느 쪽 번호인지 구분하기
| 안 | 방법 | 판단 |
|---|---|---|
| **A(권장)** 번호 공간 공유 + 서버 판별 | 두 표의 쓰지 않은 번호가 절대 겹치지 않는다(발급 때 서로 확인, 잠금 7002). 칸은 똑같이 6자리다. 어느 쪽 화면에서 썼는지(부모님 기기·자녀 계정)로 서버가 맞는 표를 고르고, 반대 표에 있으면 `wrong_side` | 사람이 외울 규칙이 없다. 지금 번호와 형식이 같아 P1 부품을 그대로 쓴다 |
| B 앞자리 규칙(예: 부모님 번호는 9로 시작) | 눈으로 구분된다 | 번호 공간이 1/10로 줄어 추측이 10배 쉬워진다. '9로 시작하면…'을 어르신과 선생님에게 설명해야 한다. 기각 |
| C 자릿수 다르게(7자리) | 형식으로 구분된다 | 입력 부품과 테스트가 둘로 갈라지고, 전화로 불러 줄 때 틀리기 쉽다. 기각 |

`wrong_side`가 '그 번호가 지금 어딘가에 있다'는 사실을 드러내는 점: 실패로 세어 같은 한도(10분 5회)에 묶인다. 알아낸 번호를 맞는 쪽에서 써도 §4의 확인 단계가 남는다. 감수할 만하다.

### 3.5 링크
- 지금 초대 안내 페이지는 번호를 주소 `#` 뒤에 둔다(방침 6절). 부모님이 보낸 링크는 `#k=p&c=123456`처럼 종류를 붙인다.
- 앱은 `k=p`면 C1p 칸에만, 없으면 지금처럼 P1 칸에만 미리 채운다. 자동으로 연결하지 않는 규칙(방침 2절)도 그대로다.

## 4. 보안·오용 (DV-2 + LG-1)

### 4.1 위험의 방향이 바뀐다
- 지금 흐름: 번호를 **받는 쪽이 부모님**이다. 번호가 새도 최악은 부모님이 엉뚱한 가족에 들어가는 것이고, 그때도 동의(P2)가 남는다.
- 역방향: 번호를 받는 쪽이 **'자녀라고 말하는 사람'**이다. 번호가 새면 모르는 사람이 부모님 답을 계속 볼 수 있다.
- 시설에서는 종이가 여러 사람 손을 거친다. 선생님 휴대폰, 다른 입소자의 가족, 방문객이 번호를 볼 수 있다. 위험이 지금보다 한 단계 크다(policy r1과 같은 판단).

### 4.2 대책 비교
| 대책 | 막는 것 | 못 막는 것 | 채택 |
|---|---|---|---|
| **부모님 확인(P1q), 서버 강제** | 종이·카톡을 본 모르는 사람의 연결. 확인 전에는 프로필이 없어서 서버에서 아무것도 보이지 않는다 | 부모님이 습관처럼 '네'를 누르는 경우, 옆 사람이 대신 누르는 경우 | **필수(R-1)** |
| 자녀가 고른 이름 보여 주기(정해진 보기 6개) | '누가'를 알아볼 단서가 생긴다 | 거짓 보기 선택('딸'). 직접 쓰는 칸은 개인정보 수집과 사칭 문구('엄마 나야') 위험 때문에 두지 않는다 | 채택 |
| 짝 맞추기 숫자 2자리(두 화면에 같은 숫자) | 전화로 함께 확인할 때 | 어르신에게 숫자 대조라는 한 단계가 더 생긴다. 시설에서는 두 사람이 같이 있지 않다 | 기각(1.2에서 다시 봄) |
| 번호 유효 24시간 | 종이가 오래 돌아다니는 위험 | 시설 → 가족 전달은 방문·통화 주기라 며칠 걸린다(가정) | 기각. **7일** + 쓰면 바로 사용 처리 + '아니에요'면 즉시 새 번호 |
| 연결 뒤 7일 띠 '{딸}과 연결됐어요. 모르는 분이면 끊을 수 있어요' | 습관적 '네' 뒤 늦게 알아챈 경우 | — | 채택(P3 띠, 7일 뒤 사라짐) |
| 시설 안내지에 '선생님 휴대폰으로 연결하지 마세요' | 선생님이 선의로 자기 폰에 연결하는 경우 | 악의 | 채택(§6.1) + 약관 제3조 금지 행위('부모님 몰래 연결해서 답 보기')는 이미 있음 |

### 4.3 추측과 한도
- 번호 공간은 10⁶이다. 쓰지 않은 부모님 번호가 N개면 한 번 맞을 확률은 N/10⁶이다.
- 자녀 한 계정은 10분에 5회로 묶인다(P1 잠금 재사용). 자녀는 비익명 계정(카카오·구글·이메일 인증)이라 계정을 늘리는 비용이 익명보다 크다.
- 맞혀도 얻는 것은 '부모님 화면에 요청 하나'뿐이다(§4.2). 부모님 쪽 정보는 하나도 받지 못한다.
- **전체 한도 300회/10분을 두 방향이 같이 쓰면**, 자녀 쪽 공격이 부모님 쪽 연결까지 `busy`로 막는다. 지금도 그런 구조다. 새 함수는 전체 한도를 **방향별로 따로** 센다. 이를 위해 `redeem_attempts`에 `kind` 열을 더하고 기본값은 'parent_device'로 둔다.
- 차단: 한 자녀 계정이 30일 안에 **서로 다른 부모님에게 거절 3번**을 받으면 30일 동안 `blocked`다. 같은 부모님에게 두 번 거절받으면 그 부모님 번호는 이 계정에서 `invalid`로 다룬다.

### 4.4 연결 끊기·차단 경로 (부모님 쪽)
- 지금 P16 '그만두기'에는 [그만 보여 주기] / [모두 지우기]만 있다. **자녀 한 명만 끊는 길이 없다.**
- 새로 `parent_remove_child(p_child)`를 둔다.
  - 그 자녀의 프로필을 이 가족에서 뺀다.
  - 자녀 계정은 남고, 자녀는 C1d부터 다시 시작한다.
  - 응원 기록 중 그 자녀가 보낸 것은 지운다.
  - 마지막 자녀가 빠지면 지금 삭제 규칙(0008 '마지막 자녀면 가족 전체')과 부딪친다. 그래서 **마지막 자녀는 이 RPC로 뺄 수 없고** 부모님에게는 [모두 지우기]를 권한다.
  - 시트 문구 초안: '{딸}과 연결을 끊을까요?' · '끊으면 {딸}에게 고른 답이 보이지 않아요' · [연결 끊기] / [닫기].
- 이 RPC는 지금 자녀 먼저 가족에도 쓸 수 있다. 삭제가 걸린 위험 영역이라 독립 리뷰 2명이 필요하다(DECISIONS 11-20 리뷰 단계).

- **약관 동의 시점**: 지금은 연결할 때 약관 한 줄로 동의한다(terms 제4조). 역방향에서는 번호를 만드는 사람이 선생님일 수 있다. 그래서 **약관·방침 확인 기록(`record_terms_agreement`)은 P1q '네'를 누를 때** 남기고, 그 화면에 지금 P1의 약관 줄을 둔다. 번호를 만들 때는 기록하지 않는다.
- 번호를 만들 때 생기는 처리(무작위 로그인 번호, 번호, 시각)는 '이용자가 요청한 기능을 제공하는 데 꼭 필요한 처리'(법 제15조①4호, 방침 머리의 "서비스 제공")로 본다(잠정). 선생님이 누른 경우 '이용자의 요청'으로 볼 수 있는지가 L-8이다.
- **의사능력**: 시설에는 스스로 정하기 어려운 분도 계실 수 있다. 가족이나 시설이 동의를 대신할 수 없다는 전제로, 안내 문구로만 막아도 충분한지가 L-9다. 홍보물에는 특정 질환이나 시설 유형을 대상으로 삼는 표현을 쓰지 않는다(guardrails 1절).

- 시설은 이용자 정보를 **받지도, 보지도, 맡아 처리하지도 않는다.** 시설용 계정·화면·명단 기능을 만들지 않는다.
- 그래서 처리 위탁(법 제26조)도 제3자 제공(제17조)도 아니다(잠정).
- 제휴를 맺는다면(홍보물 비치 수준) 협약서에 넣을 세 줄 초안:
  1. 시설은 이 앱의 이용자 정보를 받거나 처리하지 않는다.
  2. 직원의 설치 도움은 입소자 본인의 요청에 따른 사실 행위이며, 연결·동의 화면은 입소자 본인이 누른다.
  3. 시설은 입소자 이름과 연결 번호를 함께 적은 명단을 만들지 않는다.
- 3번은 중요하다. 시설이 '이름 + 번호' 명단을 만들면 그 명단은 시설 자신의 개인정보 처리가 되고, 새면 특정 어르신을 노린 연결 시도로 이어진다. 안내지 번호 칸에 이름 칸을 두지 않는 이유다.
- 제휴로 대가(무료 이용권, 수수료)가 오가면 B2B 관계가 생긴다. 그때 위탁 여부를 다시 본다. 지금 결정(DECISIONS 11-16)은 B2B를 사이드 탐색으로만 두고 있다.
