# QA·접근성 의견 (Gemini 에셋 R1) · 2026-11-17
다른 위원 파일은 읽지 않았다. 용량·시간 수치는 모두 가정이고, 토스 WebView 실측은 미확인이다.

## 안건별 입장
**A 해님(하이브리드): 찬성.** 근거(사용자 관점): 어르신이 해님을 볼 때 크기는 화면마다 44~92px로 다르다. 래스터는 크기마다 선명도와 용량이 흔들리지만 SVG는 한 파일로 150% 확대까지 선명하다(사실: 벡터의 성질). 래스터로 교체하면 표정 5종 × 크기 3종 × 밀도 3배수(@1x/@2x/@3x, 웹은 srcset)로 파일 약 45개를 관리해야 한다(가정). 수정 제안: Gemini는 콘셉트 탐색에만 쓰고, 앱 안에 들어가는 해님은 SVG만 허용하는 것을 검수 규칙으로 둔다. 표정 구분은 아래 검증법을 통과해야 확정한다.
**B UI 아이콘 Gemini 미사용: 찬성.** 근거: 아이콘은 currentColor로 상태 색(주황·초록·비활성)을 바꾸고, 24 격자에서 선 두께가 일정해야 한다. 래스터로는 대비 3:1 보장과 상태별 색 회귀를 자동 검사할 수 없다. 예외 없음.
**C 일러스트 적극 사용: 조건부.** 근거: 스토어 그래픽·스플래시처럼 앱 밖에 쓰는 것은 위험이 낮다. 앱 안 빈 상태·완료 그림은 토스 2초 반응 규칙과 대비 검수에 걸린다. 조건 4개:
1. 앱 안 래스터는 WebP(또는 AVIF, 토스 WebView 지원 여부 미확인), 장당 80KB 이하(가정). 첫 화면 경로(코드 입력·코스 홈)에는 래스터를 두지 않는다. 로딩 실패나 지연 시 단색 자리를 먼저 보여 줘 2초 안에 화면이 반응하게 한다.
2. 밀도: 표시 크기 × 2배와 × 3배 두 벌을 만들고(@1x는 생략 가능, 가정) `srcset`으로 내보낸다. 150% 글자 확대는 이미지 크기를 바꾸지 않는다. 다만 자체 "글씨 크게" 설정이 이미지 영역을 키운다면 @3x가 필요하다.
3. 그림 위에 글자를 올리지 않는다. 글자는 그림 밖 단색 바탕에 둬서 대비 4.5:1을 계산할 수 있게 한다. 그림 안의 정보(예: 완료 체크)는 반드시 글자로도 표시한다.
4. 대체 텍스트: 장식은 `alt=""`(TalkBack이 건너뜀), 의미가 있는 그림은 짧은 한국어 alt를 둔다. alt 누락 0건을 자동으로 검사한다.
**D 법·표시: 조건부(QA 영역 밖).** 표기 범위는 정책이 판단한다. QA는 실제로 표시되는 문구가 정해진 범위와 맞는지만 회귀 항목으로 검증한다(예: 사진에만 "AI가 만든 그림"이 붙는지).
**E 해님 성격 재점검: 찬성.** "아이 취급" 여부는 grep으로 잡을 수 없다. 어르신 3가구 관찰 질문에 "이 그림을 보면 어떤 느낌이 드세요? 누구를 위한 앱 같아요?" 1문항을 넣는다. 화면 하나에 시안 두 개(현재 해님 / 성숙한 비율)를 보여 주고 고르게 한다. 성공 기준(가정): 3가구 중 2가구 이상이 "아이용 같다"고 말하지 않으면 통과.
**F 빌드 1 범위 자르기 제안.** 빌드 1 앱 안: 해님 SVG 표정 3종(기본·활짝·걱정, designer.md §3), 도장 1종, 빈 상태 1장(SVG 또는 단색), UI 아이콘 SVG. 빼는 것: 표정 5종 중 2종, 자세 변형, 온보딩 일러스트, 완료 축하 래스터(모션 없이 SVG 해님으로 대체). 스토어 그래픽·앱 아이콘 후보는 Gemini로 만들어도 앱 회귀와 무관하므로 허용한다.

## 표정 구분 검증 방법
- 사람: 44px(도장)·56px·92px로 출력해 팔 길이(약 40cm)에서 3명이 각각 "웃음/활짝/걱정"을 맞힌다. 기준(가정): 56px 이상에서는 정답률 90% 이상, 44px에서는 50% 미만이면 도장에서 표정을 쓰지 않는다. 어르신 1명 이상을 포함하고, 돋보기 없이 본다.
- 자동(보조): 표정별 SVG를 해당 크기로 렌더한 뒤 표정 쌍마다 픽셀 차이 비율을 낸다(pixelmatch 류 도구, 저장소 설치 여부 미확인). 차이가 일정 값 미만이면 "구분 어려움" 경고를 띄운다. 임계값은 사람 결과로 한 번 보정한다.
- 색에 의존하지 않는다: 회색조 변환 후에도 구분되는지 확인한다(색각 이상 대비).

## 앱 용량·로딩 (토스 2초 규칙)
- 측정: 느린 망(개발자 도구 Slow 4G 또는 실기기 LTE 약세)에서 첫 화면이 반응하기까지의 시간과 이미지 전체 로드 시간을 따로 잰다. 게이트: 반응 2.0초 이내. 이미지는 늦게 떠도 되지만 레이아웃이 밀리면 안 된다(width·height를 지정해 자리 고정).
- 예산(가정): 웹 번들 안의 이미지 합계 1MB 이하, 화면당 래스터 1장 이하. 사진 콘텐츠(14~30장)는 번들에 넣지 않고 서버에서 그날 1장만 받는다.
- SVG도 비용이 있다: 필터·그림자가 많은 SVG는 저가 기기에서 렌더가 느릴 수 있다(미확인). 92px 해님을 저가 Android 실기기에서 1회 확인한다.

## 회귀 비용과 자동화 가능성
| 검수 기준 | 자동화 | 방법 |
|---|---|---|
| 파일 형식·크기·용량 예산, @2x/@3x 쌍 존재 | 가능 | 빌드 전 스크립트로 폴더를 스캔해 규격 위반 시 실패(스크립트는 개발 몫) |
| alt 누락, 그림 위 글자 금지 | 부분 | 마크업 정적 검사 + 시각 확인 |
| 대비(글자·아이콘) | 가능 | 토큰 조합 계산. 그림 위 글자를 금지하면 래스터 대비 계산이 필요 없어진다 |
| 에셋 교체 시 화면 변화 | 가능 | 주요 화면 스크린샷 비교(Playwright 등, 토스 WebView가 아닌 브라우저 기준). 의도한 변경만 승인 |
| 표정 구분·아이 취급 느낌·앨범 톤 | 불가 | 사람 검수(위 방법) |
- 회귀 비용 줄이기: 에셋은 이름 규칙을 지키는 레지스트리 하나로만 참조한다(`assets-manifest` 기준). 시안·앱·테스트가 같은 ID를 쓰면 에셋이 바뀌어도 코드 변경은 0이고 스크린샷 승인만 남는다. Gemini로 다시 생성할 때마다 크기·여백이 달라지는 것이 가장 큰 회귀 원인(가정)이라, 캔버스 크기와 여백을 고정한 후처리 단계를 둔다.

## 내가 틀릴 수 있는 이유
1. 토스 WebView가 이미지 캐시를 잘 해서 용량 걱정이 과할 수 있다.
2. 고해상도 WebP 한 장이면 밀도별 두 벌이 필요 없을 수 있다(용량 대비 효과는 실측 필요).
3. 어르신은 그림의 세부보다 글자와 버튼만 볼 수 있어서, 표정 구분 검증의 가치가 낮을 수 있다.
4. 3가구로 "아이 취급" 여부를 판단하는 것은 일화 수준이다.

## 빠진 질문
- Gemini 결과물을 SVG로 옮기는 사람과 시간은 누구 몫이고 얼마인가? 이게 없으면 하이브리드는 "래스터 교체"로 흘러간다.
- 다크 모드는 토스에서 쓰지 않지만 Play 앱에서 다크 모드를 지원할 것인가? 지원하면 래스터 배경 처리(투명 PNG의 테두리 번짐)가 새 회귀 항목이 된다.
