# 컴포넌트·아이콘 디자이너 의견 (R2, 2026-11-17)
r1 6개(biz·brand·icons·policy·qa·ux)를 모두 읽고 썼다. 수치는 가정이고 실측하지 않았다.

## 동의하지 않는 의견 2개와 반박
1. **사업 r1의 "앱 아이콘은 해님 단독보다 앨범·집 상징이 앞"**: 방향은 동의하지만 근거가 반만 맞다.
   - 반박: 앱 아이콘은 1024에서 알림 24px까지 같은 원본을 쓴다.
   - 앨범·집 상징은 선이 많아 48px 이하에서 뭉개질 위험이 크다(집 + 사진틀 + 해 = 요소 3개).
   - 브랜드 r1의 "작은 크기는 얼굴 없이 해 실루엣"이 기술적으로 가장 안전하다.
   - 수정안: 아이콘은 **해 실루엣(얼굴 없음) + 폴라로이드 틀 1개**, 요소 2개 이하.
   - 어린이 느낌은 얼굴을 빼면 줄고 앨범 결도 남는다. 자녀 5~10명 1문항 테스트(사업 제안)에는 동의한다.
2. **QA r1의 "WebP 장당 80KB 이하"만으로 기준을 삼는 것**: 용량 상한만으로는 부족하다.
   - 80KB 안에서도 120px짜리 작은 그림을 래스터로 넣을 수 있고, 그러면 150%·다크·대비 문제가 그대로 남는다.
   - 반박: 기준은 **두 조건을 모두** 충족해야 한다.
     - ① 표시 크기 160px 이상(그 미만은 SVG, 브랜드 r1의 "160x120 소품은 래스터 이점 없음"과 같은 결론)
     - ② WebP 80KB 이하. 제가 r1에 쓴 60KB는 근거가 약해 QA의 80KB로 맞춘다.
   - 추가 조건: 그림 안에 글자 금지, 첫 화면 경로(코드 입력·코스 홈) 금지(QA 의견 수용).

## 바뀐 입장
- **C 일러스트**: 앱 안 래스터는 **빌드 1에서 0장**으로 바꾼다. QA·브랜드·사업 모두 기존 SVG 유지를 제안했고, 빈 상태 컴포넌트가 이미 해님 88 + 글자 구조라 큰 그림이 필요 없다. 위 기준(160px·80KB)은 빌드 2부터 적용한다.
- **용량 상한**: 60KB → 80KB(QA 값 수용, 실측 전 가정).
- **F 범위**: 내 r1의 "빈 상태 일러스트 4종 빼기"는 SVG 4종이 이미 있다는 사실을 놓쳤다. 정정하면 "새로 그리지 않는다"이고, 기존 SVG 중 offline·no-content만 남기고 나머지는 빌드 1 화면에서 쓰지 않는다(UX r1 수용).
