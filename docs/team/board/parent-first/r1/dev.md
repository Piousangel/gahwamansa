# 앱 개발 의견 (R1) · 부모님 먼저 시작하는 흐름
근거: supabase/migrations 0001~0015, app/src를 읽었다. 시간은 1인 기준 **가정**이고 실측이 아니다.

## 지금 구조에서 막히는 곳 (사실, 코드 기준)
- `create_family`(0003:13)는 익명 사용자를 `child_required`로 거부한다. 익명인 어르신은 가족을 만들 수 없다. `families.created_by`는 auth.users를 가리켜 누가 만들었는지는 중립이다.
- `issue_invite_code`는 `my_role()='child'`만 허용한다(0009:67). `invite_codes.created_by`는 profiles를 참조하므로 어르신이 발급해도 스키마는 맞는다.
- `redeem_invite_code`는 **익명만** 허용하고(0009:109) 무조건 `role='parent'`로 넣는다(0009:173). 역방향(자녀가 입력)은 새 RPC가 필요하다. `create_family`는 `already_has_profile` 검사가 있어 자녀가 기존 가족에 합류할 경로가 아예 없다(형제 초대와 같은 결손).
- RLS의 역할 가정: `codes_read`는 자녀만(0002:34) 읽는다. 어르신이 발급하면 화면은 RPC 반환값으로만 보여 줘야 한다. `answers`·`sessions`·`cheers`는 역할과 무관하게 맞는다.
- 지우기 규칙(0008:35): "마지막 자녀면 가족 전체"다. 자녀가 없는 어르신 단독 가족에서 어르신이 지우면 `families`·entitlements 행이 남는다(빈 가족). 어르신 먼저 흐름에서는 "가족에 남은 사람이 없으면 가족 삭제"로 바꿔야 한다.
- `child_summary`는 자녀가 합류한 뒤에는 그대로 동작한다. 단, 자녀가 확인되기 전(대기 상태)에는 요약을 막는 조건이 필요하다(B).

## 안건별 입장
- **A 빌드 1 포함: 조건부 찬성.** C단계(C0 역할 선택, C2 번호 화면)와 **합칠 때만** 찬성한다. 따로 하면 빌드 1이 1주 가까이 밀린다. 가벼운 판이란 "어르신이 '가족 만들기'를 누르는 순간 가족과 어르신 프로필을 만들고(익명 유지), 그 뒤로는 연결된 상태"를 뜻한다. 그러면 미연결 열람과 같은 코드 경로(`linked=true`)를 그대로 쓴다.
- **B 역방향 번호: 조건부 찬성.** 서버에 세 가지가 필요하다. ① `create_family_as_parent()`(익명 허용, 어르신 프로필과 entitlements 생성) ② `issue_invite_code`를 역할 분기로 고치고, 어르신 발급은 `kind='child_join'`과 24시간 만료 ③ `join_family_as_child(code)`(비익명만, 시도 제한·advisory lock은 redeem과 공유). 사칭 대책은 "확인 한 번" 문구만으로는 부족하다. 서버가 막아야 한다. 합류한 자녀 프로필에 `approved_at`을 두고, 어르신이 `approve_child`로 승인하기 전에는 `child_summary`·cheers를 막는다. 어르신 화면에 보여 줄 "누가"는 지금 DB에 없다. 자녀 이름(입력 1칸)이나 카카오 닉네임 저장이 필요하고, 이건 정책 확인이 필요하다.
- **C 먼저 쓴 기록: 찬성(초안대로).** 가족을 처음 만들 때부터 연결된 상태라 지금 저장 로직이 그대로 돈다. 동의는 "가족이 생기는 시점"이 아니라 **자녀 승인 시점**에 받아야 실제로 보는 사람이 생긴다. 서버 변경은 없고, 앱에서 동의 화면 진입 위치만 바뀐다.
- **D 전달 방법: 찬성.** 번호 표시와 공유는 C2(자녀 번호 화면) 컴포넌트를 그대로 쓴다. 토스에서는 공유 문구에 설치 유도가 들어가면 안 된다.
- **F 동의: 조건부.** 자녀가 여럿이면 승인도 여러 번 받는다. 동의는 가족 단위 한 번(현행 `consented_at`)으로 유지하자. 대신 "새 가족이 연결되면 다시 알림"을 둘지 정책 결정이 필요하다.
- **G 하나로 합치기: 찬성.** 역할을 고른 뒤 같은 두 화면을 쓴다. "번호 만들기(CodeShow)"와 "번호 쓰기(CodeInput+ConnectScreen)"가 역할에 따라 부르는 RPC만 바꾼다. 문구는 역할별 키 2벌이 필요하다.
- E: 공수 관점 의견은 없다(사업 위원에게 맡긴다).

## 공수 (가정)
| 덩어리 | 단독 | C단계와 합칠 때 |
|---|---|---|
| 서버: 위 RPC 3개 + 승인 + 빈 가족 삭제 + codes kind/만료 + pgTAP | 16~20h | 16~20h(겹침 없음) |
| 앱: 역할 선택, 번호 화면 2개, 승인 화면, 문구 | 14~18h | 6~8h 추가(C0·C2 재사용) |
| 통합·단위 테스트 | 6~8h | 4~5h |
| 합계 | 36~46h | **26~33h**(약 10~13h 절감) |

## 토스 anonKey 트랙과의 관계
- 토스에서는 어르신·자녀 모두 익명이 아닌 사용자(anonKey 매핑)라 `is_anonymous` 가드가 원래 맞지 않는다. 부모님 먼저 흐름은 가드를 "역할 선택" 기반으로 바꾸게 만든다. 토스 개편 비용(r1에서 5~7h로 잡은 것)을 앞당겨 함께 치르는 셈이라, 토스까지 보면 중복 작업이 줄어든다.
- 토스 안에서는 "어르신이 먼저 찾아서 시작"하는 획득 경로가 자연스럽다(가정). 반대로 Play 트랙은 자녀 카카오 로그인이 아직 없다.

## 내가 틀릴 수 있는 이유
1. 승인 단계를 넣으면 자녀의 첫 경험이 "기다림"이 되어 전환을 해칠 수 있다. 보안 요구를 내가 과하게 잡았을 수 있다.
2. 역할 분기로 가드를 바꾸면 RLS·RPC 전체 회귀 범위가 넓다. pgTAP 157개 중 몇 개가 바뀔지는 세어 보지 않았다.
3. 공수는 C단계 화면 설계가 v3 시안대로 확정됐다는 가정 위에 있다.

## 빠진 질문
- 자녀가 끝내 들어오지 않는 단독 가족을 얼마나 유지하고, 언제 정리하는가(데이터 보관 정책).
- 어르신이 가족을 만든 뒤 폰을 바꾸면 재연결 번호는 누가 만드는가. 지금은 자녀만 만든다.

## 사용자에게 묻고 싶은 것
- 자녀 합류에 어르신 승인 단계를 넣어도 되는가(보안 대 마찰).
- 부모님 먼저 흐름을 토스 트랙 전용으로 시작해도 되는가(Play는 기존 자녀 먼저 흐름 유지).
