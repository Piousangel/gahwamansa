# 정책 의견 (부모님 먼저 R1) · 2026-11-17
법률 자문 아님. 법적 판단은 모두 **전문가 확인 필요**. 다른 위원 파일 읽지 않음. 근거는 안건 문서와 기존 policy.md·board r2.

## 핵심 위험 (사용자 관점)
자녀 먼저 흐름에서는 **번호를 받는 쪽이 어르신**이라, 최악의 경우 어르신 기록이 그 가족에게 들어가지 않는다. 부모님 먼저에서는 방향이 뒤집혀 **번호를 받는 쪽이 "자녀"라고 주장하는 사람**이다. 번호가 새면 모르는 사람이 어르신의 답·참여를 계속 본다. 고령자 대상 메신저 피싱("엄마 나 폰 고장났어, 번호 알려줘")의 대본에 그대로 들어맞는다(가정: 일반적 수법 기준). 자녀 먼저보다 위험이 한 단계 크다.

## 안건별 입장
**A 빌드 1 포함: 조건부.** B의 확인 장치와 F의 동의 게이트가 함께 들어갈 때만. 둘 중 하나라도 빠지면 빌드 2. "가벼운 판"이 확인 장치를 빼는 판이면 반대.
**B 역방향 번호 보안: 조건부(초안 보강).**
1. **어르신 승인 전에는 아무것도 공개하지 않음.** 자녀가 번호를 입력하면 "대기" 상태. 어르신 화면에 "OOO(자녀가 입력한 호칭·카카오/토스 닉네임)님이 연결하려 해요. 아는 분이에요?" [네, 내 자녀예요]/[아니에요]. 승인 전 자녀 화면은 빈 상태. 초안의 "연결 후 확인 한 번"은 순서가 틀림(이미 연결된 뒤 확인하면 그 사이 노출).
2. "아니에요"는 즉시 거절·번호 폐기·새 번호 안내, 그리고 "모르는 사람에게 번호를 알려 주지 마세요" 한 줄.
3. 번호: 1회용, 24시간(초안 지지), 어르신 쪽 미사용 번호는 1개만 유효. 자녀 쪽 입력에도 시도 제한(기존 5회 잠금 재사용). 6자리는 무차별 대입에 약하므로 제한은 필수.
4. 번호 화면·공유 문구에 "가족에게만 보내세요" 경고. 카톡 공유 미리보기에 번호를 크게 노출하지 않는 방안은 라이터와 협의.
5. 연결된 사람 목록을 어르신 설정에서 항상 볼 수 있고 **어르신이 개별 연결을 끊을 수 있어야** 함(지금 설계는 끊는 권한이 자녀 쪽 중심).
6. 승인 시 자녀에게도 "어르신이 연결을 확인했어요" 알림. 거절 반복 계정은 서버 로그로 표시.
**C 처음부터 가족 생성 후 답 저장: 조건부.** 저장 자체는 어르신 본인의 기록이라 가능하나, **동의를 두 단계로 나눈다**: (1) 첫 코스 전 "내 답을 이 폰 기록으로 저장해요"(저장 동의, 방침상 수집 고지), (2) 자녀 승인 시점(B-1)에 "이 사람에게 내 고른 답과 날짜가 보여요"(공개 동의). 공개 동의 전 저장분을 소급 공개할지는 공개 동의 화면에 **명시적으로 묻는다**("지금까지 고른 답도 보여 줄까요?" 기본값=예/아니오는 사용자 결정). 동의 기록은 board r2대로 서버 게이트로 강제.
**D 전달 방법: 조건부.** 말로 불러 주기·화면 보여 주기는 피싱 대본(전화로 번호 요구)과 겹친다. 공유 버튼 기본, 말로 전달은 막을 수 없으므로 B-1 승인이 최종 방어선.
**E 사업: 의견 없음(정책 영향만).** 자녀가 끝내 안 들어오는 가족은 "자녀 없는 가족"으로 남는다. 보관 기간 상한(예: 미연결·미사용 N개월 후 삭제 안내, N은 사용자 결정)을 방침에 둔다.
**F 동의·개인정보: 조건부.**
- 자녀가 여럿: **공개 동의는 사람 단위**. 새 자녀가 연결될 때마다 B-1 승인과 공개 동의를 다시 받는다(한 번 동의로 이후 자녀 모두에게 공개되면 범위가 어르신 모르게 넓어짐). 화면에 "지금 보는 사람: 2명" 표시.
- 삭제 권한 변화: 지금 "마지막 자녀가 지우면 가족 전체 삭제"는 **어르신이 만든 가족에는 맞지 않는다**. 어르신이 가족의 주인이므로 자녀 탈퇴는 그 자녀 연결·자녀 데이터만 삭제, 어르신 기록은 유지. 가족 전체 삭제는 어르신(또는 어르신이 앱을 못 쓰는 경우 이메일 요청+본인 확인)만. 자녀 먼저 가족과 규칙이 달라지면 혼란이므로 **두 흐름 모두 "어르신 기록은 어르신이 지운다"로 통일**을 제안(현 규칙 변경, 사용자 결정). 서버 RPC·pgTAP 변경 범위는 개발 확인.
- 방침 갱신: 수집 경로(어르신이 먼저 만든 가족), 공개 대상 승인 절차, 삭제 권한을 `site/index.html`·`delete-account.html`에 반영 필요(현재 미반영).
- 토스: anonKey로 어르신이 가족을 만들면 연결 해제 시 삭제 의무의 대상이 어르신 가족 전체가 됨(가정, 트리거 방식 미확인).
**G 하나로 합치기: 찬성.** 같은 "번호 만들기/번호 쓰기" 화면을 쓰되, **번호를 쓴 쪽이 자녀일 때만** 어르신 승인 단계를 추가. 보안 단계를 공유 화면이 생략하지 않도록 서버에서 강제(역할별 RPC 분기).

## 틀릴 수 있는 이유
1. 승인 단계가 어르신에게 한 번 더 판단을 요구해 오히려 "네"를 습관적으로 누를 수 있다(피싱 방어 효과 과대평가).
2. 사람 단위 공개 동의는 형제 많은 가족에서 번거로워 이탈을 키울 수 있다.
3. 어르신이 가족 주인이 되는 삭제 규칙은 어르신이 앱을 못 쓰게 된 경우(건강 악화) 자녀가 지울 수단을 줄인다.

## 빠진 질문
- 어르신 승인 화면에 보여 줄 "누구인지" 정보가 충분한가(닉네임은 위조 쉬움). 자녀가 직접 쓰는 호칭만으로는 확인이 안 된다.
- 자녀가 어르신 폰에서 대신 승인하는 경우는 어떻게 막나(막을 수 없다면 고지로만).

## 사용자에게 묻고 싶은 것
1. 공개 동의 전 쌓인 답을 소급 공개할지 기본값을 무엇으로 할지.
2. 삭제 규칙을 "어르신 기록은 어르신이 지운다"로 두 흐름 모두 바꿀지.
3. 자녀가 안 들어온 가족의 보관 기간 상한.
