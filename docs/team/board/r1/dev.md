# 앱 개발 의견 (R1)
관점: 구현 실현성·공수. 시간은 전부 **추정**(1인, 하루 순작업 6h 가정, 실측 아님). 근거: app/ 코드(테스트 50+13), supabase/migrations 0001~0011, toss/ 스캐폴드, plans/03·04.

## 안건별 입장
**A 자녀 범위 축소: 찬성(조건부).** 지금은 UI만 숨기면 안 된다. 자녀 계정이 `daily_sessions`를 RLS(sessions_read)로 직접 읽어 단계·연속일이 DB 수준에서 열려 있다. 동의 문구와 실제 노출이 어긋나는 걸 막으려면 서버에서 닫아야 한다.
- 서버: `child_today_summary()` RPC(오늘 했는지 bool + 오늘 고른 답) 신설, 자녀의 `daily_sessions` select 정책 제거, 마이그레이션+down+pgTAP(자녀가 세션 행을 못 읽음) 약 4~5h.
- 앱: `fetchChildHome`이 RPC 1회로 단순화(왕복 감소), ChildHome에서 연속일·"아직이에요" 제거, 단위·통합 테스트 수정 약 2~3h. 동의 문구는 라이터 확정 후 copy.ko.json 교체 0.5h.
- 합계 약 7~9h. 수정 제안: "못 한 날"은 서버가 아예 구분해 주지 않는다(미참여를 표시할 데이터 자체를 안 줌). 독촉 원천 차단이 UI 규칙보다 안전하다.

**B 토스 트랙 재연결·폰 교체·끊김 화면 보류: 조건부 찬성.** 공수 0h(만들지 않음). 단 anonKey는 토스 탈퇴·재가입 시 바뀐다(plans/04 확인). 그때 어르신은 "처음부터 다시"가 되므로 **Connect 화면에서 같은 6자리 흐름으로 재연결 코드를 받는 경로(서버 `issue_invite_code(p_target)`는 이미 있음)** 는 남겨야 한다. 새 화면은 아니고 문구만 추가. Play 트랙의 P11/P14는 별도 약 8~10h(미착수).

**C 응원 수신(P8) + 설정(C7) 빌드 1 포함: 조건부.** 포함하면 11월 제출이 더 어려워진다.
- P8: `cheers` 테이블·RLS(읽기·보내기·읽음 표시)는 있으나 **RPC·앱 코드 없음**. 자녀 보내기(정해진 문구 8개) + 어르신 수신 표시 + 읽음 처리: 서버 pgTAP 포함 3h, 클라이언트(웹 기준) 8~10h.
- C7 설정: 호칭 저장 RPC 없음(profiles에 update 경로 없음, display_name 컬럼만 존재) → `set_display_name` RPC 2h, 화면(호칭·삭제 이동·알림은 제외) 6h. 알림 설정은 푸시 자체가 빌드 2라 제외.
- 제안: 응원 수신은 포함(약속을 이미 자녀 화면이 하고 있어 UX 차단 2번), 설정은 "호칭+삭제"만.

**D 삭제 버튼 위계 반전: 찬성.** 현재 코드는 "삭제하기"가 주 버튼. 문구·순서 변경이라 앱 1~2h(테스트 문구 포함), 코스 홈 링크를 설정으로 옮기면 C7 의존. 서버 변경 없음.

**E 호칭 변수화: 찬성.** 서버 `set_display_name`(C와 공용) + 자녀 화면 문구 템플릿화(`{호칭}`)와 "어르신" 제거: 앱 3~4h, copy.ts에 치환 함수와 테스트 1h. 호칭 미설정일 때 폴백 문구가 필요(라이터).

**F(참고): 대안은 Play 우선 복귀**가 공수상 가장 싸다. 앱·서버가 이미 완성도가 높고 남은 건 UX 차단 수정뿐.

**G MVP 컷 제안(빌드 1 필수):** 어르신 Connect·동의·코스 3단계·완료·응원 수신·삭제, 자녀 가입(토스 식별)·코드 발급·홈(오늘 했는지+고른 답)·응원 보내기·삭제. **후순위:** 리포트, 푸시, 설정 알림, 재연결/폰 교체 화면, 도장 모션, 구독·결제, 형제 초대.

## 토스 클라이언트: 재사용 가능/불가
- **가능(순수 TS, 약 40%)**: `features/types.ts`(Api·TodayContent·reason), `fakeApi.ts`(테스트·devtools 데모에 유용), `realApi.ts`(supabase-js는 웹에서 동작, 세션 저장소만 교체), `copy.ts+copy.ko.json`, `codeInputLogic.ts`, `tokens.ts`, 콘텐츠 규칙. 추출은 복사로 시작하면 1~2h, `packages/core` 분리는 Metro watchFolders 설정 때문에 4~6h 추정(미확인 변수).
- **불가**: 모든 화면(RN `View/Pressable/StyleSheet`), react-navigation, safe-area, AsyncStorage, AppState(→ visibilitychange), RNTL 테스트(→ vitest+React Testing Library). React 18(토스) vs 19(앱) 차이도 있다. 화면은 사실상 재작성이며 v2 시안·UX 감사 반영 때문에 어차피 새로 짠다.
- 미확인: WebView에서 음성 읽기(Web Speech) 동작, 큰 글씨(OS 확대) 반영, 토스 내비 바와 뒤로가기 규칙.

## 토스 인증(anonKey → Supabase 세션)
- 흐름: 미니앱 `createAnonymousKeyAuthCode()`(300초·1회) → Edge Function → 앱인토스 mTLS 교환 → anonKey → 매핑 테이블 `identities(anon_key→user_id)` → 세션.
- **난이도: 중상.** 위험 3개. (1) mTLS: 로컬 Edge 런타임에 `Deno.createHttpClient`는 있으나 실제 인증서 호출은 **미확인**(T3, 사용자 인증서 필요). 안 되면 소형 별도 서버 +1~2일. (2) 세션 발급: 문서에 권장 흐름 없음. 서버가 JWT를 직접 서명하려면 호스팅 프로젝트의 서명 키 방식이 **미확인**, 대안은 admin 생성 사용자+`generateLink`/OTP 검증. (3) **우리 RPC가 `is_anonymous` 클레임으로 역할을 가른다**(create_family는 비익명, redeem은 익명 요구). 토스에서는 모두 같은 종류의 사용자이므로 가드를 "역할 선택" 기반으로 바꿔야 한다. 마이그레이션 0012+pgTAP 수정 약 5~7h.
- 인증 함수+매핑+통합 테스트 약 14~20h(mTLS가 한 번에 되는 경우). 토큰은 쿠키 불가(iOS 서드파티 쿠키 차단)라 메모리/Storage 보관 필요, 1시간 만료 시 코드 재발급.

## 11월 안 토스 검수 제출은 현실적인가
**전체 범위로는 아니오. 최소 슬라이스의 "제출"만 빠듯하게 가능, "출시"는 11월 불가.** 오늘이 11/17이라 근무일 약 10일(60h) 남음.
| 덩어리 | 추정 |
|---|---|
| 서버: 인증 함수·매핑·역할 가드·A·호칭 RPC | 28~38h |
| 클라이언트 셸(Vite 구조·인증 부트스트랩·내비 바·라이트 모드·core 추출) | 14~18h |
| 어르신 화면(Connect·동의·코스 3·완료·응원·삭제) | 18~24h |
| 자녀 화면(식별·코드 발급·홈·응원 보내기·삭제) | 12~16h |
| 테스트·QA 수정·검수 체크리스트 | 10~14h |
| **합계** | **약 82~110h = 14~18일** |
- 최소 슬라이스(응원·설정·리포트 제외, 삭제 유지)는 약 55~65h(9~11일). 11/30 제출은 **T2·T3(콘솔 계정, mTLS 인증서)가 11/19까지 풀리고 디자인 재작업이 없을 때만** 가능, 내 가정 확률은 약 30~40%. 검수 소요 일수·사업자 등록 필요 여부는 **미확인**이라 출시 날짜는 말할 수 없다.
- 첫 토스 출시 최소 경로(스파이크 외): 콘솔 워크스페이스·`appName` 확정 → mTLS 인증서 → 인증 함수 → 역할 가드 개편 → 어르신 6화면+자녀 4화면 → 개인정보·연결 해제 정책 → 비게임 체크리스트 → 업로드·토스앱 실기 테스트.

## 내가 틀릴 수 있는 이유
1. 추정은 실측이 아니다. mTLS가 하루 만에 풀리면 서버 시간이 10h 줄고, 반대로 서명 키 방식이 막히면 2~3일 늘 수 있다.
2. 화면 재작성 시간을 로직 재사용으로 낙관했을 수 있다. WebView 접근성(큰 글씨·음성)에서 예상 못 한 문제가 나올 수 있다.
3. 어르신이 토스 사용자가 아니면 모든 토스 공수가 어르신 쪽에서 무의미해지는데, 이 점은 내 공수 논리 밖이다.

## 안건에 없지만 가장 중요한 질문
1. 토스 트랙의 어르신 입구를 정할 것인가: 어르신이 토스 사용자가 아니면 "자녀 전용 미니앱 + 어르신은 Android 앱" 구조가 되는데, 6자리 번호 전달 외에 설치 유도 금지를 어떻게 지키는가(03·04의 미해결).
2. 두 채널(토스 anonKey / Play 익명·카카오)에서 한 가족이 섞일 때 서버의 `is_anonymous` 기반 역할 모델을 무엇으로 바꾸는가(마이그레이션이 두 클라이언트에 모두 영향).

## 사용자에게 묻고 싶은 것
- 콘솔 워크스페이스와 mTLS 인증서를 11/19까지 준비해 줄 수 있는가(안 되면 11월 제출은 포기가 맞다).
- 11월 목표가 "제출"인지 "승인·출시"인지, 그리고 Play 테스트 트랙 업로드는 12월로 미뤄도 되는가.
