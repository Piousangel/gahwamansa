# QA·접근성 의견 (R1)
근거 범위: 04 plan, 03 analysis(비게임 출시 가이드 요약), qa.md, BOARD 안건. SCREENS.md·UX-AUDIT는 전문을 읽지 않았다(미확인 부분은 표기). 토스 WebView 동작은 모두 **미확인**이며 실기기 스파이크 전엔 판정 불가.

## 안건별 입장
A(범위 축소): 조건부 찬성 — 어르신에게 "자녀가 뭘 보는지"가 단순할수록 동의 이해도 검증이 쉽다(관찰 질문 3번이 한 문장으로 끝남). 회귀 위험: 자녀 홈의 칩·연속일·"아직이에요" 제거 시 qa.md §2 조건 4·5(1분 반영, 연속일 불변)의 검증 대상이 바뀐다. 제안: 연속일은 어르신 도장용으로 남기고 자녀 화면에서만 숨기면 서버 테스트는 불변. "오늘 했는지" 하나만 남기면 1분 게이트가 단일 신호로 단순해진다. 동의 문구는 화면에 실제 보이는 항목과 1:1 대조 체크표를 게이트에 추가(문구-화면 불일치 = 출시 차단).
B(토스 재연결 보류): 조건부 찬성 — anonKey가 기기 교체에도 유지된다는 건 문서 사실이나 **실기기 검증 전엔 가정**. 새 폰 로그인·토스 재설치·탈퇴 후 재가입(키 변경)을 토스 QR로 1회씩 확인하기 전까지 "불필요"로 확정하지 않는다. 탈퇴 후 재가입은 어르신 기록 단절이라 안내 문장이 필요(보류 화면 0개여도 문장 1개는 요구).
C(P8 응원 + C7 설정): 조건부 — 검증 부담이 큼. 설정(호칭·삭제·알림)은 삭제·동의 철회가 있어 게이트 필수. 응원 수신은 정해진 문구 8개 표시뿐이라 부담이 작지만 푸시 의존이면 토스 푸시 명세 미확인이라 **빌드 1은 앱 열었을 때 표시만** 포함. 설정은 호칭+삭제+동의 철회 3개만, 알림 토글은 푸시와 함께 빌드 2.
D(삭제 위계): 찬성 — "그만둘래요"가 주 버튼이면 오조작 삭제 위험이 커진다. 반드시 2단계 확인과 되돌릴 수 없음 안내, 큰 글씨에서 버튼 위치 이동 없음 검증. 회귀: 삭제 후 상대 기기 화면 문장(S13)을 어르신·자녀 양방향으로 확인.
E(호칭 변수): 찬성 — 단 호칭 변수는 TTS와 글자 확대에서 깨지기 쉽다. 받침 유무에 따른 조사(엄마가/아빠가, 이/가·은/는) 오류와 긴 호칭(8자) 줄바꿈 회귀 테스트가 필요. 호칭 미설정 기본값 문장도 검증.
F(토스 전제): 조건부 — 3가구 확인은 QA 관찰과 병합 가능하나 순서를 지킨다: T0 질문을 관찰 전에 전화 한 통으로 끝내 헛걸음을 막는다. 토스 미사용 가구는 샌드박스 대신 자녀 폰에서 토스 QR 대리 시연 불가(어르신 단독 사용 검증 안 됨)이므로 판정에서 분리 집계.
G(화면 컷): 안건 외 제안 — 116개 전부를 실기기로 확인하는 것은 불가능. 화면을 **"출시 게이트 대상 15~20개"(연결·동의·코스 3단계·완료·오류 7종·설정·자녀 홈)** 와 "나머지(스크린샷 눈 확인만)"로 분리한다. 숫자 15~20은 가정.
H(좋은 소식만): 조건부 — 검증 가능한 규칙으로 바꾸면 찬성: "화면·푸시·TTS 문구에 미완료·끊김·아직 단어 0건" grep 게이트. 단 못 한 날 아예 무신호면 자녀가 "앱 고장인가?" 오해 가능 → 중립 상태("오늘은 쉬셨어요")가 감시인지 위로인지는 관찰로만 판단 가능(미확인).

## 토스 WebView 접근성 검증 (핵심)
| 항목 | 방법 | 한계 |
|---|---|---|
| 글자 150% | 토스 앱은 OS 글자 크기를 WebView에 반영하는지 **미확인**. 반영 안 되면 시스템 설정을 올려도 변화 없음. 따라서 자체 "글씨 크게" 설정(CSS 변수 rem)을 앱이 제공하는 설계를 권고 | 토스 앱 안에서만 확인 가능(QR+실기기). 브라우저 devtools는 OS 글자 설정 재현 불가, 브라우저 글꼴 확대만 근사 |
| 핀치 줌 비활성 vs 확대 접근성 | 가이드가 핀치 줌 비활성을 요구(03). 저시력 어르신의 유일한 확대 수단 상실 → 20sp 이상·자체 글씨 크기 옵션으로 보상해야 함. Android 확대(삼중탭)·iOS 확대/디스플레이 확대가 WebView에서 살아 있는지 실기기 확인 | 충돌 여부 미확인. viewport `user-scalable=no`와 OS 확대는 별개이나 토스 구현은 불명 |
| TalkBack/VoiceOver | 의미 요소(button, h1, aria-label)로 작성, 6칸 코드 입력은 단일 input+inputmode=numeric 권고(6개 칸은 낭독 혼란). 토스 내비게이션 바(네이티브)가 포커스 순서에 끼는 것 확인 | 토스 앱 안 WebView 동작은 QR 기기에서만. iOS 기기 확보 여부 미확인 |
| 음성 읽기(TTS) | Web Speech API `speechSynthesis` 가 토스 WebView에서 동작하는지 **미확인**(RN 앱의 TTS와 별개 구현). 한국어 음성 부재·iOS 자동재생 제한(사용자 탭 필요)을 가정. 안 되면 대안: 사전 녹음 mp3(콘텐츠 14~30일치 문장 수에 비례해 비용) | 브릿지에 TTS가 있는지 SDK 확인 필요(미확인) |
| 색 대비·터치 | 웹 devtools에서 계산 가능(자동화 쉬움). 토스 안에서는 안전 영역·네비바 때문에 하단 버튼이 가려지는지 실기기 확인 | — |
토스 샌드박스·QR 한계: SDK 3.x는 샌드박스 앱 없이 브라우저 devtools, 실제 토스 앱 테스트는 콘솔 QR(사용자 계정 필요). 따라서 브라우저 통과 ≠ 토스 앱 통과. 토스 앱 안 검증은 사용자 폰에서만, 횟수를 줄이려면 한 번의 세션에 아래 체크를 몰아서 한다. 업로드 전 테스트에서 anonKey 코드 교환(서버 의존)은 실기기에서만 완전 확인 가능.

## 출시 게이트를 줄이는 방법
1. 서버 게이트(RLS·RPC·멱등)는 이미 자동화됐으므로 실기기는 "토스 WebView 고유 위험"(글자·TTS·백버튼·지연·네비바 가림·세션 유지)에만 집중. 기존 qa.md §2의 조건 1~2는 연결 방식이 anonKey로 바뀌면 재정의 필요(코드 입력은 자녀·어르신 연결에 여전히 쓰이는지 미확인).
2. 화면 컷 G에 맞춰 게이트 대상 화면 목록을 고정하고, 목록 밖 화면 추가는 게이트 재판정 요구.
3. 토스 안 확인은 사용자 폰 2회 세션(빌드 업로드 직후, 수정 후)으로 제한. 세션당 체크리스트 1장, 소요 약 60분(가정).
4. 회귀 목록은 11개 유지 + 토스 5개 추가(백버튼, 2초 지연, 라이트 모드, 핀치, TTS 대체). 정책: 새 안건 A·D·E 때문에 매 빌드 추가되는 회귀는 호칭 조사 단위 테스트, 삭제 양방향, 동의 문구-화면 대조 3개뿐.

## 내가 틀릴 수 있는 이유
1. 토스가 OS 글자 크기·TTS를 브리지로 이미 지원할 수 있다(그러면 위 우려는 과대).
2. 어르신 대부분이 TalkBack을 안 쓰므로 우선순위를 낮춰도 될 수 있다(그러나 자녀·저시력은 쓸 수 있음).
3. 15~20개 게이트 화면 컷은 임의 가정이라 빠진 중요 화면이 있을 수 있다.
4. 토스가 핀치 줌 비활성을 앱 단에서만 요구하고 OS 확대는 유지하면 충돌이 없다.
5. 3가구는 통계가 아니라 일화다. 합격 기준은 신호이지 증명이 아니다.

## 안건에 없지만 가장 중요한 질문
1. 어르신이 토스 앱 안에서 **우리 미니앱까지 어떻게 도달하는가**(검색? 자녀가 보낸 링크? 홈 화면 바로가기?). 도달 경로가 3가구 관찰의 첫 과제이며 qa.md는 "앱 아이콘 찾기"로 되어 있어 수정 필요.
2. 토스 본인 인증 단계가 어르신에게 어려워 시작도 못 하면 앱 품질 이전에 이탈한다. 이 단계는 우리가 통제 불가라 지표 분리 필요.
3. 연결 방식(anonKey vs 6자리 코드)이 확정돼야 게이트 1·2를 다시 쓸 수 있다.

## 사용자에게 묻고 싶은 것
- 토스 앱 테스트용 폰(Android+iOS 각 1대)을 확보할 수 있는가.
- 어르신 3가구에서 토스 설치·인증 여부를 방문 전에 전화로 먼저 물어봐도 되는가.
- 글자 "크게 보기" 자체 설정을 빌드 1에 넣는 것에 동의하는가(핀치 줌 금지 보상).
