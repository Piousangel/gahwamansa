# QA·접근성 의견 (R2) · 2026-11-17
r1 7개를 모두 읽고 작성. 수치는 가정, 토스 WebView 동작은 미확인.

## 동의하지 않는 의견 2개와 반박
1. **PM A("오늘 했는지"까지 지우고 '가장 최근 고른 답+날짜'만)**: 어르신 관점의 감시 우려는 동의하나 검증 관점에서 반대한다. (a) SPEC 완료 조건 4("코스 완료가 자녀 홈에 1분 안 반영")의 관측 신호가 사라진다. 신호가 없으면 게이트 4는 "답이 뜨는가"로 바뀌는데, 답은 2단계(밸런스)에서 이미 저장되므로 3단계 완료 신호와 구분이 안 된다. (b) 지운 쪽이 자녀를 더 불안하게 한다는 UX·writer 지적이 맞다(앱 고장 오해). 반박안: "오늘 했어요"(좋은 소식 한 줄)만 남기고 단계 칩·연속일·"아직"은 자녀 화면에서 제거한다. 게이트 4는 이 한 줄 하나로 측정한다.
2. **UX H 대안("며칠 소식이 없어요" 선택 알림 + 동의 문구에 '며칠 안 열면 알려요')**: 방향은 이해하나 빌드 1에 넣으면 안 된다. (a) 푸시 의존 기능이라 토스 푸시 명세 미확인, 빌드 2 이후. (b) "N일째 없음"은 시간 경과 테스트(자정·KST·유예일)가 필요해 회귀 비용이 크고, 오작동 시 자녀에게 허위 경보가 간다(감시·불안 방향의 오류가 가장 해롭다). (c) 동의 문구가 늘면 어르신 이해도 검증 항목이 늘어난다. 반박안: 빌드 1은 자녀 홈의 중립 고정 문구("엄마의 하루는 이제 시작이에요" 류, UX 제안)까지만. 경보형 알림은 3가구 관찰 후 결정.

## 바뀐 입장

- 안건 C: r1에서 응원 수신 표시만 포함, 설정 3개라고 했으나, policy·PM이 설정을 삭제(Play 요건)의 실체로 본다 → **설정은 호칭·삭제·동의 철회로 유지, 알림 토글만 컷**. 응원은 PM·UX·writer와 같이 "자녀 화면이 약속하므로 둘 다 넣거나 둘 다 뺀다"로 설득됨.

## 쟁점 ①: dev 공수(55~65h, 11/30 제출 30~40%)에 맞춘 QA 게이트 축소
접근성 필수(깎지 않음): 글자 본문 20sp 이상·버튼 64dp·화면당 3버튼, 대비 4.5:1(자동 계산), 150%에서 잘림 0, 시간 제한 0, 오류 문장 이해, 라이트 모드, 백버튼, 2초 반응, 자체 "글씨 크게" 설정(토스 OS 글자 반영 미확인 보상). 이 8개는 자동화 가능한 것이 많아 사람 시간이 작다.
줄이는 것(사람 시간 약 절반, 가정): ① 서버 게이트(RLS·RPC·멱등)는 기존 자동 테스트 통과 로그로 대체(이미 pgTAP 116, 통합 13). ② 게이트 화면 15~20개 고정, 나머지는 스크린샷 눈 확인. ③ 200% 확대·디스플레이 최대는 "보통" 등급으로 강등(150%만 차단). ④ TalkBack은 출시 차단에서 제외, "높음"까지(코드 입력은 단일 input으로 설계해 비용 낮춤). ⑤ 자녀 화면 접근성은 터치 48dp·대비만. ⑥ Play 트랙 실기기 게이트는 토스 완료 뒤로 미룸(회귀는 단위 테스트로만).
dev의 테스트·QA 10~14h 안에 들어가려면 위 6개가 전제다. 하나라도 빼면 출시 차단 후보가 추가로 생긴다고 본다(11/30 확률은 더 낮아짐, 판단은 PM).

## 쟁점 ②: 토스 실기기 2회 세션의 현실성
- 사실: 토스 앱 안 검증은 사용자 계정·QR·폰 필요(04). 브라우저 devtools 통과는 토스 앱 통과가 아님. 가정: 사용자 일정은 하루 60분 2회가 한계.
- 줄이는 방법: 세션 1(업로드 직후): 반응 2초, 백버튼, 라이트 모드, 핀치, 글자 150% 반영 여부, TTS 동작, 네비바 가림, anonKey 코드 교환 — **8개를 체크리스트 1장에 몰아 한 번**. 세션 2(수정 후): 실패 항목만. 어르신 3가구 방문은 세션 1과 분리하지 않고, 어르신 폰에서 토스 설치 여부를 전화 확인한 가구만 방문(T0 선행).
- 대체 불가 항목: TTS·글자·iOS 쿠키 차단은 개발 쪽이 mp3 대체·자체 글자 옵션·토큰 인증으로 **설계 시점에 안전하게** 만들면 세션 1 실패 확률을 낮출 수 있다(방어적 설계가 검증 부담을 줄이는 유일한 길).
- 위험: 사용자 폰이 한 대면 iOS 검증이 빠진다. 그 경우 iOS는 "미검증 출시 위험"으로 DECISION-MEMO에 명시해야 한다.

## 쟁점 ③: 안건 H 문구 원칙을 QA 항목으로 만들 수 있는가 — 가능(부분)
자동(grep, 단위 테스트): 어르신·자녀 문구와 푸시 문구에서 금지어 0건. 목록(초안, writer가 확정): 아직, 못 했, 안 했, 미완료, 끊겼, 실패, 틀렸, 오답, 정답, 왜 안, 빨리, 벌써, 지각, 연속 실패, 치매, 예방, 치료, 개선, 효과. 허용 예외 문장은 "아직 준비 중이에요"(동의 보류 안내, writer 3-4)처럼 화이트리스트로 관리해 오탐을 막는다. 사용 불가 단어 목록은 copy.ko.json에서 스캔(키 외 문구가 코드에 있으면 실패). 동시에 "정해진 중립 문구만 허용"을 테스트(문구 키 화이트리스트).
사람 확인(자동 불가): 문장의 톤·탓하는 느낌·"무소식=안심" 오해. 관찰 질문 3(동의 이해)과 자녀 1인에게 "이 화면을 보고 엄마가 괜찮은지 알 수 있나요"를 묻는 질문 1개를 추가한다.
한계: 금지어가 없어도 자녀가 "빈 화면=고장"으로 읽는 것은 grep으로 못 잡는다(UX 지적 유효).
