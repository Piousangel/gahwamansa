## 2. '보여서 생기는 좋은 일' 한 줄 — 두 안과 판단

| | 안 A — 넣음(권장) | 안 B — 넣지 않음 |
|---|---|---|
| `body[1]` | **연결된 가족은 이야기를 꺼내고 챙겨 드릴 수 있어요** (29자) | **연결된 가족이 이야깃거리와 챙겨 드릴 거리로 봐요** (27자) |
| 성격 | 목적을 **가족이 하는 일의 장면**으로 말함(UX 2.4 '들키는 순간'을 미리 보여 줌) | 목적을 **쓰임의 이름**으로만 말함(v5 '이야깃거리로 봐요'와 같은 꼴) |
| 줄 수·길이 | 같음(5점) | 같음(5점), 2자 짧음 |
| 법률 | 목적 2가지(이야기·챙겨 드림) 모두 들어 있음 | 같음 |
| 어르신이 읽는 느낌(추정) | "가족이 나를 챙겨 주겠구나" → 보이는 것이 덜 불안. 대신 '드릴 수 있어요'가 좋은 일을 약속하는 쪽으로 기울 수 있음 | 중립. '챙겨 드릴 거리'라는 낯선 묶음말을 어르신이 한 번 더 풀어 읽어야 함 |

**판단: 안 A.**
1. 두 안 모두 목적 줄은 **반드시** 있어야 한다(아래 3절 — 이 줄이 없으면 v6 새 쓰임이 동의 밖이다). 그러니 '좋은 일 한 줄을 더 넣을까'는 줄을 하나 더 쓰는 문제가 아니라 **목적 줄을 어떻게 쓰느냐**의 문제다. 안 A는 줄이 늘지 않는다(200% 부담 0).
2. UX 2.4: '보여요'만 말하는 것보다 보여서 생기는 일을 말하는 문장이 덜 불안하다. 리스크 2.1 ①의 '모여 보여요'가 처음 줄에 있어 무게가 커졌기 때문에 바로 다음 줄에서 그 쓰임을 사람의 장면으로 받아 주는 편이 낫다.
3. 유도 위험(추정, 개인정보 동의 문구는 이익만 강조하면 안 됨)은 이렇게 막는다: ① 사실 줄(무엇이·누구에게) **뒤**에 둔다 ② '~수 있어요'(가능)로 쓰고 '챙겨 드려요'(약속)로 쓰지 않는다 ③ 감정어(행복·든든·마음)·효과어 없음 ④ 거부 안내 두 줄이 버튼보다 먼저 ⑤ 두 버튼 같은 무게. UX 2.4 예시 "가족이 좋아하시는 걸 챙겨 드릴 수 있어요"는 '좋아하시는'이 금지어라 쓰지 않았다.
4. 안 B는 L-13 회신이 "목적 문구를 더 중립으로"라고 오면 바로 갈아 끼울 대체안으로 둔다(같은 키, 같은 버전 v6 — 아직 출시 전이므로).

## 3. 거절·미응답 때 v5 범위 유지 — 설명 문구(예비)

기획 v2.1은 **외부 테스터 모집 전에 v6로 시작하고 테스터 v5 동의·답을 초기화**한다(0.1 '추가 P2', 0.5 [8]). 그러면 출시 때 v5 동의자는 0명이고, 새로 오시는 분은 v6 [좋아요] 또는 [싫어요](v5 거절과 같음 — 저장 0) 둘 중 하나다. **출시 때는 아래 문구가 필요 없다.**

다만 서버 게이트(`consent_version` < v6이면 모아 보기 데이터 대신 날짜 카드만)는 만들기로 했으므로, 나중에 범위를 또 넓힐 때나 초기화를 못 한 경우를 위해 **재동의 화면 문구**를 예비로 둔다(리스크 2.1 '재동의 설계': 거절 = v5 범위 유지, 미응답 = v5 범위, 코스 끝 뒤 하루 한 번까지, 코스를 막지 않음).

| 키(제안) | 문구 | 이유 |
|---|---|---|
| `consent_v6.title` | 가족에게 보이는 모습이 바뀌어요 | 무엇이 바뀌는지를 먼저(재동의임을 숨기지 않음) |
| `consent_v6.now` | 지금은 날짜마다 고르신 답이 가족에게 보여요 | 지금 범위(v5)를 사실로 |
| `consent_v6.body` | 1절 v6 `body[0]~[4]`와 같은 다섯 줄 | 새로 동의하는 범위가 신규 화면과 글자까지 같아야 버전 하나로 기록된다 |
| `consent_v6.keep_note` | 싫어요를 눌러도 지금처럼 날짜마다 보여요. 지금까지 답도 그대로예요 (22자 + 13자, 두 문장) | 거절이 손해가 되지 않게(리스크 2.1, 제22조⑤ 취지). '지워져요'가 아님을 분명히 |
| `consent_v6.accept` / `decline` | 좋아요 / 싫어요 | 같은 무게, 신규 P2와 같은 버튼. '지금처럼 둘게요'도 봤으나 8자로 버튼 2~6자 규칙을 넘어, 거절 결과(유지)는 `keep_note`가 버튼 **앞에서** 말하게 했다 |
| `consent_v6.declined_notice` | 지금처럼 날짜마다 보여요 | 거절 뒤 한 줄 확인 |

- 미응답(화면을 닫음·안 봄): 문구 없음. v5 범위 그대로, 다음 코스 끝에 한 번 더(하루 한 번까지).

## 4. 법률 판단 (LG-1)

### 4.1 재동의가 필요한가 → **필요(보수 판단)**, 출시 전이라 'v6로 시작 + 테스터 초기화'로 갈음
| 5요소(제17조②) | v5 | v6 | 바뀜 |
|---|---|---|---|
| 1 받는 자 | 연결된 가족 | 연결된 가족 | 없음 |
| 2 목적 | 이야깃거리 | 이야깃거리 **+ 챙겨 드릴 거리**(답 옆에 운영자 문장을 붙여 보임) | **바뀜** |
| 3 항목 | 고른 답·날짜 | 고른 답·날짜(새 항목 없음). 보이는 **모양**이 날짜 카드 → 한 달 모은 목록 | 항목은 같음, 제공 방식이 바뀜 |
| 4 기간 | 한 달 | 한 달 | 없음 |
| 5 거부 권리 | 있음 | 있음 | 없음 |

- **근거**: ① 제공 동의는 목적을 알리고 받는다(법 제17조② 2호) — 목적이 넓어지면 이전 동의는 넓어진 목적을 덮지 않는다(제18조① 목적 외 제공 금지, 추정). ② 리스크 2.1: '그날 고른 답'과 '모아서 정리된 나'는 정보주체가 받아들이는 무게가 다르다(윤리 경계). ③ 지금 동의 장치는 버전을 **저장만** 하고 비교하지 않는다(리스크 위험 2 사실) → 문구만 바꾸면 v5 동의자는 v6 범위를 동의한 적 없이 받게 된다.
- **가장 싼 길(리스크 2.1)**: 출시 전이므로 v6 하나로 시작하고 테스터 v5 동의·답은 지운 뒤 다시 묻는다. 서버 게이트는 그래도 만든다(기획 0.1 — 옛·새 자녀 앱 일관성, 다음 범위 변경 대비).
- **L-13 회신이 '방침 개정으로 충분'이어도** 테스터 초기화 비용이 작아 위 길을 바꾸지 않는다(제안).
- 구분 동의(제22조①2호)·거부해도 서비스(제22조⑤)·쉬운 말(시행령 제17조①)은 v5 구조 그대로라 유지된다.

### 4.2 '풀이하지 않아요'가 지켜지는 조건 (사실로 만들어야 하는 것)
- '챙겨 드릴 거리'는 **보기(선택지)마다 미리 쓴 같은 문장**이어야 한다 — 같은 보기를 고른 누구에게나 같은 줄. 사람별 누적·횟수·갈래 꼬리표 집계로 문장을 고르면 '어떤 분인지 풀이'가 된다(리스크 Q2 안 B 반대 근거). 콘텐츠 설계서 4.1 "고르신 쪽 하나에만 붙는다"와 같음.
- 숫자 없음(Q3), 순위 없음(Q2) — 목록은 날짜순.
- 위 둘이 깨지면 `body[2]`가 거짓이 된다 → 구현 레인 수용 기준에 넣을 것.

### 4.3 보관 31일·1년 연장(Q11)과 모순 점검
- `body[0]` '한 달 동안 모여', `body[4]` '한 달 뒤에 … 지워져요' = 파기 31일째(0023·0043), 자녀 목록 30일(0021)과 같다.
- 1년 연장은 **부모님 본인이 설정에서 따로 켜는 새 동의**(answer-retention-option §1, L-7 뒤). 그 화면이 자기 기간 문장을 갖고 따로 기록되므로 v6 문장을 고칠 필요가 없다. 단 연장 범위가 **가족도 1년 보는 B안**이면 5요소 #4 재동의라 v7이 된다(§2 B안). A안(부모님만 다시 보기)이면 v6 그대로.
- 그래서 v6에는 '한 달만'·'언제나 한 달' 같은 닫는 말을 쓰지 않았다.
