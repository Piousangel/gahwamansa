- 기기 안에만: 로그인 상태, 초대 번호(최대 7일), 미연결 도장 날짜(7일).

## 5. 암호화 (고시 제7조, 보안 회의 E6·D15 반영)
- 전송: 앱 ↔ Supabase·Firebase HTTP API는 TLS만(사실), release 빌드 cleartext 금지(release-gates 확인 항목), DB 직접 접속 SSL 강제.
- 저장: **데이터베이스와 백업은 Supabase가 AES-256으로 암호화**(사실: Supabase security 문서, 보안 회의 D1·D15). 컬럼 단위 암호화는 하지 않는다 — 고시 제7조②의 저장 암호화 대상(주민·여권·면허·외국인등록번호, 카드·계좌, 생체, 비밀번호)을 받지 않기 때문(D1, 2차 자료 → 원문·118 확인 L-1~L-3). 앞으로 그런 정보를 받게 되면 저장하지 않는 것이 우선, 필요하면 Edge AES-GCM + HMAC(D17).
- 비밀번호: 이용자 비밀번호를 받지 않는다(소셜·인증번호·익명). 인증번호는 Supabase Auth가 처리, 10분 만료.
- **내려받은 자료**(제7조⑤): 지표 CSV·감사 내보내기·대장 등 이용자 정보가 든 파일은 취급자 노트북에만, FileVault 켠 디스크 + 암호화 zip으로 저장, 쓰고 나면 지움. 개인 식별값은 넣지 않는 것이 원칙(SV-16 스니펫 `is_test` 제외·20명 미만 비율 숨김). FileVault가 ⑤ 충족인지는 118 확인 L-2.
- 기기: 초대 번호는 앱 전용 저장소(MODE_PRIVATE, 자동 백업 꺼짐), Android 12+ 기기 간 이전도 제외(data_extraction_rules, D7 — L4). 세션 토큰은 Keystore 래핑하지 않음(D8, 빌드 2 조사). production 빌드에는 개발자 메뉴가 없다(release-gates A8).

## 6. 접속 기록 보관과 점검 (고시 제8조)
- 기록 요소(제2조3호): 식별자·접속 일시·접속지·처리한 정보주체 정보·수행 업무. Supabase Pro는 플랫폼 감사 로그가 없고(사실) API·DB 로그는 7일만 남으므로(사실: pricing "Log retention Pro 7 days"), **수기 접속 대장 + `admin_audit`(0039·0043)**로 1년 이상 보관한다.
  ```
  날짜·시각(KST) | 콘솔 | 접속지(집·사무실 등) | 목적(예: 삭제 요청 REQ-2026-012 처리, 장애 확인) | 본 정보(테이블·건수, 식별값은 끝 4자리) | 수행 업무(조회/수정/삭제/내려받기) | 비고
  ```
- 위·변조 방지(제8조③): 대장은 저장소 밖 문서 {저장 위치}, **매월 1일 PDF로 고정 + 해시(sha256) 기록**.
- 점검(제8조②): 매월 1일 대장과 `admin_audit`·Auth 감사 로그(Pro 7일분)를 대조, 내려받기 기록 포함. 설명 안 되는 접속이 있으면 §9.
- **관리자 감사 기록 규칙(DECISIONS 11-18, 방침 표기: 운영자 작업 기록)**: 모든 `admin_*` RPC의 사유(reason)에는 **요청 번호만**(예: `REQ-2026-012 웹 삭제 요청`), 이름·메일·닉네임·기종 금지. 처리자(operator)는 역할명(`owner`). 서버가 사유·처리자에 `@`·9자리 이상 숫자열이 있으면 `pii_in_args`로 거부(사실: 0047 `admin_check_args`, 보안 회의 D5). 서버가 거부하는 것은 이 두 가지뿐이다. 이름·닉네임·기종, 하이픈이나 공백으로 끊은 번호(예: 010-1234-5678)는 0047 기준 서버를 통과하므로 이 규칙으로만 막는다(L1 보강 중 — 병합되면 이 줄을 고친다). 요청 번호↔메일 대응은 문의 메일함의 삭제 요청 대장에만 두고 처리 완료 후 §7 기준으로 지운다.
- **약관·방침 게시 기록(0048)**: 새 버전은 `admin_publish_terms_version(종류, 버전, 사유, 처리자)`로 등록한다(감사 `terms_publish`). 등록은 **되돌릴 수 없다**(지우거나 고치는 함수 없음, 최신 = 게시 시각이 가장 늦은 것).
  1. 버전 문자열: `v<숫자>[.<숫자>]` 또는 `YYYY-MM-DD`. 게시본 머리 "버전 N" = `vN`.
  2. 등록 전 **두 번 대조**: ① 게시본 머리 버전 = 앱 버전 상수 ② 등록할 문자열 = ①. 대조한 사람·시각을 §6 접속 대장에 적는다.
  3. **등록·게시·앱 상수 배포는 같은 날**: 등록 → 게시 → 앱 순서. 등록 전 버전은 앱이 보내도 기록되지 않고(`unknown_version`), 등록 뒤 앱이 늦으면 모든 사용자에게 재동의가 필요하다고 나온다(`needs_reagree`).
  4. 잘못 등록했을 때: 바로 앱 상수 배포를 멈추고 리드를 거쳐 L1에 보정 마이그레이션을 요청한다(서버 함수로는 못 고침). 대장에 경위를 적는다.
  5. 이전 버전 문서는 방침 13절대로 링크로 남긴다.

## 7. 파기
- 자동: pg_cron `purge-expired-data` 매일 — 고른 답·코스 기록 31일째, 응원 31일, 초대 번호·입력 시도 30일, 알림 큐 30일, 이용 기록 14개월, 카카오 해제 큐 포기 행 30일, 감사 기록 1년(사실: 0023·0028·0039·0042·0043). 카카오 포기 행은 06시 점검에서 **당일** `admin_kakao_unlink_retry`/`_resolve`로 처리(D2, 0047). production 첫 실행 성공을 G-INT 전에 확인(release-gates G-18).
- 계정 삭제와 함께: 약관·방침 확인 기록(`auth.users` on delete cascade, 0046), 동의 이력(0019). 시간 기준 파기는 없다 — 계정이 남아 있는 동안 지난 버전 기록까지 보관(방침 4절과 같음).
- **빈 곳(리뷰 M1)**: 가족 연결 전 계정(프로필 없음, 확인 기록 role `none`)은 앱 `delete_my_account`·`admin_delete_account` 모두 지우지 못한다(`no_profile`, 0039). 서버 경로는 리드가 L1에 요청. 방침·삭제 안내는 "메일로 요청"을 안내하므로, 경로가 생기기 전에는 게시하지 않는다(CHANGES P20). 그 전에 요청이 오면 대장에 적고 경로가 생기는 대로 처리한다.
- 요청 삭제: 앱 안 삭제는 즉시. 웹 요청은 접수일부터 10일 안(보통 7일, 시행령 제43조③), `admin_delete_*`로 처리하고 대장에 적는다.
- 백업: 일 1회 백업 7일 보관 후 덮어쓰기(Pro).
- 테스터 명단(Gmail): 비공개 테스트 종료 후 {테스트 종료일 + 30일}까지 삭제(LG-12), 삭제한 날 대장에 기록.
- 내려받은 자료: 목적을 마치면 즉시 삭제(§5).
