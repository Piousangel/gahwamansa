# 스승님 조사: Lauren Tan과 SpaceXSI (2026-11-20)

리서치 담당이 썼다. 오너가 "우리 스승님"으로 소개한 영상과 두 이름을 공개 자료로 조사했다. 로그인이 필요한 곳은 보지 않았다. 확인 날짜는 모두 2026-11-20이다.

1. **영상**: 「All Code Is Slop (Except Mine) — Lauren Tan, SpaceXSI」. 채널은 AI Engineer(@aiDotEngineer)다. 2026-11-14에 올라왔다는 2차 자료가 있다.
2. **SpaceXSI는 사람이 아니라 회사다.** Lauren Tan의 소속이다. 옛 xAI가 SpaceX에 합쳐진 뒤의 AI 조직이고, 공식 페이지 하단 법인명은 SpaceX Super Intelligence LLC다. 영상 제목의 "Lauren Tan, SpaceXSI"는 "발표자, 소속" 표기다.
3. **영상 본문 미확인.** 자막과 영상을 직접 보지 못했다. 이 문서의 영상 내용은 공개 요약 3곳(아래 출처 [3][4][6])과 본인의 X 글 [8]을 맞춰 본 것이다. 요약끼리 숫자가 다른 곳은 그대로 표시했다.
4. 핵심 한 줄: **에이전트가 만든 코드를 믿으려면 사람이 더 읽을 게 아니라, 잘못된 선택이 처음부터 불가능한 환경(코드 구조·린트·검증)을 만들어야 한다.**

## 1. 인물 소개 (확인된 사실만)

### Lauren Tan (handle: poteto)
SpaceXSI에서 Grok Bot을 만드는 엔지니어다. X 소개글은 "grok @bot at @SpaceXSI. react compiler core team, prev cursor, meta, netflix"이다 [7][8]. 그 전에는 Meta의 React Compiler 핵심 팀에 있었고, Cursor·Netflix에서 일했다 [5]. 싱가포르에서 자랐고 모나시 대학교에서 회계·재무를 전공했다. 스프레드시트와 매크로를 만드는 게 더 재미있어서 프로그래밍을 독학했다고 한다 [5]. Grok Bot을 첫 코드부터 출시까지 약 7주 만에 낸 팀에 있었다 [5][6]. 에이전트 스킬 묶음 **pstack**(Cursor 플러그인, 핵심은 `/poteto-mode`)을 공개했다 [9][10].
- 동명이인 확인: 영상 제목·X 소개글·요약 사이트가 모두 "Lauren Tan = poteto = SpaceXSI의 Grok Bot"을 가리킨다. 그래서 영상 속 인물과 같은 사람으로 판단한다.
- 숫자는 출처마다 다르다. 본인 월 PR 수는 3,000건 [4][5]과 2,500건 [7, Digg 요약]으로 갈린다. 팀 단위로는 "한 달 11,000건, 되돌림 약 0.5%"라는 요약이 있다 [3][4]. 영상을 직접 보지 못해 어느 숫자가 맞는지 확인하지 못했다.

### SpaceXSI
사람이 아니라 회사(조직)다. 공식 Grok Bot 소개 페이지는 SpaceXSI라는 이름을 쓰고, 하단 법인명은 SpaceX Super Intelligence LLC다(2026-08-11 게시) [11]. Lauren Tan과 동료 Roman Ugarte는 YC Lightcone 팟캐스트에서 Grok Bot을 만든 방식을 설명했다(2026-11-14 게시, 요약 [6]).

## 2. 핵심 철학·원칙

### A. 에이전트를 믿는 4층 구조 (넓은 층에 시간을 더 쓴다)
| 층 | 내용 | 근거 |
|---|---|---|
| 1. 코드베이스 | 구조·API 설계·타입·경계. 쉬운 길이 곧 맞는 길이 되게 한다 | [3][8] |
| 2. 정적 분석 | 린트·타입·컴파일러·테스트·CI | [3][4] |
| 3. 검증 | 실행 검증(앱을 직접 돌림)과 형식 검증 | [3][4] |
| 4. 글(가장 얇게) | AGENTS.md·스킬·주석. 에이전트 판단에 기대므로 최소로 쓴다 | [3][8] |

본인 X 글은 사람의 리뷰를 맨 마지막 층으로 두고, 이 층은 늘리기 어렵다고 말한다 [8].

### B. 원칙 목록
1. **고칠 때마다 결정적 검사로 바꾼다.** 에이전트를 바로잡을 때 AGENTS.md에 한 줄을 더하지 말고 "make that a deterministic check"(검사로 만들라)라고 한다. 더 좋은 방법은 잘못된 선택 자체를 설계로 없애는 것이다 [4][3].
2. **코드베이스가 곧 프롬프트다.** "Your codebase is the agent's largest input"(코드베이스가 에이전트의 가장 큰 입력)이다 [3]. 에이전트는 기존 패턴과 우회 코드, 기술 부채까지 따라 한다. 그래서 새 코드만이 아니라 옛 패턴도 치운다 [4].
3. **미묘한 판단이 필요한 기능은 하나하나 리뷰하지 말고 금지한다.** 예를 들어 React `useEffect`는 제품 코드에서 쓰지 못하고 프레임워크 내부에서만 쓴다. Electron main과 renderer 디렉터리는 서로 import하지 못하게 의존 그래프 검사와 린트로 막는다 [3][4].
4. **주석으로 우회를 정당화하지 못하게 한다.** 에이전트가 setTimeout 같은 땜질을 하고 주석으로 변명하는 사례가 있었다. 그래서 주석의 약 99%를 금지하고, 린트 오류 메시지가 "근본 원인을 고치라"고 안내하게 했다 [4]. pstack에는 `no-comments` 스킬과 Comment Sicko 리뷰어가 있다 [9].
5. **리뷰는 코드 읽기보다 증거 확인이다.** 영상·스크린샷·도표·형식 검증 결과를 본다. 에이전트가 Chrome DevTools Protocol로 앱을 직접 돌린다. 이때 사용자 관점에서 모든 기능을 적은 지도(**feature map**)와 토큰을 아끼는 전용 CLI를 쓴다 [4].
6. **토큰은 대부분 검증에 쓴다.** TLA+로 핵심 흐름(기기 간 알림)을 모델 검사하고, Lean으로 가상화 라이브러리의 성질을 증명한다. 속성 기반 UI 테스트(Bombadil)도 쓴다. 다만 형식 검증이 만능은 아니라고 선을 긋는다 [4][6].
7. **안쪽 루프부터 고친다.** 코드를 쓰는 루프가 엉망이면 "automating that loop just produces more slop"(자동화해도 엉망만 늘어난다)이다 [5]. 대규모 "소프트웨어 공장"보다 코드베이스 개선이 먼저다 [6].
8. **자동화는 유지보수·성능·버그 수정에, 기능 결정은 사람에게.** 사람이 쓰는 소프트웨어의 경험은 일부러 설계해야 하기 때문이다 [5][13]. 매 릴리스 뒤에는 에이전트가 앱을 사용자처럼 퍼징하고, 버그마다 PR을 열어 자동 병합한다 [4].
9. **내부에서 먼저 써 보고 낸다.** 매일 보는 변화는 불편할 만큼 오래 내부에서 써 본다. "if something doesn't get internal product market fit, we don't ship it"(내부에서 안 맞으면 출시하지 않는다)이다 [13].
10. **신뢰 사다리.** 봇의 권한은 읽기 → 행동 → 결과 소유 순서로 넓힌다. 새 입사자처럼 좁은 권한에서 시작한다. 같은 역할의 사람에게 무엇을 줄지를 기준으로 삼는다 [13].
11. **실행이 싸지면 실패는 '의도가 불분명해서' 생긴다.** 병목은 "무엇을 만들지 합의"로 옮겨 간다 [13].
12. **90%와 100%는 다르다.** Grok Bot 제품 리드의 말이다: "There is a huge difference between 90% done and 100% done." [11]

### C. pstack 원칙 (Lauren Tan의 작업 방식을 코드로 옮긴 것) [9][10]
- **laziness-protocol / subtract-before-you-add**: 가장 작은 변경, 더하기 전에 먼저 지운다.
- **prove-it-works**: 대리 지표 말고 실제 결과물을 확인한다. "결론 안 남"은 통과가 아니다. 버그는 재현 → 원인 확인 → 같은 재현이 통과하는 순서로 고친다.
- **experience-first / exhaust-the-design-space**: 구현 편의보다 사용자 경험을 앞에 둔다. 확정 전에 시안 2~3개를 비교한다.
- **type-system-discipline / model-the-domain**: 잘못된 상태는 표현할 수 없게 만든다. 도메인 규칙은 흩어진 if 대신 구조에 담는다.
- **encode-lessons-in-structure**: 교훈은 글 대신 린트·검사·스크립트로 남긴다.
- **guard-the-context-window / never-block-on-the-human**: 큰 작업은 서브에이전트에 맡기고 요약만 받는다. 되돌릴 수 있는 일은 묻지 않고 진행하며, 되돌릴 수 없는 일(배포·데이터 삭제·고객 메시지)만 멈춰서 확인한다.
- **interrogate / arena**: 여러 모델이 diff를 깨 보게 하고 증명된 지적만 남긴다. 같은 과제를 병렬로 여러 번 시도해 좋은 부분을 합친다.
- **show-me-your-work**: 결정을 기록하고, 주장마다 "측정함/추론함/추측함"을 밝힌다.
- 리드가 서브에이전트 보고를 옮겨 적지 않고 **diff를 직접 보고 요약**한다 [10].

## 3. 우리 팀에 옮길 것

비교 기준은 지금 우리 방식이다. 리드가 여러 에이전트 레인을 조율하고, 작성자와 리뷰어를 분리한다. PR과 워크트리로 일하고, 전문가 패널이 리뷰한다. 오너는 큰 방향만 정한다. 완성도가 우선이고, 출시는 12월 중순이다.

### 3-1. 이미 하고 있는 것 (계속한다)
| 우리 방식 | 대응하는 원칙 |
|---|---|
| `app/.eslintrc.js` 레이어 규칙·디자인 시스템 규칙과 기준선 테스트(`layerBaseline`·`dsBaseline`, 위반이 늘면 실패) | B-1 교정을 검사로, B-3 금지로 막기. **이미 스승님 방식 그대로다** |
| 작성자≠검토자, 놓친 것·부족한 것·과한 것을 묻는 리뷰 | interrogate(증명된 지적만), subtract-before-you-add |
| 워크트리 + PR + 작은 단위 병합 | poteto-mode의 PR 플레이북(워크트리, 작은 커밋, 초안 아닌 PR) |
| 디자인 품질 관문: 렌더해서 직접 보기, 기기 폭×확대 매트릭스 | B-5 증거로 리뷰, prove-it-works |
| "미확인/가정" 표기, 실행한 것만 보고 | show-me-your-work(측정/추론/추측) |
| 오너는 큰 방향만, 리드는 결정만 묶어서 질문 | never-block-on-the-human, B-11 병목은 방향 합의 |
| 레인별 전문 에이전트 | Grok Bot의 "관심사 하나에 작은 봇 여럿" [13] |

### 3-2. 바꾸거나 더할 것 (구체 행동·비용)
1. **반복되는 리뷰 지적을 검사로 바꾸는 주간 작업.** 리뷰 문서 형식(`docs/team/reviews/`)에 "검사로 바꿀 수 있나: 린트/테스트/타입/아니오" 칸을 더한다. 리드는 주 1회 지적을 모아 2번 이상 나온 것 상위 3개를 린트 규칙이나 테스트로 만드는 PR을 연다. OPERATING.md에 "문서 규칙을 더하기 전에 검사로 만들 수 없는지 먼저 본다"를 한 줄 넣는다.
   - 비용: 리드 정리 30분 + 개발 에이전트 1회(규칙 2~3개)/주.
2. **PR 본문에 '증거' 칸을 의무로.** 화면이 바뀌는 PR에는 에뮬레이터 스크린샷이나 짧은 녹화, 바뀌기 전·후 테스트 출력을 붙인다. 버그 PR에는 재현 → 수정 → 같은 재현 통과를 붙인다. `pr-guard.yml`에 "본문에 `## 증거` 절이 없으면 경고" 단계를 더한다(지금처럼 막지는 않는다).
   - 비용: 워크플로 수정 1회(작음), PR당 몇 분.
3. **사용자 관점 기능 지도(feature map) 한 장.** 어르신 화면(P1~P7)과 자녀 화면을 사용자 말로 적는다. 화면마다 들어가는 길, 상태(동의 전/후, 연결 전/후, 오프라인), 기대 결과를 담는다. 같은 지도를 QA 체크리스트(`docs/team/qa/`), 에이전트 앱 실행 검증, 전문가 패널 리뷰의 어휘로 함께 쓴다. 화면이 바뀌면 같은 PR에서 지도도 고친다.
   - 비용: QA 레인 반나절, 이후 PR마다 몇 줄.
4. **핵심 상태 흐름에 속성 기반 테스트.** 초대 코드(6자리·1회용·7일 만료), 동의 전후 저장 여부, 재연결과 익명 계정 90일 정리가 대상이다. TLA+ 대신 Jest에서 fast-check 같은 도구로 "어떤 순서로 눌러도 동의 없이는 답이 저장되지 않는다" 같은 성질을 검사한다(도구 도입은 개발 레인 판단). 상태가 꼬이는 곳 2~3개만 한다.
   - 비용: 개발 1~2일. 위험 영역(동의·삭제)이라 값어치가 크다.
5. **'우회 정당화 주석' 금지 + 린트 메시지가 원인을 안내하게.** 결정 근거 주석(ARCHITECTURE·DECISIONS 링크)은 지금처럼 둔다. 대신 setTimeout·지연·`eslint-disable`로 증상을 덮고 주석으로 변명하는 패턴을 리뷰 체크리스트에 넣는다. `eslint-disable`은 이유와 결정 링크가 없으면 실패하게 한다. 새 린트 규칙의 메시지에는 "어디로 옮겨라/무엇을 써라"를 쓴다(지금 DS 규칙처럼).
   - 비용: 작음.
6. **새 기능·큰 변화는 팀 가족 테스터가 먼저 매일 써 보기(내부 PMF).** 공개 출시 전에 오너 가족·테스터 가족이 최소 1~2주 매일 쓰는 기간을 출시 게이트(`release-gates.md`)에 넣는다. 통과 기준은 "테스터 어르신이 안내 없이 매일 열었나"다. 12월 중순 일정과 부딪히면 오너가 기간을 정한다.
   - 비용: 일정 1~2주(결정 필요).
7. **리드는 에이전트 보고를 옮겨 적지 말고 diff와 증거를 직접 본다.** 이미 "리드가 산출물 재검증"이 있지만, 완료 보고에 "리드가 직접 본 것: diff·스크린샷 목록"을 따로 적게 한다.
   - 비용: 없음(형식만).

### 3-3. 우리 상황에 안 맞는 것 (가져오지 않는다)
- **에이전트가 자기 PR을 자동 병합하는 것, 릴리스 뒤 퍼징 → 자동 병합.** 그 팀은 수개월에 걸쳐 쌓은 검증 층이 있어서 가능하다 [5]. 우리는 출시 전이고, 동의·개인정보·삭제 같은 위험 영역이 크다. 작성자≠검토자 원칙을 유지한다.
- **TLA+·Lean 같은 형식 검증.** 우리 규모와 일정에 비해 과하다. 대신 위 3-2의 4번처럼 속성 기반 테스트로 충분하다.
- **주석 99% 금지를 그대로 따르기.** 우리는 결정 근거를 주석과 문서 링크로 남기고 사람(오너)도 코드를 읽는다. "우회 정당화 주석"만 막는다.
- **useEffect 금지 같은 특정 규칙을 그대로 복사하기.** 원칙은 "우리가 반복해서 틀린 것을 막는다"이다. 남의 금지 목록이 아니라 우리 리뷰 기록에서 규칙을 뽑는다.
- **월 수천 PR 규모의 처리량 목표.** 우리 목표는 처리량이 아니라 완성도와 12월 중순 출시다.
- **여러 회사의 모델을 섞는 리뷰(interrogate·arena).** 필요하면 위험 영역 PR에서만 codex 스킬 같은 다른 모델 리뷰를 선택적으로 쓴다(비용 판단은 리드).

## 4. 제품(가화만사성) 관점 시사점

엔지니어링 발표라서 제품에 직접 쓸 수 있는 내용은 많지 않다. 아래는 우리가 해석한 것이다(가정).
1. **신뢰 사다리 = 가족 사이 공개 범위의 순서.** Grok Bot은 읽기 → 행동 → 소유 순서로, 새 입사자처럼 좁게 시작한다 [13]. 우리 앱도 처음에는 최소로 공개하고, 동의한 뒤에만 답을 저장하고, '더 오래 보관'은 가족이 직접 켜게 했다(O-D). 이 순서가 이미 같은 방향이다. 앞으로 기능을 더할 때도 "어르신이 사람에게라면 이걸 처음부터 맡기겠나"를 기준으로 삼으면 감시 금지 원칙과 맞는다.
2. **90%와 100%의 차이 [11].** 어르신 화면은 거의 다 된 흐름 하나보다 끝까지 막힘 없는 흐름 하나가 낫다. 출시 범위를 줄이더라도 하루 코스(사진 → 질문 → 따라 쓰기 → 완료)는 100%로 만든다. 지금 정한 '완성도 우선'과 같다.
3. **내부에서 안 맞으면 내지 않는다 [13].** 어르신 관찰 테스트(V27, `elder-observation-guide.md`)를 출시 게이트로 쓰자는 근거가 된다. "테스터 어르신이 안내 없이 다시 열었나"를 첫 기준으로 둔다.
4. **기능 지도의 어휘 = 어르신의 말.** feature map은 사용자 관점 어휘가 핵심이다 [4]. 우리 지도는 '오늘 사진', '팻말'처럼 어르신이 쓰는 말로 적는다. 그러면 화면 문구·푸시·스토어 설명이 같은 말로 맞춰진다.
5. **실행이 싸지면 실패는 의도에서 난다 [13].** AI로 사진·문구를 많이 만들 수 있게 된 지금, 품질은 생성 속도가 아니라 "이 사진이 어르신에게 어떤 기억을 불러야 하나"라는 의도 명세에서 갈린다. 사진 큐레이션 기준(시대·장면·피할 것)을 글 대신 검사(메타데이터 필수 항목 검사)로 만들 수 있는지 큐레이터 레인이 검토할 만하다.
6. **experience-first, 시안 2~3개 비교 [9].** 이미 전문가 패널로 시안을 비교하고 있으니 계속한다.
