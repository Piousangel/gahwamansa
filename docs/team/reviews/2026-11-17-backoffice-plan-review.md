# 11-backoffice 기획 독립 검토 (2026-11-17, 서버·정책·보안 3인, 읽기만, 테스트 미실행)
대상: docs/plans/11-backoffice.md. 근거: migrations 0001~0018, seed_content_14d.sql, scripts/photos, site/delete-account.html, 10 마스터 대장, Vercel 공식 약관. 결론: **방향(단계형·Studio→로컬 웹) 동의, 순번 공식·본인 확인·삭제 기한은 고쳐야 착수 가능.**

## 높음
- [서버] **제안 공식("진행일 < n이면 진행일+1, 다 돌면 순환")도 밀린다.** 진행일=`오늘-course_start_date`인 한, 이미 한 바퀴 돈 어르신은 n이 바뀌면 그대로 건너뜀(진행일 20: n=14→`mod(20,14)+1=7`, n=15→`6`). 날짜 차이에서 순번을 계산하는 방식으로는 못 고친다. 제안: 어르신별 **커서 저장**(`profiles.content_seq`·`content_seq_date`). 그날 첫 `get_today_content`에서 한 번만 "다음 day_index"로 전진(같은 날은 그대로), 다 보면 처음부터. n·추가 시점과 무관하고, 0019의 어르신별 구분과도 프로필 단위로 맞는다
- [서버] **번호 충돌.** 마스터 대장(10 §2)에서 0024~0025는 푸시 토큰·발송이다. 서버 줄이 순번 수정을 0024로 쓰면 겹친다. 대장에 번호를 먼저 받고(예: 0019에 넣거나 0026), 11 §4의 "0019~0025 묶음에 끼우기"를 정확한 번호로 바꿀 것
- [서버] **게시한 콘텐츠를 수정하면 과거 답의 뜻이 바뀐다.** 시드가 `on conflict (day_index) do update`로 prompt·option을 덮어쓴다(seed:24,41). answers는 question_id만 들고 있어 자녀 화면의 "A"가 새 문구로 보인다. 원칙: 게시 후 문항 수정 금지, 고치려면 새 행 추가 + 예전 행 은퇴(`retired_at`). 스크립트가 이미 게시된 day_index의 덮어쓰기를 거부하게
- [정책] **본인 확인 "가입 이메일 OTP"는 대부분에게 불가능.** 어르신은 익명 로그인(DECISIONS 11-16)이라 이메일이 없고, 카카오 자녀는 이메일을 받지 않는다(10 ⑥a). 제안: 자녀는 로그인 수단별(이메일·구글=그 주소로 회신 확인, 카카오=앱 안 "삭제 요청 코드" 또는 연결 자녀 닉네임+가족 정보 대조), 어르신은 앱 안 표시 코드, 폰 분실이면 연결 자녀가 앱에서 삭제하도록 안내. delete-account.html §2의 "확인 필요"와 같은 미해결이니 한 결정으로 묶을 것
- [정책] **처리 기한이 문서 안에서 다르다(§4 30일, §5 7일).** 개인정보보호법상 삭제 요구는 받은 날부터 **10일 이내** 조치·통지(시행령 제43조 3항, 조문 번호는 법무 확인 권장)라 30일은 안 된다. "목표 7일, 상한 10일"로 통일하고 delete-account.html §4 빈칸에 같은 값. Play 정책은 기한 숫자보다 "앱 밖 웹 링크로 요청 가능 + 삭제 범위·보관 고지"가 요건(정확한 문구는 Play 고객센터에서 재확인)

## 중간
- [정책] 삭제 페이지는 "답변과 참여 기록만" 부분 삭제를 약속하는데 계획의 RPC는 family/profile 전체뿐. `admin_delete_answers(profile)` 추가 또는 페이지 선택지 제거. 관리자 삭제 RPC는 `delete_my_account`(0008) 본문을 복사하지 말고 공통 내부 함수로 빼서 두 경로가 갈라지지 않게
- [보안] **Studio 원문 열람 위험: 조건부 허용.** 데이터가 A/B 선택·정해진 응원 키·호칭 20자라 민감도는 낮지만, Studio는 접근 기록이 남지 않는다. 조건: ① Supabase 조직 멤버 1명, 계정 MFA 필수 ② prod는 테이블 편집기 대신 집계 뷰·저장된 SQL 스니펫만 사용 ③ 개별 조회는 수기 대장(날짜·사유)에 기록 ④ 기간을 "관리자 웹 A 가동 또는 출시 후 8주" 중 빠른 쪽으로 못박기
- [보안] service role 스크립트(upload-photos 등)와 Studio SQL은 `aal2`·`admin_audit`를 **우회**한다. 관리자 쓰기는 사용자 JWT로 RPC를 부르게 하거나, 스크립트가 감사 행을 직접 남기게. "운영자도 삭제 불가"는 postgres/service role 앞에서는 거짓이니 "authenticated에 delete·update revoke + 변경 트리거"로 표현을 낮출 것
- [정책] `admin_audit` 보관: 안전성 확보조치 기준상 개인정보처리시스템 접속기록 **최소 1년**, 월 1회 점검. 보관 1년(파기 배치 대상에서 제외)으로 명시
- [보안] **Vercel Hobby 상업 이용 제한: 사실.** Vercel 이용약관 4절 "You shall only use the Services under a Hobby plan for your personal or non-commercial use."(vercel.com/legal/terms, 11-17 확인). 운영 백오피스는 상업 이용으로 보는 것이 안전하므로 배포 시 Pro(개발자 좌석 월 $20, docs/plans/hobby). 맥 로컬 실행은 Vercel과 무관해 제한 없음
