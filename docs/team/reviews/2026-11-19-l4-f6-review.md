## M (고칠 것)

### M1. 진짜 앱 ANR·크래시가 로그에 남지 않고, 창 닫기 루프가 우리 앱의 ANR도 'Wait'로 넘김
- run.sh:89-90, dismiss-system-dialogs.yaml:9-10(`.*responding.*` → `tapOn 'Wait'`)
- `hide_error_dialogs=1`은 시스템 프로세스뿐 아니라 모든 앱의 ANR·크래시 창을 막는다. 정규식도 "Process system isn't responding"와 "com.bumojasik… isn't responding"를 구분하지 않고, 둘 다 Wait 로 넘긴다. 거짓 통과 경로는 좁다(크래시면 화면이 사라져 이어지는 assert 가 실패). 그러나 ANR 이 한 번 났다가 회복되는 경우(앱이 느린 UI 스레드로 통과)는 보고서에 전혀 안 남는다. 느린 에뮬레이터 때문인지 앱 버그인지 구분이 안 된다.
- 방향: (a) 닫기 정규식을 시스템 것으로 좁힘(`.*Process system.*responding.*` 등). (b) run.sh 끝(또는 trap)에서 `adb logcat -d -b events,main | grep -E "ANR in com.bumojasik|FATAL EXCEPTION"` 를 보고서 옆에 저장하고, 우리 패키지의 ANR·크래시가 있으면 경고 또는 실패 처리. 시작 전 `adb logcat -c` 필요.
- 참고: README 가 "원인 1 = 시스템 ANR 창"이라 하는데, 5/5 통과가 hide_error_dialogs 때문인지 120초 루프 때문인지 분리되지 않았다. 둘이 겹쳐 있어 하나는 불필요할 수 있다(hide 켜면 창 자체가 안 뜨므로 dismiss 는 안전망 역할뿐).

### M3. 가장자리 3% 스와이프는 제스처 내비게이션 기기에서 동작이 불확실
- edge-scroll.yaml:9-13, dev-menu.yaml:6-12
- 3% ≈ 11dp(360dp 폭)는 Android 제스처 내비의 뒤로가기 영역(약 20~30dp)에 든다. 이 영역에서 시작한 수직 스와이프는 시스템이 가로채 스크롤이 안 되거나, 버전에 따라 뒤로가기로 처리될 수 있다. 5/5 통과는 gahwa_parent(아마 3버튼 내비) 한 대 기준이다. 실패하면 거짓 통과가 아니라 "앱 정보" 못 찾음으로 실패(안전한 쪽)지만 다른 AVD·실기기에서 깨진다. 또 "누를 것이 없는 자리"라는 주석은 사실이 아닐 수 있다(행은 전체 폭이라 가장자리에도 있다). 실제 수정 효과는 위치가 아니라 느린 속도(600ms)일 가능성이 크다.
- 방향: x 를 8~10%(뒤로가기 영역 밖)로 올리고 같은 조건으로 재검증, 또는 가장자리 근거를 빼고 "느리게 끌기"로 주석 정리. README 에 "3버튼 내비 AVD 전제"를 쓴다.

- L1. run.sh:89-98 — put(90)과 trap(98) 사이가 비어 있다(극히 짧음). trap 을 먼저 걸고 PREV 를 읽는 순서가 안전하다. 또한 `settings get` 이 실패해 PREV 가 빈 값이면 restore 가 `delete` 를 하는데, 그 기기에 원래 값이 있었다면 지워진다(`null` 문자열과 "읽기 실패"를 구분: 실패면 복원 생략).
- L2. run.sh:89-98 — 같은 기기에 두 실행이 겹치면 두 번째가 PREV=1(첫 실행이 켠 값)을 저장해, 첫 실행 종료 때 delete 한 뒤 두 번째 종료 때 1 로 되돌려 영구히 켜진 채 남는다. README 는 "감사관 등 다른 사용자 설정 보존"이라 주장하므로 동일 기기 동시 실행 금지(이미 ANDROID_SERIAL 분리 규칙 있음)를 한 줄 적으면 충분. kill -9·맥 종료 시에는 복원 불가(에뮬레이터 -read-only 면 종료 때 초기화됨).
- L3. trap 구조 — EXIT trap 은 `set -e` 실패, `fail`, Ctrl-C(SIGINT)·SIGTERM 에서 모두 실행되므로 요청 항목(실패·Ctrl-C·set -e 중단)은 충족한다. 기기 고정도 `ANDROID_SERIAL`을 export 한 뒤(61행)에만 settings 를 건드리므로 안전하다: 여러 대면 53행에서 멈추고, 지정 시 그 기기만 쓴다. 단 기존부터 있던 문제: Metro 를 띄운(80행) 뒤 85행 `fail`은 trap 설치(98) 전이라 Metro 가 남는다. cleanup+trap 을 80행 앞으로 옮기는 것이 좋다. 에뮬레이터를 직접 띄운 경우(45·57행) 종료 때 끄지 않는 것도 기존 동작.
- L4. wait-first-screen.yaml:7-17 — 앱이 크래시해 런처로 나간 경우에도 120초를 다 쓰고서야 실패한다(거짓 통과는 아님, 최종 `assertVisible` 이 막는다). 실패 지연일 뿐이다. 10초 단위 사이에 `appId` 포그라운드 확인이 어려우면 현재 구조도 허용 범위. 선택: 반복 사이 `assertNotVisible` 런처 문구 등은 불안정해 권장하지 않음. `repeat` 의 `times`+`while` 병용은 기존 파일에서 이미 쓰이던 형태라 문법상 문제는 아닌 것으로 본다(Maestro 2.12.1 실행 미확인).

### env.generated 변형 덮어쓰기 수정 (build.gradle:427-434)
`generate()` 호출처는 두 곳이다: 디버그 변형 `preBuild.doFirst`, 그리고 모든 변형의 `createBundle<변형>JsAndAssets.doFirst`. 새 가드는 `gradle.startParameter.taskNames` 에 4개 변형 이름 중 하나라도 있으면(named) 요청 문자열에 자기 변형 이름이 없는 변형의 쓰기를 건너뛴다.
- 출시 경로 `scripts/build-production.sh` (`bundleProductionRelease assembleProductionRelease`): named=true, `productionrelease` 포함 → productionRelease 번들 직전에 production 값 기록. 번들 직후 `cleanGeneratedAppEnv` 로 삭제(기존). 그래프에 끼는 다른 변형(디버그 라이브러리 의존)은 쓰기를 건너뜀 → 이전의 "나중 변형이 덮어씀" 제거. 출시값이 확실히 들어간다고 판단.
- `assembleStagingRelease` (build-staging.sh): 같은 논리로 staging 값. 문제 없음.
- 작업 이름이 비어 있거나 변형 이름이 없을 때(IDE 동기화, `assembleDebug`, `assembleProduction`, 카멜 약어, 플래그만): named=false → 예전 동작(모두 씀). 동기화는 doFirst 를 실행하지 않아 영향 없음. 릴리스 번들은 각자 자기 번들 직전에 쓰므로 이 경우에도 정확. 디버그만 "마지막이 이김"(기존 한계).
- 설정 캐시: gradle.properties 에 켜져 있지 않음(주석 처리된 기본값만). 켜면 실행 시점 `gradle.startParameter` 접근이 막힐 수 있음(L, 이미 doFirst 안의 `project.hasProperty` 도 같은 제약).
- 안전망: 번들 시 값이 없거나 BUILD_TYPE 이 release 가 아니면 `metro.release.config.js` 가 멈추고(fail-closed), `verifyReleaseBundle` 이 산출물을 검사한다. 건너뛰어서 값이 비는 쪽은 빌드 실패이지 잘못된 값 번들이 아님.

#### M-R1 (권고). 가드를 디버그 변형으로만 한정

- 릴리스 변형의 `generate()` 는 번들 직전 한 곳에서만 불리고 그 번들 작업 자체가 그래프에 있다는 것은 해당 변형이 실제로 빌드된다는 뜻이다. 그런데 `assembleProduction assembleStagingDebug` 처럼 일부만 변형 이름으로 적은 혼합 호출이면 named=true 가 돼 그래프에 있는 productionRelease 번들이 건너뛰어진다. 그때는 파일이 없거나 debug 값이라 `metro.release.config.js` 가 멈춰 빌드 실패(안전)하지만, 번들 순서·finalizer 시점에 따라 앞선 release 번들이 남긴 다른 flavor 값이 BUILD_TYPE=release 로 통과할 여지는 이론상 있다(게이트는 flavor 가 아닌 BUILD_TYPE 만 봄).
