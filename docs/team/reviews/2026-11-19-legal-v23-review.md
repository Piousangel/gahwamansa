# 법률 문서 v2.3 독립 리뷰 (커밋 5721349 ↔ 서버 0046·0047·0048)

> 리뷰어: 작성자와 다른 독립 리뷰(medium). 법률 자문 아님 — 문서 사실문과 마이그레이션 코드의 일치 여부만 본다.
> 대상: privacy.html v2.3, delete-account.html, internal-management-plan.md v0.3, data-safety-form.md, consent-exposure-map.md, CHANGES.md.
> 근거: `server-l1-launch`의 0026·0039·0042·0043·0046·0047·0048.

## 판정: 조건부 통과 (H 없음, M 4건 수정 후 게시)
사실문 대부분은 코드와 맞다(cascade·유일 제약·게시 버전만 기록·본인 최신만 조회·admin_* 전부 `admin_check_args` 경유·감사 1년 파기·열 grant). 어긋나는 곳은 "프로필 없는 계정의 삭제 경로", "서버가 막는다는 문장의 범위", "서비스 역할 읽기 불가"의 과장 소지, 운영 절차의 되돌릴 수 없는 등록이다. 자문 아님 표시는 5개 문서(방침·삭제 안내 HTML은 원래 해당 없음) 모두 유지, `{}` 깨짐 없음(`{…}` 자리표시는 모두 의도된 todo span).

## 확인한 일치 항목(문제 없음)
- terms_agreements: `auth.users on delete cascade`(0046), 같은 사용자·버전 쌍 유일(0048), 지난 버전 쌍 보관(삭제 없음), 시간 기준 파기 없음, 앱은 표 직접 접근 불가·`my_terms_status()`로 본인 최신만, 게시 안 된 버전은 `unknown_version`.
- 마지막 자녀 삭제 시 부모님 익명 계정 삭제(0026·0039 `is_anonymous`만) → 부모님 확인 기록도 cascade. 문장 일치.
- admin_audit 1년(0043 `at < now-1 year`), 허용 action 목록 일치(terms_publish 포함), 카카오 큐 30일(`gave_up_at` 또는 `enqueued_at` 기준 — 재시도해도 30일 상한 유지, "늦어도 30일" 일치).
- profiles 열 grant(0047) = 문서의 id·user_id·family_id·role·created_at·호칭. 푸시 금지어 목록·공백 제거 검사 일치, "유료" 서버 목록 없음을 map이 스스로 밝힘(정직함).

## M (수정 필요)
- **M1. 프로필 없는 계정은 삭제 경로가 없는데 문서는 "계정을 지울 때 바로 지움"이라 약속** — privacy 4절 확인 기록 행·delete-account 3절·internal §7·data-safety #8. 0046 주석대로 확인 기록은 프로필 생기기 전(role='none': 자녀 로그인 직후, 어르신 연결 화면)에도 쌓이는데, `delete_my_account`는 프로필 없으면 `no_profile`을 던지고 `admin_delete_account`·`account_delete_core`도 프로필 uuid 기준이라 이 계정은 앱·운영자 모두 못 지운다. 가입하다 그만둔 계정의 확인 기록·로그인 정보가 시간 파기 없이 남는다. 고칠 방향: (a) 서버: 프로필 없는 계정 삭제(또는 N일 미사용 정리) 경로를 L1에 요청, (b) 그 전까지 방침·삭제 안내에 "가족 연결 전에 그만두신 경우는 메일로 요청"을 넣고 P19류 게시 조건에 추가. role 값에 'none'이 있으므로 방침 "그때 부모님/자녀 중 어느 쪽"도 "…또는 아직 정해지지 않음" 반영.
- **M2. "서버가 메일 주소나 긴 숫자가 든 사유를 받지 않습니다"(privacy 4절)·"서버가 … 거부"(CHANGES)의 범위 과장 소지** — 코드는 `@` 포함 또는 연속 숫자 9자리 이상만 거부(`[0-9]{9,}`). `010-1234-5678`·`010 1234 5678`·이름·닉네임은 통과. 방침은 전화번호를 같은 문장에 묶어 읽혀 "전화번호도 막힌다"로 오해된다. 고칠 방향: 방침은 "서버가 메일 주소(@)나 길게 이어진 숫자가 든 사유는 받지 않고, 그 밖의 개인정보도 적지 않는 것을 운영 규칙으로 합니다"로 분리. 내부관리계획 §6에 "하이픈·공백으로 끊은 번호는 서버가 못 거름" 한 줄.
- **M3. "큐 회원번호는 서비스 역할도 못 읽음"(data-safety #2) 과장** — 0047은 표 `select`만 회수했다. Edge Function이 쓰는 `kakao_unlink_claim`은 definer로 `kakao_user_id`를 서비스 역할에 돌려준다(해제에 필요). internal §4-5는 "직접"이 붙어 맞지만 data-safety는 빠졌다. 고칠 방향: "표를 직접 읽지는 못하고 해제 함수로만 받는다"로 통일.
- **M4. 방침 11절 "이용자 정보를 지우거나 고치는 운영자 작업은 기록이 남는 정해진 방법으로만 합니다"** — 서버가 강제하는 것은 service_role의 쓰기 회수까지이고, Studio SQL(postgres)·대시보드 직접 편집은 막히지 않는다(내부관리계획도 "금지"라는 규칙으로만 둠). 약속형 문장이 코드 보장보다 세다. 고칠 방향: "…방법으로만 하도록 정해 두었고, 접속 대장으로 점검합니다"처럼 규칙·점검으로 표현, 또는 이 문장 삭제.
- **M5. 약관 버전 등록은 되돌릴 수 없는데 절차에 확인 단계가 없음**(internal §6 약관·방침 게시 기록) — 최신 = published_at 최대, 삭제·수정 함수 없음. 오타로 `v9`를 등록하면 모든 사용자 `needs_reagree=true`가 마이그레이션 전까지 고정된다. 고칠 방향: 등록 전 "버전 문자열 두 번 대조(게시본 머리 = 앱 상수)" 체크와 "잘못 등록 시 L1에 보정 마이그레이션 요청" 절을 추가. 또 "등록 → 게시 → 앱" 순서에서 등록 직후 앱이 상태를 보면 게시 전에 재동의가 뜰 수 있으니 앱 상수 배포와 같은 날로 묶기.

## L (다듬기)
- **L1. 내부관리계획 §6·§7 문장 위치 깨짐** — "요청 번호↔메일 대응은 문의 메일함의 삭제 요청 대장에만…" 문장이 약관 게시 기록 불릿 끝으로 옮겨졌고(원래 감사 규칙 불릿 끝), §7 "production 첫 실행 성공을 G-INT 전에 확인"은 '자동' 불릿에서 '계정 삭제와 함께' 불릿 끝으로 옮겨졌다. 각각 원래 불릿으로 복원.
- **L2. 방침 1절 28행 "카카오 연결 끊기·처리 기록 예외는 4절"** — 4절 행 이름이 "운영자 작업 기록"으로 바뀌었으니 "작업 기록"으로 맞춘다.
- **L3. 어르신 눈높이** — 4절 운영자 작업 기록 행 첫 칸이 괄호 두 겹으로 길고, "무작위 식별 번호"·"서버가 … 사유를 받지 않습니다"는 설명 없이 쓰임("사유"·"서버"). 2절 확인 기록 "그때 부모님/자녀 중 어느 쪽으로 쓰셨는지"도 어색(→ "부모님으로 쓰셨는지, 자녀로 쓰셨는지"). 4절 "부모님 기록은 마지막 자녀가 계정을 지울 때도 함께 지웁니다"는 "가족 마지막 자녀가 지우면 부모님 쪽 기록도 함께 지워집니다"가 쉽다.
- **L4. 용어 불일치** — 방침·삭제 안내 "운영자 작업 기록" / 내부관리계획·data-safety #18 "관리자 감사 기록(admin_audit)" / 방침 11절 "관리 화면 접속 기록". 내부 문서에 "(방침 표기: 운영자 작업 기록)" 병기.
- **L5. 내부관리계획 §2 "대상은 무작위 uuid 또는 큐 번호만"** — `terms_publish`의 detail은 종류·버전이다. "또는 약관 종류·버전" 추가(data-safety #18은 이미 포함).
- **L6. data-safety #18 근거 번호에 0040(content_publish·retire)·0044 누락**, 내부관리계획 §4-2 RPC 목록에도 콘텐츠 게시 RPC 없음(전부 `admin_check_args` 경유이므로 "모든 admin_* RPC"로 통칭 권장).
