## M
1. **info 규칙 충돌.** colorRules는 "옅은 면(…infoSoft…) 위 글자는 inkTitle·inkBody만, info는 paper·card 위에서만"이라 하지만, SUMMARY·colorRoles는 info를 infoSoft 안내 띠의 글자로 정의하고 contrast.text에도 `info on infoSoft 7.35`가 허용 조합으로 있다(통과 값). 하나로 정리: infoSoft 위 info 글자는 허용(7.35)하고 규칙문에서 예외로 명시, 또는 허용 목록에서 제거.
2. **금지 조합 목록(contrast.forbidden)이 불완전·기준 불명.** 6건뿐이고 '확인용'이라 테스트가 못 쓴다. 재계산상 어르신 7 미달인 inkSub on noticeSoft(6.81), inkSub on sky(6.62), action on paperSoft·noticeSoft·actionSoft·infoSoft·sky(6.03~6.63), accent on paperSoft·noticeSoft·infoSoft·sky(6.49~6.90), dangerInk 옅은 면 전부가 목록에 없다. 목록 대신 **허용 목록(역할×면 화이트리스트) + 테스트는 허용 조합만 통과**로 바꾸면 누락이 안 생긴다. 이 항목에 BackLink 변경 이유(SUMMARY와 다름)도 SUMMARY에 정정 기록 필요.
3. **RULES-V4.md가 검사 가능한 문장이 아님.** 키 안내 표 + 변경 사유 + 검증 요약이라 규칙 자체가 없고, 규칙 문장은 JSON 문자열 안에 흩어져 있다. 일부는 토큰 테스트로 되나(대비·비율 1.2·minHeight) 다음은 검사 방법이 없다: "누를 것은 면·밑줄·아이콘 중 하나 동반", "accent 화면당 1곳", "danger와 accent 같은 화면 금지", "700 역할 화면당 2개 이하", "헥스·숫자 크기 직접 지정 금지". 각 규칙을 `R-번호 | 문장 | 검사(토큰 테스트 / eslint 규칙 / 화면 렌더 테스트 / 사람 검토) | 대상`의 표로 쓰고, 직접 지정 금지는 eslint(no-restricted-syntax로 hex·fontSize 숫자·fontWeight 숫자 리터럴), accent·danger는 화면 렌더 테스트로 명시할 것.

## L
1. 중복·이름: `color.ink`와 `color.action`이 같은 #744821(값 중복). ink는 폐기 별칭이므로 `color`에서 빼고 `v3Aliases`로 이동해 생성물에서 v3 이름이 섞이지 않게. `v3Aliases.inkSub`는 "값 교체됨"이라 별칭이 아님(삭제 가능).
2. 역할 누락·표기: `onAction`(흰 글자, typeRoles.button tone)이 color에 토큰으로 없음(흰 #FFFFFF 직접). `disabledInk` 5.29만 있고 danger/accent 규칙문 "대비 1.02"는 dangerInk 기준(danger 값은 1.26) — 어느 토큰인지 명시. contrast.text에 `action on card` 행이 2번 중복.
3. RULES-V4 '검증' 절의 "28건"은 text만의 건수이고 nonText 6건은 별도(34건). 문구 정리. 인접 크기 비율 예외(22/20 1.10, 26/22 1.18)는 보완 쌍 목록을 tests에 이름으로 박아 둘 것(목록 없이는 테스트가 예외를 못 앎).
4. 구조: 최상위 키 29개(color, colorRoles, typeRoles, components 등)에 role 설명이 한글 문장이라 코드 생성 때 파싱이 약함. 생성 대상(color·typeRoles·touch·dock·backLink)은 값만 필드로, 설명은 별도 `note`로 분리 권장.
