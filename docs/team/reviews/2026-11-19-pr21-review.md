## 중간

**M1. 보충값에 `supplemented: true`가 붙지만 아무도 읽지 않는다. 근거 없는 numeral 자녀 28/38이 원본 값과 같은 모양으로 화면에 나간다**
- 위치: `scripts/gen-tokens-v4.js:21-25`, `:91` / 생성물 `tokensV4.ts`의 `type.numeral`·`type.hand` / #29 `ui/ds/roles.ts:9`(`TextRole`에 `numeral`·`hand`·`label` 포함)
- 근거: 원본 `typeRoles.label/numeral/hand`에는 note 문장만 있다. 근거별로 나누면 다음과 같다.
  - 근거 있음: label 20/30·16/24(note에 그대로 있음), numeral 어르신 34/46(note 34 + 줄높이 규칙 '32 이상 +12'), hand 어르신 32/44.
  - 근거 없음:
    - **numeral 자녀 28/38**: 원본에 자녀 값이 없다.
    - **hand 자녀 32/44**
    - **hand 상한 1.5**: R-11은 본문 2.0, '큰 제목·Dock·번호' 1.5라고만 정하고 손글씨는 정하지 않았다.
    - **label 상한 2.0**
  - `supplemented`는 역할 단위 boolean 하나라서 어느 칸이 보충값인지 알 수 없다. `grep -rn supplemented app/src`도 0건이다(생성물만 있음). #29에서는 화면이 `<Text role="numeral">`을 자녀 화면에서 바로 쓸 수 있다.
- 영향: 디자인이 정하지 않은 자녀 번호 칸 28이 '토큰'으로 굳는다. 원본에 값이 생기면 원본이 이기지만, 그 전에 화면 레인이 쓰기 시작하면 값이 바뀔 때 시각 회귀가 생긴다. PR 본문은 "디자인 확인이 필요합니다"라고 적었지만, 코드에는 이를 막는 장치가 없다.
- 고칠 방향(둘 중 하나):
  - (a) 근거 없는 칸은 생성하지 않는다. 예를 들어 `numeral.child`가 없으면 자녀 Text가 dev 경고와 함께 `bodyLg`로 대체하거나, `TextRole`을 audience별로 좁힌다.
  - (b) `supplemented`를 칸 단위로 바꾼다. 예: `supplemented: ['child', 'maxFontScale']`. 테스트에 "보충 칸 목록 = 알려진 대기 목록"을 고정해서, 디자인이 원본에 값을 넣으면 목록을 줄이도록 강제한다.
  - 어느 쪽이든 RULES-V4 '열린 항목'에 "numeral 자녀·hand 상한은 디자인 확인 대기" 줄을 디자인 레인에 요청한다.

### M1 후속: main(디자인 PR #35)이 원본을 확정했다. 다시 생성하면 해소된다
- main의 `tokens-v4.json`에 `typeRoles.label/numeral/hand`의 `elder`·`child`·`weight`·`maxFontScale` 숫자 필드가 생겼다.
  - label: 20/30·16/24, 상한 2.0
  - numeral: 34/46·**자녀 30/40**(C0-c 인증번호 칸 시안 값), 상한 1.5
  - hand: 32/44(자녀는 "쓰지 않음, 값만 같게"), 400, 상한 1.5
- 이 브랜치 생성기의 `build()`로 main 원본을 생성해 보았다(파일은 쓰지 않음). 세 역할 모두 `supplemented: false`가 되고, numeral 자녀는 **28/38 → 30/40**으로 바뀐다. 생성기의 우선순위(원본 값 > SUPPLEMENT)가 의도대로 동작한다.
- 그러니 **M1은 main을 병합하고 `node scripts/gen-tokens-v4.js`를 다시 돌리면 해소된다.** 단, 이 브랜치에 main만 병합하고 생성을 빼먹으면 지금 생성물과 달라서 `--check`와 `tokensV4.test`가 실패한다. 실패하는 것이 맞는 동작이고, 생성 커밋을 하나 더하면 된다.
- 남는 정리(L):
  - `SUPPLEMENT` 표와 `supplemented` 필드는 이제 아무도 쓰지 않는다(빈 칸이 없음). 표를 지우고, 원본에 숫자가 없으면 `throw`하는 편이 L1과 같은 방향이다.
  - numeral 자녀 값이 바뀌므로 #29 화면 적용 전에 시각 확인 대상에 넣는다(지금 쓰는 화면은 0곳).

## 낮음

**L1. 생성기가 원본이 빠지거나 문장이 바뀌면 조용히 기본값을 쓴다** — `gen-tokens-v4.js` 해당 위치는 다음과 같다.
- `:68` `weight ?? 400`·`maxFontScale ?? 2`
- `:67` tone 기본 `inkBody`
- `:169` `bottomMin: 28` 고정. 원본은 문장 `"max(28, insets.bottom)"`이고 생성기가 이를 읽지 않는다.
- `:171` `socialGroup?.maxItems ?? 1`
- `:180` surface가 `/^card/`가 아니면 `'paperSoft'`. 원본 문장이 "흰 card…"로 바뀌기만 해도 이렇게 된다.
- `:181` 테두리 두께를 못 읽으면 1.5

surface와 socialGroupMax는 테스트가 잡지만 나머지는 잡지 않는다. 원본에 숫자 필드가 없는 경우에만 보충하고, 문장 파싱이 실패하면 `throw`하는 편이 '원본이 이긴다' 원칙에 맞다.

**L2. 단독 prettier가 생성물을 다르게 포맷한다** — `npx prettier --check src/ui/tokensV4.ts`가 실패한다. `.prettierrc`에는 `bracketSpacing`이 없어 `{ ink: 'action' }`처럼 바꾸고, 긴 meta 줄도 나눈다. eslint는 통과한다. 편집기에서 저장할 때 포맷하면 생성물이 바뀌고 `--check`·jest가 깨진다. `app/.prettierignore`에 `src/ui/tokensV4.ts`를 넣는다(생성물 머리 주석과 같은 뜻).

**L3. numeral '번호 칸 68'이 생성물에 없다** — 원본 note "어르신 34(번호 칸 68)"의 68은 버려진다. 번호 칸 컴포넌트를 만들 때 다시 숫자를 손으로 쓰게 된다. 지금 쓰는 곳은 없다.

**L4. 대비 테스트는 tone×면 짝만 보고, 역할 기본 tone은 paper·card만 확인한다** — `tokensV4.test.ts:66-85`. 옅은 면 위에서 어떤 컴포넌트가 어떤 짝을 쓰는지는 #29의 몫이다. #29 리뷰 M2(Banner 행동 링크)가 실제로 여기서 새는 사례다.

**L5. `text20SizeToRole[24]`가 `heading` 하나로 묶인다** — 24는 섹션 제목·뒤로 링크·말풍선 세 쓰임이 섞여 있다. note에 적혀 있지만 기계적으로 옮기면 말풍선이 700이 된다(R-04 '본문 bold 금지'). 화면 레인 이행 가이드에서 24는 "note 필독"으로 표시하길 권한다.

## 좋았던 점
- 대비를 원본 숫자가 아니라 현재 색 값으로 다시 계산해서, 원본 값이 바뀌어도 테스트를 고칠 필요가 없다.
- 보완 쌍을 손 예외가 아니라 원본 목록 이름으로만 허용한다(R-05·R-20을 기계로 강제).
- v3 값을 건드리지 않고 별칭·@deprecated로만 이행해서 기존 화면 회귀 위험이 0이다.
