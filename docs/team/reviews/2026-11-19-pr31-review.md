## 중간

**M1. 예산 테스트가 C0 로그인을 intro 0.6으로 재서, 원래 버그(B1, 하단 과적) 모양을 통과시킨다**
- 위치: `__tests__/dsDockBudget.test.ts:25-34`(`variant: 'intro'`), `:79`(`INTRO_DOCK_RATIO`)
- 근거: 같은 `planDock`으로 다시 쟀다(임시 테스트, 지움).
  - 320×640·200%에서 C0 Dock(카카오·구글 + 이메일 링크)은 **372dp**다. 0.6 상한은 384라 spill 0으로 통과한다. 즉 화면 높이의 58%가 하단에 고정된다.
  - 0.4로 재면 이메일 링크가 본문으로 가서 240/256으로 들어간다. 0.4로 바꿔도 테스트는 계속 통과한다.
  - RULES R-12 단서: "로그인 화면은 주 슬롯 안에 SocialGroup… **그룹이 들어가도 Dock ≤ 40%**, 넘치면 보조 링크가 본문으로"(`dock.socialGroup.heightLimit`).
- 영향: 이 테스트는 "새 문구·새 슬롯이 상한을 깨는 것을 PR에서 막는다"가 목적이다. 그런데 사례가 B1(카카오 버튼 잘림)을 일으킨 구성을 허용한다. #29의 DsScreen도 variant만 보고 0.6을 써서 런타임에서도 같다(#29 M4).
- 고칠 방향: SocialGroup 사례는 상한 0.4로 잰다. `planDock` 호출 때 `isSocialGroup(c.dock.primary) ? undefined : INTRO…`. #29 DsScreen에도 같은 규칙을 넣는다. intro 40% 예외가 C0에도 적용되는지가 디자인 판단이면, 확인 전까지는 R-12(더 엄격한 쪽)를 따른다.

**M2. 화면이 `ellipsisException`을 써도 lint·기준선 어디에도 걸리지 않는다 → R-10 "예외는 ui/ 안에서만"이 강제되지 않는다**
- 위치: `.eslintrc.js` DS_SYNTAX(`numberOfLines` JSX 속성만), #29 `ui/ds/Text.tsx:18-22`(주석 "위반 수는 dsBaseline 테스트가 센다")
- 근거: features/에서 `<Text role="body" ellipsisException={{lines: 1, reason: 'wordCell'}}>`를 쓰면 tsc는 통과하고(#29 probe), DS_SYNTAX에는 해당 selector가 없다. 그래서 `numberOfLines` 금지를 이름만 바꿔 우회할 수 있다. 기준선 표에도 이 종류가 없다.
- 고칠 방향: `{selector: "JSXAttribute[name.name='ellipsisException']", message: '[DS:ellipsis] …ui/ 컴포넌트 안에서만'}`을 더하고 기준선에 `ellipsis: 0`을 둔다. R-10은 `ellipsizeMode`도 lint 대상으로 적었는데 빠져 있으니 같은 규칙에 넣는다(지금 0건).

**M3. R-03 우회 경로가 열려 있다: `Touchable*`·`Animated.Text`·namespace import**
- 위치: `.eslintrc.js:25-30`(`importNames: ['Text', 'TextInput', 'Pressable']`)
- 근거: RN의 `TouchableOpacity`·`TouchableHighlight`·`TouchableWithoutFeedback`(Pressable 대체), `Animated.Text`, `import * as RN from 'react-native'` → `<RN.Text>`는 잡히지 않는다. 지금 features/·app/에는 0건(grep)이라 기준선에 영향은 없다. 하지만 Button·Choice를 피해 직접 누르는 것을 만드는 가장 쉬운 길이다.
- 고칠 방향: `importNames`에 Touchable 3종을 더한다. `no-restricted-syntax`에 `JSXMemberExpression[object.name='Animated'][property.name='Text']`와 `ImportNamespaceSpecifier` (react-native)를 더한다. 모두 0건이라 기준선 0으로 시작할 수 있다.

## 낮음

**L1. `[DS:height]` 12건 중 적어도 9건은 글자 상자가 아니다** — 이미지(`HistoryScreen.tsx:124`·`KeyboardStep.tsx:346`), 원·도장(`StampRow.tsx:79·82`·`RoleSelect.tsx:202`·`ParentFamilyScreen.tsx:195`), 테이프 장식(`ChildHome.tsx:177`) 등이다. R-09는 "글자 상자에" height 금지다. AU-10에서 error로 올리면 오탐이 9건 이상 나오므로, 그 전에 `width` 숫자와 함께 쓴 정사각·이미지 스타일은 제외하거나 해당 줄에 `eslint-disable-next-line` + 이유를 붙이는 규칙을 정한다. 지금은 warn + 기준선이라 수만 고정된다.

**L2. 적용 범위 밖 화면이 있다** — `src/push/PushPermissionScreen.tsx`(N1 화면)에 `Text20 size=` 4건이 있지만 `features/`·`app/` 밖이라 세지 않는다. `src/dev/DevMenuHost.tsx`도 마찬가지인데 이쪽은 개발용이라 무방하다. SUMMARY 문구("features/·app/ 경로")대로이긴 하나, push/는 화면 계층이니 범위에 더하거나 ARCHITECTURE에 예외로 적는다.

**L3. 예산 사례는 '예정 구성'이라 실제 화면과 묶이지 않는다** — '사례 누락' 테스트는 파일 이름만 확인한다(`/<DsScreen[\s\S]*?\bdock=/`). 화면이 사례와 다른 슬롯·문구를 써도 통과한다. 화면 적용 PR에서 사례의 `dock` 객체를 화면 파일과 공유하게 하면(예: 화면 파일이 `export const dockFor = (t) => …`를 내보내고 테스트가 그것을 쓴다) 추정이 실제 구성을 따라간다. 추정 자체의 한계(한글 1em 근사, insets.bottom 무시: #29 L3)는 PR 본문에 적혀 있다.

**L4. 색 lint는 JSX 속성 색을 보지 않는다** — `<Icon color="#…">`, Svg `stroke`·`fill` 리터럴은 `Property` selector 밖이다. 지금 `[DS:color]`이 0건인 이유 중 일부일 수 있다. `JSXAttribute[name.name=/^(color|stroke|fill)$/][value.type='Literal']`을 더한다.

**L5. `Text20 weight="bold"`는 세지 않는다** — 단조로움 진단 A2(bold 약 50%)의 주 원인이지만 lint 대상에 없다(SUMMARY 목록에도 없음). `size`와 함께 이행되니 당장은 문제가 없다. 다만 화면을 옮긴 뒤 다시 bold를 쓰는 것은 Text20을 막는 2단계에서만 잡힌다.

**L6. 전체 lint를 jest 안에서 두 번 돈다** — `dsBaseline`과 `layerBaseline`이 각각 `lintFiles(['src/**'])`를 돈다. 부하가 큰 맥에서 스위트 하나가 수십 초 걸린다. 공용 helper로 결과를 한 번만 만들거나(같은 워커에서 모듈 캐시), 한 테스트 파일로 합친다.

## 좋았던 점
- 메시지 앞머리 `[DS:종류]`로 기준선 키를 뽑아서, 규칙을 더하면 기준선이 자동으로 실패한다(빠뜨릴 수 없음).
- override 병합 함정(같은 규칙 옵션이 덮임)을 `paths`로 합쳐서 피했고, 레이어 기준선과 섞이지 않게 분리했다.
- 예산 테스트에 "과적하면 실패한다" 장치 확인 사례가 있다.
