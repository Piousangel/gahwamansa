# PR #44 리뷰 — staging 빌드에 production 검사가 끌려오던 것 (932ba2b) · 2026-11-19

리뷰어: 독립 리뷰어(작성자 아님). 판정: **조건부 통과(M 1 수정 권고)**. H 0 · M 1 · L 2.

## 검증(`./gradlew --offline <작업> --dry-run`, JDK17·로컬 SDK, 작업 그래프만 확인)
| 요청 | 결과 |
|---|---|
| assembleStagingRelease | verifyOssLicenses 없음, preStagingReleaseBuild·createBundleStagingRelease 있음. preProductionReleaseBuild 는 그래프에 끼지만 요청 변형이 아니라 doFirst 가 즉시 반환(의도) |
| assembleProductionRelease | preProductionReleaseBuild(예시 값·앱 정보 검사) + verifyOssLicenses + createBundleProductionRelease 모두 있음 |
| bundleProductionRelease | 위와 동일 |
| assembleRelease(집계) | named=false → 두 변형 모두 요청으로 취급, 검사 둘 다 실행, verifyOssLicenses 포함 |
| installProductionRelease / packageProductionRelease | **verifyOssLicenses 없음** (아래 M1) |

## 확인
- production release 경로: env 게이트(checkPlaceholder)·앱 정보 게이트(checkAppInfo)는 `variantRequested` 가 참이면 그대로 실행 — 작업 이름에 `productionrelease` 가 있거나 변형 이름이 없는 집계(assembleRelease)에서 빠지지 않음. release 번들 직전 generate 도 유지.
- 작업 이름이 없을 때(IDE 동기화): `taskNames` 가 비어 `named=false` → `variantRequested` 가 모든 변형에서 참 = 이전 동작과 같음. 동기화는 작업을 실행하지 않으므로 doFirst 도 안 돎. Android Studio 실행 버튼은 `:app:assembleStagingDebug` 등 이름을 넘겨 named 경로.
- `contains` 일치는 `assembleStagingRelease` 에 `stagingdebug` 가 없어 정확. 구성 시점 평가라 doFirst 안에서 gradle 객체를 읽지 않음(구성 캐시 안전).

## 지적
- **M1** verifyOssLicenses 가 `assembleProductionRelease`·`bundleProductionRelease` 에만 걸림. 이전에는 preProductionReleaseBuild 의존이라 `installProductionRelease`·`packageProductionRelease`·`lintVitalProductionRelease` 등 production release 의 모든 경로에서 돌았음 → 이 경로들에서 OSS 검증이 빠짐(dry-run 확인). 출시 산출은 bundle 이라 실제 위험은 낮으나 "빠짐 0" 기준엔 구멍. 권고: `createBundleProductionReleaseJsAndAssets`(install·package·assemble·bundle 그래프에 모두 포함됨, 위 dry-run) 에 `dependsOn("verifyOssLicenses")`. staging 번들 작업과 이름이 달라 INF-1 해소와 양립.
- **L1** `requested` 가 문자열 포함 검사라 `-x` 제외나 카멜 약어(`aPR`)는 못 봄. 지금 호출 형태엔 영향 없음.
- **L2** `assembleDebug`(이름 없음)는 두 flavor 의 generate 가 모두 돌아 나중 쪽이 env.generated.ts 를 덮음 — 기존 한계(악화 아님). "debug 는 flavor 이름을 붙여 호출"을 문서에 남길 만함.
