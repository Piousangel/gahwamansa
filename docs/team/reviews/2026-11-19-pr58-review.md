## 판정: **합치기 가능** (높음 0 / 중간 0 / 낮음 2)

| 중점 | 결과 | 근거 |
|---|---|---|
| 전역 useRealTimers가 beforeAll·describe 단위 가짜 시계를 깨는가 | 깨지 않음(그런 파일 없음) | `useFakeTimers`를 쓰는 16개 파일을 grep으로 모두 확인했다. 모두 **테스트 안**이거나 `beforeEach` 안에서 켠다(u0Banner·u0Toast는 beforeEach에서 켜고 자기 afterEach에서 끈다). `beforeAll`은 eventsContract 하나뿐이고 시계와 상관없다. describe 본문이나 파일 최상위에서 켜 두는 곳도 없다. afterEach 안에서 `runOnlyPendingTimers`·`advanceTimers` 같은 가짜 시계 API를 부르는 곳도 0건이다. jest-circus 순서상 전역 afterEach가 파일 최상위 afterEach보다 먼저 돌 수 있지만, 그런 의존이 없어 영향이 없다. RNTL 자동 정리(언마운트)가 실제 시계로 돌아도 남은 가짜 타이머는 버려질 뿐이다 |
| 가짜 시계로 바꾼 뒤에도 '취소' 시간을 실제로 검증하는가 | 검증함(상한은 이전과 같음, L1) | ① 시간 값은 `cheerUndoMs(false,1)=4000`, 화면 읽기·200% = 6000 단위 테스트가 그대로 있다. ② '리뷰 M2' 테스트: 고른 직후 `취소`가 켜져 있고 → `advanceTimersByTime(4050)` → 그때 한 번 보내고 '취소'는 비활성이다. ③ '취소' 테스트: 4200ms 넘겨도 보내지 않는다. ④ 백그라운드 테스트(실제 시계)는 고른 직후 `send` 미호출을 단언한다. 실제 대기를 가짜 시계 앞당기기로 1:1로 바꿨을 뿐이라 단언의 강도는 그대로다 |
| 기타 | 맞음 | 가짜 시계는 render 전(테스트 맨 앞)에 켠다. RNTL `waitFor`는 jest 가짜 시계를 알아서 앞당긴다. 테스트 끝의 `jest.useRealTimers()`는 이제 전역과 겹치지만 해가 없다 |

## 낮음
- **L1. '취소' 시간의 아래쪽 경계는 확인하지 않는다(이전부터)** — 4050ms에 보냈는지만 보고, 4000ms보다 **일찍** 보내지 않는지는 보지 않는다. 예를 들어 1초 만에 보내도 '리뷰 M2' 테스트가 통과한다. 이번 변경으로 약해진 것은 아니다. 가짜 시계라 이제 비용 없이 넣을 수 있다: `advanceTimersByTime(3950)` → `expect(send).not.toHaveBeenCalled()` → `advanceTimersByTime(100)` → 1회. 200%·화면 읽기의 6초 경계도 같은 식으로 한 번 두면 `cheerUndoMs`와 실제 타이머가 연결돼 있는지까지 확인된다.
- **L2. 테스트 안의 `jest.useRealTimers()`는 실패하면 실행되지 않는다** — 이제 전역 afterEach가 대신하므로 그대로 둬도 되지만, 두 가지가 섞여 있어 다음 작성자가 헷갈릴 수 있다. 전역으로 통일했다는 한 줄을 jest.after.js 주석에 이미 적었으니, 테스트 안 줄은 지워도 된다(선택).
