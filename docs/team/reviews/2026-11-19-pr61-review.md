## 확인한 것(요청 항목별)

### 1. 이벤트 속성에 개인정보·내용이 들어가는가: 들어가지 않는다

새로 보내는 이벤트와 속성은 아래가 전부다.

| 이벤트 | 속성 |
|---|---|
| `app_first_open` | `role_guess`, `install_source`(`referrer`·`applink`만) |
| `child_signup_completed` | `login_method` |
| `invite_code_issued` | `purpose` |
| `invite_share_tapped` | `channel` |
| `consent_shown` / `parent_consent_accepted` / `parent_consent_declined` | `consent_version`(accepted만) |
| `consent_revoked` | 없음 |
| `cheer_sent` | `message_key`(받는 분·수 없음) |
| `child_report_viewed` | 없음 |
| `child_first_answer_viewed` | `days_since_connect`(숫자) |
| `course_step_started` | `step`, `day_index` |
| `course_step_completed`(P6) | `attempt_no`, `result`(`finished`·`skipped`) |

- 답 내용, 낱말, 호칭, 번호, 날짜 문자열은 싣지 않는다. P6은 "맞았는지"를 싣지 않고, "다 썼어요"와 "이대로 마칠게요"를 모두 `finished`로 묶는다.
- 서버 `event_prop_ok`가 키별 값 목록으로 다시 막는다. pgTAP에 `{"word":"엄마"}` 거부와 `result:"wrong"` 거부가 있다.

### 2. 세션 전 보관 큐가 계정 전환·삭제 때 섞이는가: 지금 경로에서는 섞이지 않는다

- `realApi`의 `waiting`은 메모리에 있고(앱을 다시 켜면 사라짐), 최대 4개다. 세션이 생기면 그 세션으로 보낸다.
- 세션 없이 발생하는 이벤트는 현재 `app_first_open` 하나다. 역할 고르기 화면에서 나고, 기기당 1회(`trackOnce`)다. 그 뒤 그 기기에서 처음 생기는 세션(자녀 로그인 또는 어르신 익명)으로 간다. 의도와 같다.
- 삭제나 로그아웃 뒤 세션 없는 화면(DeleteDone·Login·Connect)에서 track을 부르는 곳은 없다(diff 기준). 그래서 A의 이벤트가 B 계정으로 가는 경로는 지금 없다.
- 다만 `waiting`이 계정 경계를 모른다. 앞으로 세션 없는 화면에 이벤트가 붙으면 섞일 수 있다(L1).
- `trackOnce` 표시(`pref_evt_once_*`)는 기기 단위이고 `accountTag`에 묶이지 않는다. 계정 삭제 정리(`clearAccountKeys`)에서 지워지지 않는다. `app_first_open`은 기기 단위가 맞다. `child_first_answer_viewed`는 아래 L2.

### 3. 중복 발신: 대체로 막혀 있다

- `trackOnce`: 표시를 먼저 남기고 보낸다. 같은 틱 두 번 호출은 `inflight`가 막는다.
- `course_step_completed`: 서버가 기록을 인정한 뒤 한 번 보낸다. 버튼은 `useBusyLatch`로 막는다.
- `course_step_started`: 화면 마운트당 한 번(`sent` ref)이다. 진행 모드에서만 보내고, 이미 마친 단계는 보내지 않는다. 같은 단계 화면에 다시 들어오면(뒤로 갔다 오기, 앱을 껐다 켜기) 다시 보낸다(L3).
- `consent_shown`: 이미 동의해 건너뛴 경우는 세지 않는다.
- `invite_code_issued`: 새로 받은 때만 보낸다.

### 4. 서버 허용 목록과 eventsContract: 일치한다

- 0053의 `event_prop_ok`·`log_event`를 직전 정의(0034)와 diff하면, `result`에 `finished` 추가와 이름 `course_step_started` 추가 두 줄뿐이다.
- 앱 계약 `EVENT_NAMES`·`EVENT_PROP_VALUES.result`에도 같은 값이 들어갔다. `eventsContract.test.ts`(최신 정의 파일을 읽어 비교)가 통과한다.

### 5. 0053 pgTAP와 번호 순서

- pgTAP 8건: 시작 이벤트 기록, 목록 밖 `step`·`result`, 글자 키 거부, 기존 `result` 값 유지, anon 거부.
- **번호 순서**: 이 브랜치에는 0052가 없다(브랜치를 만든 뒤 main에 병합됨). 그래서 replay를 두 번 했다.
  - 브랜치 그대로(0051 → 0053): PASS.
  - main을 로컬에서 합친 상태(0052 → 0053, push하지 않음): PASS.
  - 0052는 `log_event`·`event_prop_ok`를 건드리지 않아 충돌이 없다.

## 서버 레인으로 넘길 의견: `account_deleted`

- 앱은 `account_deleted`를 보내지 않는다(삭제 뒤에는 세션이 없고, 삭제 전에 보내면 실패한 삭제도 세게 된다).
- 서버 삭제 함수(`account_delete_core`·`user_delete_core`)가 같은 트랜잭션 안에서 `events`에 직접 한 줄을 넣는 편이 정확하다. 이때 지킬 것:
  - `profile_id`·`family_id`는 null로 둔다. 곧 지워지고 cascade로 함께 사라지므로, 남기려면 null이어야 한다.
  - `actor_role`과 `props {scope}` 정도만 남긴다. `scope` 값 목록(`child|parent|family|none`)을 `event_prop_ok`에 추가해야 한다.
  - `device_key`는 지워진 계정과 연결되지 않게 고정값 또는 null로 둔다.
  - 운영자 삭제(`admin_delete_*`)와 본인 삭제를 구분하려면 `source` 같은 키를 하나 더 둔다.
- 하루 200개 상한과 `no_user` 검사는 `log_event`의 규칙이다. 서버가 직접 넣으면 적용되지 않는다(괜찮음).
