| 중점 | 결과 | 근거 |
|---|---|---|
| 가짜 시계로 바꾼 뒤에도 '마칠게요' 잠금 시간을 검증하는가 | **잠금이 있는지는 검증한다. 길이(1.5초)는 검증하지 않는다(전과 같음, L1)** | 일치 직후 `마칠게요`가 `toBeDisabled()`이고, 그 뒤 `waitFor`가 켜짐을 기다린다. 가짜 시계에서는 RNTL `waitFor`가 시계를 조금씩 앞당겨, 잠금이 0보다 크고 대기 한도(가짜 시간 10초)보다 작으면 무엇이든 통과한다. 예전 실제 대기 판(`{timeout: 6000}`)도 0~6초면 통과해서 길이를 보지 않았으니 이번에 약해진 것은 아니다. 다만 가짜 시계라 이제 정확한 경계를 공짜로 볼 수 있다. 포커스 이동 테스트('알림 1회 뒤 마칠게요로 포커스')도 같다 — 바로 옮기지 않음(false)은 보고, 언제 옮기는지는 보지 않는다 |
| 응원 4초 | 1차와 같은 방식 | `ac05Events` cheer_sent: 4300ms를 앞당긴 뒤 이벤트 1회 |
| 10초 기본값이 진짜 멈춤을 늦게 알리는 부작용 | 작다(L2) | 조건이 맞는 순간 끝나므로 통과하는 테스트의 시간은 그대로다(2회 실행 47~65초, 1차 PR과 비슷). 늦어지는 것은 **실제로 깨졌을 때**뿐이다. 실패한 `waitFor` 하나가 5초 대신 10초 뒤에 실패하는 정도다. 실제 회귀가 여러 테스트에 퍼지면 그만큼 CI가 느려지지만, 실패 메시지는 그대로 단언 내용이다. 한 테스트 안에서 앞의 대기가 부하로 9초쯤 걸리고 뒤 대기가 실패하면 합계가 `testTimeout` 20초를 넘어, 단언 메시지 대신 "Exceeded timeout"으로 보일 수 있다. 이 경우만 진단이 나빠진다 |
| 지운 개별 timeout | 문제없음(L3) | 8000은 10초 기본으로 더 길어졌다. 2000~4000(포커스·체크 모션·진동)은 원래 "이 시간 안에 일어난다"를 주장하던 것이 아니라 부하 여유였다. 지금도 각 테스트는 "바로는 아님(false)"과 "결국 일어남"을 같이 본다 |

## 낮음
- **L1. '마칠게요' 잠금 길이를 정확히 단언하지 않는다(예전부터)** — 가짜 시계 테스트 하나에 경계를 넣기를 권한다. `MATCH_HOLD_MS`(KeyboardStep export)를 import해서 `advanceTimersByTime(MATCH_HOLD_MS - 50)` → 아직 비활성·포커스 안 옮김 → `advanceTimersByTime(100)` → 활성·포커스 '마칠게요'. 응원 '취소'의 아래쪽 경계(PR #58 L1)와 같은 숙제다.
- **L2. 10초 기본 + testTimeout 20초** — 위의 "Exceeded timeout으로 가려지는" 경우를 줄이려면 `testTimeout`을 30초로 함께 올리거나, 두 값의 관계(기본 대기 × 2 < testTimeout)를 jest.after.js 주석에 적는다. 정말로 오래 걸리는 첫 화면 대기(historyScreen date-line 등)는 기본값을 올리지 말고 그 테스트에서만 길게 주는 방법도 있다(전역 영향 축소). 지금 값도 받아들일 만하다.
- **L3. 전역 기본값이 바뀐 이유가 두 곳에 흩어져 있다** — jest.after.js 주석과 PR 설명. 다음에 누가 개별 `{timeout}`을 다시 넣지 않도록 dev-app-notes(테스트 절)에 "waitFor 기본 10초, 개별 timeout은 쓰지 않음, 실제 대기 대신 가짜 시계" 한 줄을 남긴다.
