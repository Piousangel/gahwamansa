## 중간

### M1. 서비스 역할이 `kakao_unlink_gave_up` 뷰로 카카오 큐 행을 고치고 지울 수 있다. 감사 행은 남지 않는다 — `0047:29-32`
- 원인: 단순 뷰라 자동으로 갱신 가능하다(`is_updatable=YES`, `is_insertable_into=YES`). 뷰 소유자는 postgres(=표 소유자)라서 기본 표의 권한과 RLS가 적용되지 않는다. 그리고 Supabase 기본 권한이 새 relation에 service_role 전체 권한을 준다. 0047은 `grant select`만 추가했고, service_role의 insert·update·delete는 회수하지 않았다(anon·authenticated는 `revoke all`로 막았다).
- 재현(임시 스택, 0048까지 적용, service_role):
  ```sql
  update public.kakao_unlink_gave_up set gave_up_at = null, attempts = 0 where id = 9901;  -- UPDATE 1
  delete from public.kakao_unlink_gave_up where id = 9902;                                  -- DELETE 1
  -- 큐: 9901 attempts=0 gave_up_at=null, 9902 없음 / admin_audit kakao_% 0행
  ```
  PostgREST에도 노출된다(`public` 스키마). 따라서 ops 키 보유자가 `DELETE /rest/v1/kakao_unlink_gave_up?id=eq.N` 한 번으로 실제 해제 없이 "처리 완료"를 만들 수 있다. 그러면 카카오 연결이 끊기지 않은 채 증빙도 남지 않는다.
- 영향: 0044가 큐 DML을 service_role에서 회수해 함수 경로(감사)로만 바꾸게 한 의도와, E7 "재시도·처리 완료는 감사와 함께"를 뷰가 우회한다. pgTAP `key_hygiene`는 select만 본다.
- 고칠 방향:
  - 새 마이그레이션에서 `revoke insert, update, delete, truncate on public.kakao_unlink_gave_up from service_role;`를 실행한다. 또는 `revoke all ... from service_role; grant select ...`로 바꾼다.
  - pgTAP에 `not has_table_privilege('service_role','public.kakao_unlink_gave_up','update'|'delete'|'insert')`를 추가한다.
  - remote-checks에도 한 줄 추가한다.
  - 기존 public 뷰(`content_runway` 등)도 같은 기본 권한을 받았는지 함께 점검하길 권한다(이번에는 확인하지 않음).

### M2. `pii_in_args`가 가장 흔한 전화·카드 형식을 놓친다 — `0047:21`
- 재현(`admin_check_args` 직접 호출):

  | 입력 | 결과 |

  | `010 1234 5678` | **통과** |

  | `mom＠gmail.com`(전각 @) | **통과** |

  | `접수 202611190001`(12자리 접수번호) | 거부(과잉) |
  | `가족 3f2a9c1e-…-123456789012`(uuid 끝 묶음이 숫자) | 거부(과잉) |

- 영향: D5의 목적은 감사 행에 전화·카드 번호를 1년 동안 남기지 않는 것이다. 운영자가 실제로 적을 형식(하이픈 전화)이 통과한다. 반대로 정상적인 긴 접수번호나 uuid는 막힌다.
- 고칠 방향:
  - 숫자 사이의 `[-. ]`를 지운 뒤 9자리 이상인지 검사한다. 예: `regexp_replace(s, '(?<=[0-9])[-. ](?=[0-9])', '', 'g')`. PG에서 lookbehind가 안 되면 `[0-9][-. ]?`를 반복하는 패턴을 쓴다.
  - `@` 검사에 `＠`(U+FF20)를 더한다.
  - uuid 패턴은 먼저 지우고 검사한다.
  - 접수번호 규칙은 "숫자 8자리 이하 또는 `#n`"으로 문서에 적는다.
  - pgTAP에 하이픈 전화와 uuid 사례를 추가한다.

### M3. `publish-content.mjs`가 대상 확인 전에 서버 키로 요청한다 — `scripts/photos/publish-content.mjs:32-45, 66`
- 흐름: `opsTarget()`(주소 입력 + 키) → **곧바로 `content_photos`·`content_questions` 조회 fetch(키 헤더)** → 게이트 → 그다음에야 `confirmTarget`(ref 대조). `--check` 모드도 키를 받아 요청한다.
- 원래부터 이런 순서였지만, E3에서 주소를 손으로 입력할 수 있게 되면서 위험이 커졌다. 주소를 잘못 치면(오타 도메인, `http://`) ref 대조를 거치기 전에 ops secret 키가 그 호스트로 간다.
- 다른 5개 스크립트는 `opsTarget` 바로 뒤에서 `confirmTarget`을 부른다(`create-review-access`는 cmd 4개만 해당하고 나머지는 사용법 출력).
- 고칠 방향:
  - `confirmTarget`을 `opsTarget` 바로 뒤로 옮긴다. `--check`이면 키 없이 조회하거나, 대상 확인 뒤에 조회한다.
  - `opsTarget`에서 `https:` 이외의 주소를 거부한다. 단 local은 `http://127.0.0.1`·`localhost`만 허용한다.

## 확인했고 문제없음

- **search_path·권한**
  - 새 함수 7개와 kick 함수는 모두 `search_path=""`이고 소유자는 postgres다. public definer 가운데 search_path가 없는 함수는 0개다.
  - anon은 새 함수를 실행할 수 없다. authenticated는 `my_terms_status`·`record_terms_agreement`만 실행할 수 있다.
  - service_role은 `push_kick`만 실행할 수 없다. 종류별 kick 3개는 그대로 실행할 수 있다.
- **표 권한**: `terms_agreements`·`terms_versions`에서 service_role은 select만 가능하다. `kakao_unlink_queue`는 service_role select가 0이고 열 단위 권한도 0이다.
- **카카오 뷰**: 열은 `id, enqueued_at, attempts, last_http, gave_up_at`이다(회원번호 없음, last_http는 int).
  - 남는 경로가 하나 있다. 서비스 역할은 `admin_kakao_unlink_retry` 뒤 `kakao_unlink_claim`으로 회원번호를 받을 수 있다. Edge 함수에 필요한 경로이고 감사 행이 남으므로 수용한다.
- **display_name**
  - 함수·뷰·정책 본문에서 참조 0건이다(`prosrc`·`pg_views`·`pg_policies`).
  - app/src 참조 0건이다. 남은 곳은 문서와 database.gen.ts(L7)뿐이다.
  - authenticated의 select 열은 `created_at,family_id,id,parent_title,role,user_id`다. 0019의 `parent_title` 추가분도 유지된다.
  - authenticated의 profiles 표 insert·update·delete 권한은 기존 기본값이고 RLS 정책이 select만 있어 막힌다. 이번 변경과는 무관하다.
- **0048 `needs_reagree` 모양 변경과 앱 호출부**
  - app/src에 `my_terms_status`·`record_terms_agreement` 호출이 **아직 없다**(grep 0건, main·server 브랜치 모두). 모양이 바뀌어도 깨지는 호출부는 없다.
  - 앱 AU 연동 때는 dev-server-notes §2의 새 모양(`needs_reagree`)을 계약으로 삼는다.
- **게시 버전이 없을 때**: `my_terms_status`는 `{"needs_reagree": true}`, `record_terms_agreement`는 `unknown_version`이다. 시드에는 게시 버전이 없다(reset 직후 0행). 그래서 환경마다 먼저 게시해야 한다. remote-checks에 확인 줄이 있다(L12는 절차 문서 쪽).
- **계정 삭제 시 동의 이력 cascade**: postgres로 auth.users를 지우자 terms_agreements도 0행이 됐다. RI 동작은 표 소유자 권한으로 돌기 때문에 service_role 쓰기 회수와 충돌하지 않는다. `supabase_auth_admin`으로 바꿔 실행하는 것은 임시 스택에서 권한이 없어 확인하지 못했다.
- **Edge 키 처리**
  - 키 값이 로그·오류·응답에 들어가지 않는다. `makeRpc`의 오류는 `rpc_failed:<이름>:<상태>`이고 본문은 버린다. 키가 없으면 `service_key_missing`이다.
  - 새 키는 apikey만, 옛 키는 apikey+Bearer로 보낸다.
  - 세 함수 모두 `rpc` 외에 REST를 직접 부르지 않는다.
- **ops 숨김 입력**
  - pty에서 프롬프트 뒤에 입력하면 출력에 키가 없다(`KEY: \r\n`만 보임). 값 길이는 21자로 정상이었다.
  - 키는 argv에 들어가지 않는다. 6개 스크립트 모두 키를 출력하지 않는다.
  - 셸 기록이 남지 않는 것은 숨김 입력과 `read -rs` 안내로 충족한다(L4·L5는 예외 경로).
