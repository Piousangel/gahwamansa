# PR #101 리뷰 — C8 앱 정보 v4 부품 교체 · SWITCH_COLORS · Sheet footer 테스트 (891a865) · 2026-11-20

리뷰어: 독립 리뷰어(작성자 아님), 레벨 medium. 판정: **통과**. H 0 · M 0 · L 2. 추가 조사(cheerSheetV4 불안정)는 아래 별도 절.

## 스위치 색
- 값(`ui/ds/switchColors.ts`, tokens-v4와 일치): 끔 트랙 `line #A67C5A`, 켬 트랙 `done #166534`, 손잡이 `card #FFFFFF`. 직접 계산한 대비(WCAG 상대 휘도):
  | 쌍 | 대비 |
  |---|---|
  | 끔 트랙 / 흰 카드 | 3.72 |
  | 끔 트랙 / 종이 #F6F3EE | 3.36 |
  | 끔 트랙 / paperSoft #EFE9E0 | 3.08 |
  | 켬 트랙 / 흰 카드 | 7.13 |
  | 켬 트랙 / 종이 | 6.44 |
  | 켬 트랙 / paperSoft | 5.91 |
  | 손잡이(흰) / 끔 트랙 | 3.72 |
  | 손잡이(흰) / 켬 트랙 | 7.13 |
  → 비텍스트 3:1(WCAG 1.4.11) 모두 통과(가장 낮은 것도 paperSoft 위 끔 트랙 3.08). 이전 `lineSoft` 1.44 는 미달이었으므로 개선.
- 자녀(FamilyPushRow)·어르신(ParentSettings 두 행·NotifyRows) 모두 같은 상수. FamilyPushRow 는 이전 켬 색이 `doneInk #14532D`(9.11)에서 `done`(7.13)으로 약간 연해졌으나 여전히 충분.
- **켬·끔을 색만으로 구분하지 않음**: 스위치 기본 모양의 손잡이 위치(좌/우)가 있고, 세 곳 모두 부모 `Pressable` 이 `accessibilityRole="switch"` + `accessibilityState.checked`(화면 읽기), 스위치 자체는 읽기에서 숨김. 행 텍스트로 상태를 따로 말하는 곳도 있음.
- **어르신 화면 회귀**: 변경은 `trackColor`·`thumbColor` 두 속성뿐이고 값은 이전 `color.done`(#166534, 동일)·끔만 lineSoft→line. 레이아웃·접근성 속성 변화 없음. `tsc --noEmit` 오류 없음. (ParentSettings 두 번째 Switch 는 `{...SWITCH_COLORS}` 로 줄 수만 바뀜.)
- **L1** 비활성 상태(FamilyPushRow `disabled={busy}`)에서는 Android·iOS 가 트랙을 자체적으로 흐리게 하므로 3:1 이 유지되지는 않지만, 비활성은 WCAG 1.4.11 면제 대상이고 일시적(busy)이라 허용.
- **L2** `ui/ds/switchColors.ts` 가 ds 색을 쓰는데 어르신 파일 두 곳이 `import {SWITCH_COLORS} from '../../ui/ds/switchColors'` 를 import 맨 위에 두어 (React import 앞) 정렬이 어색함 — 기능 영향 없음.

## cheerSheetV4 불안정 원인 조사
결론: **앱 경합 없음, 시간 상수의 문제가 아니라 "첫 테스트에 몰린 콜드 스타트 비용"이 부하와 겹치는 테스트 쪽 문제**(근거는 재현 실험, 실패 자체는 재현하지 못함).

관찰(부하: 바쁜 루프 12~16개 + jest 동시 6~8벌, `--ci`):
- 캐시 있음·부하 큼: 첫 테스트("시트 머리") **6.4초**(6벌 모두 4~6초), 나머지 테스트는 0.02~0.5초. 같은 파일을 바로 이어 돌려 변환 캐시가 따뜻해지면 첫 테스트도 **0.1초**.
- `--no-cache` 로 8벌 동시: 첫 테스트 4.4~6.0초, 나머지 ≤0.6초, 9/9 전부 통과(실패 재현 못 함).
- `AppRoot` 를 단독 프로브로 렌더: 첫 렌더 0.1초·두 번째 0.008초, 버튼이 뜨기까지 5~11ms(따뜻한 캐시). 즉 `openSheet` 의 대기 자체는 즉시 풀림.
→ 4~6초는 **파일에서 한 번만 드는 비용**(react-native 지연 getter 가 Modal·ScrollView·Animated 등을 처음 요구할 때의 변환·로드, 아직 변환 캐시가 없는 CI 에서 가장 큼)이며, 첫 테스트가 그 비용 + `waitFor`(실시간 폴링)를 함께 떠안는다. 부하가 3배가 되면 15초 대기를 넘길 수 있다. 

경합 후보별 판정:
- 타이머: 포커스 이동 `focusLater` 300ms 는 Sheet 테스트에서 가짜 시계로 고정(`jest.useFakeTimers` + `advanceTimersByTime`), M1 테스트는 가짜 시계를 시트가 열린 뒤 켜서 열 때 만든 실제 300ms 타이머가 남을 수 있으나 취소 대상이 아니어도 `titleRef` 가 null 이면 무동작·mock 이라 단언에 영향 없음. 앱 쪽 `setTimeout` 은 AppRoot 느린 안내 2초뿐(가짜 시계 아님, 단언과 무관).
- 애니메이션: `useFadeIn` 은 Modal `onShow` 에서만 시작하고 jest 의 Modal 은 `onShow` 를 자동 호출하지 않으므로 테스트가 기다리는 상태(시트 문구)와 무관.
- 포커스 이동: 위 타이머와 같음, `sendAccessibilityEvent` 는 mock.
- 순서 경합(press → 시트 표시): `act(async)` 안에서 상태가 동기 반영 — 폴링은 즉시 성공.
- `getByRole` 은 큰 트리에서 느려(수백 ms) 부하에서 폴링 간격이 늘어나는 정도의 영향.

테스트 쪽 고칠 방향(앱 버그 아님):
1. 파일 맨 앞 `beforeAll` 에서 `render(<AppRoot…/>)` + `unmount()` 한 번으로 콜드 스타트를 흡수(그 `beforeAll` 만 `testTimeout` 을 늘림) → 이후 각 테스트의 `waitFor` 는 짧게 유지해도 안정. 15초 대기는 되돌려도 됨.
2. 또는 jest 설정에서 CI 변환 캐시를 `actions/cache` 로 보존(`jest --showConfig` 의 `cacheDirectory`).
3. `--maxWorkers=2`(이미 CI 가 사용)가 가장 큰 완화. 로컬에서 여러 벌을 동시에 돌릴 때만 문제.
