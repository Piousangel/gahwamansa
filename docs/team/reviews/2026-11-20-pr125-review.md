# PR #125 리뷰 — 어르신 답 역할 answer·answerRow (0360979) · 2026-11-20

리뷰어: 독립 리뷰어(작성자 아님), 레벨 low~medium. 판정: **조건부 통과(M 1 수정 권고)**. H 0 · M 1 · L 2. 추가 조사(불안정 테스트 두 개)는 아래 별도 절.

## 확인
- 값: `tokensV4.ts` 의 answer(자녀 40/52·400·상한 1.3), answerRow(26/36·400·상한 1.5)가 `tokens-v4.json` 과 일치. `roles.ts` 의 `spec()` 은 어르신 값이 없으면 자녀 값으로 대체하며 어르신 화면에서 쓰지 않는다는 점을 테스트가 지킴. `tsc --noEmit` 오류 없음, `childHome·dsComponents·tokensV4·dsDockBudget·dsLayout` 89 통과.
- **200% 홈 첫 화면 예산**: answer 상한 1.3 → 200%에서도 52/68(이전 display 상한 1.5 는 60/78)이라 높이가 줄어 예산 쪽으로는 개선. 전·후 캡처(c4-c5-before-after.png)의 200% 홈은 끊긴 연결 카드가 첫 화면을 차지해 최근 답 카드가 아래로 밀려 있는 점이 전·후 동일하고 `dsDockBudget` 통과. C5 는 answerRow 상한 1.5 로 200%에서 날짜 줄이 줄바꿈되지만 전·후 같은 구조이고 행이 잘리지 않음.
- **캡처**: 전·후 4쌍(홈 100%/200%, C5 100%/200%)이 있고, 변화는 '고른 답' 글자 굵기 700→400 뿐. 400 으로 바뀌어 강조가 눈에 띄게 줄어든 것이 보이며 설계 의도(Jua, 글꼴 미번들)와 다름은 L1.
- **R-21(700 또는 Jua 강조 3개 이하, answer 1개)**: 빌드 1 은 시스템 글꼴이라 Jua 가 없고 answer·answerRow 는 400 이므로 700 집계에서 빠짐. display(700)를 answer(400)로 바꿔 한 화면의 700 글자 수는 줄어듦 → 3개 이하 충족. 단, answer 는 "화면당 1개" 제한이 있음(아래 M1).

## 지적
- **M1 홈에서 어르신이 여럿이면 answer 가 카드마다 반복됨.** `ChildHome.AnswerCard` 가 모든 어르신 카드에 `role="answer"` 를 쓰는데(`list.map(AnswerCard)`), 토큰 note 는 answer 를 "대표 한 개, 화면당 1개"로, 여러 분이 연결됐을 때 분별 답은 answerRow 로 정의. 두 분 이상이면 한 화면에 answer 가 둘 이상 → R-21 의 "answer 1개" 위반. 권고: `withHeader`(many) 일 때는 answerRow, 한 분일 때만 answer. 테스트도 한 분만 검사 중이라 많음(many) 케이스 단언 추가.
- **L1** 설계는 두 역할 모두 fontFace Jua 인데 앱은 시스템 글꼴(`tokens.ts` 주석: 라이선스 미확인) → 400 이 평범해 강조가 약함. 빌드 2 에서 Jua 를 번들하면 C5 의 answerRow 가 행마다 Jua 라 R-21 집계(3개 이하)를 다시 해야 하므로 지금 주석에 "Jua 적용 시 재집계"를 남기길 권고.
- **L2** `roles.ts` 의 `a in r ? … : r.child` 캐스팅이 다소 우회적 — 어르신 값 없는 역할은 타입으로 막는 편이 더 안전(런타임 대체는 테스트가 있어 허용).

## 불안정 테스트 조사 (ac05Events cheer_sent · childScreensV3 M3)
결론: **같은 콜드 스타트 문제로 보이되, 실제로 흔들린 것은 파일의 첫 AppRoot 테스트**이고 지목된 두 테스트는 재현되지 않음. warmAppRoot 적용 권고(조건 있음).
- 재현: 바쁜 루프 24개 + `--no-cache` 로 ac05Events·childScreensV3 각 4벌 동시. 결과 8벌 중 7벌에서 실패 1건씩:
  - ac05Events: **첫 테스트**('app_first_open … 역할을 고르면 role_guess')가 20초 제한 초과(27.9·32.6·31.6초), 나머지 24개는 통과 — `cheer_sent` 는 4벌 모두 통과(0.3~1.8초).
  - childScreensV3: 파일에서 처음 AppRoot 를 그리는 'C3 리뷰 M1(번호 만료)' 가 `wait-code` 를 못 찾고 실패(10~49초) — `M3` 는 4벌 모두 통과(0.45~2.6초).
  → 콜드 스타트 비용(모듈 첫 로드·첫 렌더, 캐시 없는 CI 에서 큼)이 그 파일의 **처음 AppRoot 를 그리는 테스트**에 몰려 부하 때 제한을 넘는 같은 현상.
- cheer_sent·M3 는 이미 앞선 테스트가 AppRoot 를 그려 따뜻한 상태라 콜드 스타트 때문에 단독으로 흔들릴 이유가 약함. 두 테스트는 가짜 시계(`useFakeTimers`·4.1~4.3초 전진)를 쓰는데 RNTL 의 가짜 시계 `waitFor` 는 시계를 직접 전진시켜 부하와 무관하게 반복 횟수만큼 돌므로 CPU 부하가 직접 원인이 되기 어렵다. 가능성: 단독 `-t` 실행처럼 그 테스트가 **파일 안에서 처음 그리는 테스트**가 되는 실행(필터·샤딩·이전 테스트 skip)이거나, 이전에 흔들린 건이 위 첫 테스트였을 수 있음 — 관측된 실패 로그에서 테스트 이름을 확인 권고.
- 권고: 두 파일 모두 `beforeAll(warmAppRoot)`. 단 `warm.tsx` 가 경고하듯 ac05Events 는 `app_first_open`·시작 상태를 검사하므로 적용 뒤 파일 전체를 한 번 돌려 `role_guess`·first_open 단언이 그대로 통과하는지 확인(`trackOnce` 의 `inflight` 집합이 모듈 전역이라 예열이 키를 써 버리면 첫 테스트가 깨질 수 있음 — warm 은 역할 선택 화면까지만 가므로 보통 안전하나 실제 실행으로 확인 필요). childScreensV3 는 시작 링크·첫 실행 검사가 아니라 바로 적용 가능.
