## 중간

### M1. remote-checks의 0057 줄이 읽기 전용 역할에서 **쿼리 전체를 실패**시킨다(`supabase/ops/remote-checks.sql` 0057 줄)
- 새 줄은 `public.stale_anonymous_users(now(), 100000)`를 호출한다. 이 함수는 마이그레이션에서 `public, anon, authenticated, service_role` 모두 실행 권한을 회수했다.
- remote-checks는 d68e4cc(이 저장소 결정)부터 `npx supabase db query --remote --read-only`의 **읽기 전용 역할**(`supabase_read_only_user`)로도 "전부 나오게" 만든 쿼리다(파일 머리말).
  - `pg_read_all_data`는 표 SELECT만 주고 **함수 EXECUTE는 주지 않는다.**
  - PostgreSQL은 함수 실행 권한을 실행기 초기화 때 검사하므로, CASE로 감싸도 피할 수 없다.
  - 결과: `permission denied for function stale_anonymous_users`로 **remote-checks 전체(다른 수십 줄 포함)가 결과 없이 끝난다.**
- 첫 리뷰는 "remote-checks는 소유자 postgres로 실행되므로 충돌하지 않음"으로 봤다. Studio SQL Editor(postgres)라면 맞지만, 읽기 전용 경로가 문서화된 운영 방식이라 깨진다.
- 고칠 방향(둘 중 하나):
  1. 대상 수를 함수 없이 SQL로 계산한다. 읽기 전용 역할은 RLS를 우회하고 `pg_read_all_data`로 `auth.*`를 읽을 수 있다:
     `auth.users` + `not exists profiles` + `greatest(...)`를 그대로 인라인한다.
  2. 대상 **수만** 돌려주는 읽기 전용 definer 함수 `stale_anonymous_count()`를 두고, `supabase_read_only_user`에만 EXECUTE를 준다. 식별자를 돌려주지 않는다.
- 확인 방법: 임시 스택에서 `set role supabase_read_only_user` 뒤 remote-checks 전체를 실행한다(postgres가 이 역할로 바꿀 수 없으면 `has_function_privilege('supabase_read_only_user', …)`로 확인).

## 확인한 것(요청 항목별)

### 잘못 지우는 경로: 없음

| 경우 | 결과 | 근거 |
|---|---|---|
| 연결된 어르신 | 안 지움 | 후보 쿼리 `not exists profiles` + 삭제 직전 `user_delete_core`가 잠금 뒤 다시 `has_profile` 검사 |
| 자녀(카카오·구글·메일) | 안 지움 | `is_anonymous` 아님. 후보 쿼리와 잠금 재확인 모두 `is_anonymous` 조건 |
| 재연결 직후 | 의도대로 | 새 기기 익명은 프로필이 있어 제외된다. 옛 익명은 프로필이 옮겨 간 뒤 마지막 활동이 90일을 넘었을 때만 지운다(문서·pgTAP a5). 재연결 **전**에는 옛 익명이 아직 프로필을 갖고 있어 지워지지 않는다 |
| 오늘 쓴 계정 | 안 지움 | 앱을 열면 1시간 access token이 갱신되면서 `refresh_tokens` 새 행과 `sessions.updated_at/refreshed_at`이 생긴다. `greatest`가 그중 가장 늦은 값을 쓴다(NULL은 무시). pgTAP a3·a6·a7 |
| 같은 순간 번호를 넣는 오래된 익명 | 안전 | 잠금 순서는 아래 참고. 번호 연결의 프로필 insert(FK key share)가 먼저 커밋되면 `has_profile`로 지우지 않는다. 정리가 먼저면 연결 insert가 FK로 실패하고 롤백된다(0049와 같은 구조) |

- 실패 방향: 원격 GoTrue 열 형식이 달라 `anon_last_activity`가 오류를 내면, 사용자 단위 예외로 **그 사람은 지우지 않는다**(fail-closed).

### 삭제 직전 재확인의 잠금 순서와 교착

- 순서: `auth.users` 행 `FOR UPDATE` → 마지막 활동 재계산(읽기) → `user_delete_core`(같은 행 재잠금, 이미 보유) → `profiles` 확인 → `device_tokens` 삭제 → `auth.users` 삭제 → cascade(identities·sessions·refresh_tokens·terms_agreements·stale_purge_failures).
- 교착 가능성: GoTrue 토큰 갱신이 `sessions`를 먼저 잠그고 `users`를 갱신하면, 정리(users → sessions cascade)와 반대 순서가 되어 교착이 날 수 있다. 이론상 경우다.
  - PG가 한쪽을 `40P01`로 끊는다. 정리 쪽이면 사용자 단위 예외로 그 사람만 실패로 기록하고 다음 날 다시 한다. 토큰 갱신 쪽이면 앱이 다시 시도한다. 수용(L3).
- 재확인을 지난 직후 커밋된 토큰 갱신(잠금을 쓰지 않는 refresh_tokens insert)은 막지 못한다. 91일째 0시 10분에 정확히 앱을 연 사람이면 세션이 끊기고 새 익명으로 시작한다. 서버 데이터가 없는 계정이라 손실은 없다.

### 실패 격리의 서브트랜잭션 비용, 500명 한도

- 사람마다 예외 블록 1개(+ `user_delete_core` 안 측정 insert 예외 블록 1개)라, 한 번에 **최대 약 1000개의 서브트랜잭션**이 한 최상위 트랜잭션 안에 생긴다.
- 쓰기를 한 서브트랜잭션의 XID는 최상위 트랜잭션이 끝날 때까지 남는다. 64개를 넘으면 PGPROC 캐시가 넘쳐(subxid overflow), 그 사이 다른 세션의 스냅샷 판정이 `pg_subtrans`를 읽어 느려질 수 있다.
- 실행 시각이 00:10 KST(사용 적음)이고 배치가 짧아 수용할 수 있다. 정리 대상이 크게 쌓인 첫 실행이 가장 오래 걸린다(L1).
- 500명 상한은 `stale_anonymous_users(p_now, 500)`이다. 남은 사람은 다음 날 처리한다. 실패한 사람은 `failures` 오름차순으로 뒤로 보내져 맨 앞을 막지 않는다(pgTAP).

### stale_purge_failures의 RLS·권한·보관

- RLS가 켜져 있고 정책은 없다. `public·anon·authenticated·service_role` 모두 회수했다. 소유자 postgres(정의자 함수)만 쓴다.
- 읽기 전용 역할은 `pg_read_all_data` + RLS 우회로 읽을 수 있다(remote-checks의 실패 수 줄). 그 줄은 수만 센다.
- 보관: `user_id`(식별자)가 남는다. 성공해서 지워지면 cascade로 사라진다. 그러나 **실패 뒤 다시 활동해 정리 대상에서 빠진 사람**이나 계속 실패하는 사람의 행은 기한 없이 남는다(L2).

### SECURITY DEFINER의 search_path

- 새 함수 6개(`stale_anon_days`·`anon_last_activity`·`user_delete_core(uuid,text)`·`user_delete_core(uuid)` 재정의·`stale_anonymous_users`·`purge_stale_anonymous`)와 `purge_expired_data` 재정의 모두 `set search_path = ''`이고, 모든 참조에 스키마를 붙였다.
- 실행 권한은 6개 모두 앱·anon·서비스 역할에서 회수했다(`stale_anon_days`는 immutable invoker지만 같이 회수).
- `user_delete_core(uuid)`를 sql 함수로 `create or replace` → 기존 ACL(전부 회수)이 유지된다. `delete_my_account`·`admin_delete_user`는 그대로 1인자를 부른다.
- 덤으로 앱 경로의 `account_deleted`도 시 단위 시각 + 예외 블록이 된다(#66 리뷰 L1·L2 해소).

### hosted에서 auth.sessions·refresh_tokens 읽기 권한

- 확인할 수 없다(원격 금지).
- 기존 0043·0049가 이미 postgres 정의자로 `auth.users`를 지우고 있고, remote-checks가 이번에 `has_table_privilege('postgres', 'auth.sessions'|'auth.refresh_tokens', 'select')`와 `auth.users delete`를 확인하는 줄을 넣었다(단, M1 때문에 그 줄이 읽기 전용 역할에서는 함께 실패한다).
- 권한이 없으면 사용자 단위 예외로 **아무도 지우지 않는다**(fail-closed). 결과에는 `stale_anonymous_failed`가 대상 수만큼 찍힌다.
- staging 반영 직후 remote-checks(Studio, postgres) 한 번으로 확인하는 것을 반영 절차에 둔다.
