## 대상 조건(잘못 걸리는 경우)
- 조건: `is_anonymous` AND 프로필 없음 AND `greatest(가입, last_sign_in, users.updated_at, sessions 최대, refresh_tokens 최대) < now - 90일`. 연결된 어르신(프로필 있음)·자녀(비익명)는 대상이 아님(pgTAP 6·7). 재연결로 프로필이 새 기기로 옮겨간 옛 익명(프로필 없음)은 대상(의도).
- **프로필 생기기 직전 경합(번호 입력 중)**: 삭제 함수가 `auth.users` 행을 `for update` 로 잠근 뒤 프로필 존재를 다시 검사한다. 프로필 insert 는 `profiles.user_id → auth.users` FK 로 같은 행에 key-share 잠금을 요구하므로 둘은 직렬화 — redeem 이 먼저면 삭제가 프로필을 보고 `has_profile` 로 물러서고, 삭제가 먼저면 사용자가 없어져 연결이 실패(앱은 새 익명 로그인으로 재시작). 프로필이 있는 계정이 지워지는 경로 없음.
- **L1(삭제 시점 재확인 없음)**: 목록(`stale_anonymous_users`)은 배치 시작 시 한 번 구해 두고 `user_delete_core` 는 프로필만 다시 본다(마지막 활동 재검사 없음). 목록을 만든 뒤 삭제 직전 몇 초 사이에 그 계정이 앱을 열면(토큰 갱신) 최근 활동 계정이 지워질 수 있다. 지워져도 잃는 것은 약관 동의 기록·세션뿐(프로필·답 없음)이라 영향이 작고, 앱은 새 익명 로그인으로 복귀. 삭제 직전 활동 재검사를 넣으면 닫힘.

## 마지막 활동 계산
- **GoTrue v2.198(로컬 스택)에서 실측**: 익명 가입 후 토큰 갱신 1회 → `users.updated_at`·`sessions.updated_at`·`sessions.refreshed_at` 이 갱신되고 `refresh_tokens` 에 새 행(created/updated 갱신)이 생김. 즉 앱을 쓰면(갱신이 일어나면) `greatest` 의 여러 항이 함께 올라간다.
- 추가 실험(롤백 트랜잭션): 가입·로그인이 120일 전이어도 `users.updated_at` 만 5일 전이면 제외, `refresh_tokens` 만 5일 전이어도 제외, 둘 다 오래되면 포함 — `greatest` 가 NULL 을 무시하고 `refresh_tokens.user_id`(varchar) 와 `u.id::text` 비교도 맞음.
- **L2** `auth.sessions.refreshed_at` 은 `greatest` 에 없다. 지금 GoTrue 는 갱신 때 위 다른 항도 같이 올리므로 영향 없으나, 이후 버전이 `refreshed_at` 만 갱신하도록 바뀌면 활동 중인 연결 전 계정이 오래된 것으로 보일 수 있다(그 계정은 프로필이 없어 잃는 것이 작음). 방어로 `refreshed_at` 을 항에 추가 권고(해당 열은 로컬 auth 스키마에 존재; 호스티드 스키마와 열 일치는 반영 전 확인).

## user_delete_core 2인자 판
- 1인자 판은 2인자 판에 위임하며 본문 동작이 0054 와 같다: 직접 실행 결과 연결 전 계정 삭제 시 `scope: none`, 기록 `account_deleted {"scope":"none","role":"none"}`(이전과 같음). `create or replace` 라 ACL 이 유지됨 — 실행 권한을 0057 전·후로 비교해 anon·authenticated·service_role 모두 그대로(`false`), 2인자 판은 `public, anon, authenticated, service_role` 모두 revoke.
- 이름 검사(`invalid_event`)는 내부 호출만 가능하므로 앱 입력이 아님. 두 판 모두 `security definer set search_path = ''`, 본문 참조가 전부 스키마 한정(pg_catalog 함수는 빈 search_path 에서도 해석됨).

## 배치: 최대 500·실패 격리·멱등
- 한 번에 최대 500, 오래된 순. 두 번 연속 실행: 1회 2명 삭제 → 2회 0명(멱등). 이미 지워진 id 는 `user_delete_core` 가 null 을 돌려줘 세지 않음.
- **M1 사용자별 실패 격리가 없다(독 알약).** `purge_stale_anonymous` 의 루프는 사용자 단위 예외 블록이 없어 한 계정의 삭제가 예외를 내면 루프 전체가 중단되고, 바깥 `purge_expired_data` 의 예외 블록이 `stale_anonymous = -1` 로 만들며 **그 실행에서 이미 지운 사용자까지 모두 롤백**된다. 직접 재현: 오래된 순으로 두 번째 계정(04) 삭제 때 예외를 내는 트리거를 걸자 `stale_anonymous = -1`, 세 번째 계정(05)은 그대로 남음. 오래된 순 정렬이라 같은 계정이 다음 날 또 맨 앞에 와서 **그 뒤 모든 계정의 정리가 영구히 막힌다**(경고만 남음). 현재 FK(`profiles`·`families`·`invite_codes` 는 set null·cascade)로는 흔치 않지만, 다른 FK·트리거·권한 문제가 생기면 법 제21조 파기 이행이 조용히 멈춘다. 권고: 루프 안에서 사용자별 `begin … exception when others then …` 로 감싸 실패는 건수(음수가 아닌 `failed` 키)와 warning 으로 남기고 나머지는 계속.

## 권한
- `stale_anonymous_users`·`purge_stale_anonymous`·`user_delete_core(uuid,text)` 는 public·anon·authenticated·service_role 모두 revoke, pgTAP 11 이 세 역할 × 세 함수를 검사(통과). `purge_expired_data` 는 `create or replace` 라 기존(0043) ACL 유지, 모두 `security definer set search_path=''`.
- **L3** `stale_anon_days()`(상수 90)는 `service_role` 에서 revoke 하지 않음(public·anon·authenticated 만). 값이 비밀이 아니고 부작용이 없어 위험은 없으나 다른 함수와 같게 맞추는 편이 일관.
- remote-checks 의 `stale_anonymous_users(now(), 100000)` 호출은 postgres(소유자) 로 실행되므로 서비스 역할 revoke 와 충돌하지 않음.
