## 방침 4절 이행 여부(경로별)
방침 근거: privacy.html 4절 표 "이용 기록 — 최대 14개월. 계정이나 가족 기록을 지우면 그 기록도 함께 지웁니다". `events` 는 `device_key = sha256(auth uid)` 로 프로필 없이도 쌓이고(0022 `log_event`), 가족·프로필에 묶인 행만 FK cascade 로 지워졌다.
- **연결 전 계정(앱 본인 삭제·관리자 `admin_delete_user`)**: `user_delete_core(uuid,text)` 가 인증 계정 삭제 직전 `device_key = event_device_key(p_user)` 행을 삭제(1인자 판이 이 함수를 부르므로 두 경로 모두). 프로필이 있으면 `has_profile` 로 먼저 빠져 이벤트를 건드리지 않음. **충족.**
- **연결된 계정이 연결 전에 쌓은 이벤트**: `account_delete_core` 가 `v_p.user_id` 계정을 지우기 전 같은 `device_key` 행을 삭제(프로필 없이 쌓인 행 포함 — 연결 후 프로필 있는 행은 기존 cascade). 자녀(다른 자녀 남음)·어르신 본인 삭제·마지막 자녀 모두 이 줄을 지남. **충족.**
- **가족 전체 삭제 때의 어르신 익명 계정**: 지워질 어르신 uid(`v_parent_uids`, `is_anonymous` 필터가 실제 삭제 쿼리와 같음)의 `device_key` 를 같은 문 안에서 삭제 → 지워지는 계정과 정확히 일치. **충족.**
- **0057 자동 정리**: `purge_stale_anonymous` 가 `user_delete_core(…,'account_purged')` 를 부르므로 같은 삭제가 적용. 재연결로 남은 옛 익명 계정도 90일 뒤 그 계정 기록이 함께 지워짐. **충족.**
- **충족 못 하는 경로(M1·L1)**: 아래.

## 과하게 지우는 경로
- 삭제 대상은 `device_key = sha256(삭제되는 uid)` 뿐(uid 는 재사용되지 않음, 인덱스 `(device_key, ts)` 사용). 가족 삭제 쿼리는 `u.id = any(v_parent_uids) and u.is_anonymous` 로 실제 삭제되는 계정에만 한정 → **다른 사람의 이벤트·살아 있는 계정의 이벤트를 지우는 경로는 찾지 못함**.
- 탈퇴·정리 기록(`account_deleted`·`account_purged`)은 `device_key` null 이라 보존(의도, 방침 식별자 없음). 다른 가족 구성원(남은 자녀·어르신)의 기록은 그대로(테스트 5·6이 확인하도록 설계됨).
- 삭제 순서가 인증 계정 삭제 직전이고 같은 트랜잭션이라 중간 실패 시 함께 롤백(이벤트만 지워지고 계정이 남는 반쪽 상태 없음). 함수 정의는 `create or replace` 라 기존 ACL 유지, `security definer set search_path=''`, `event_device_key` 는 함수 안에서 호출(앱·anon 에 revoke 된 함수라 정의자 권한 필요 — 정의자 실행이라 문제 없음).

## 지적
- **M1 `discard_anonymous_session()`(0017)이 이용 기록을 지우지 않는다.** 소셜 로그인 직전 앱이 부르는 이 RPC(`realApi.ts` dropAnon)는 "프로필 없는 익명 계정"을 `delete from auth.users` 로 직접 지우는, **0058 이 고친 두 공통 함수 밖의 계정 삭제 경로**다. 이 경로로 지워진 연결 전 계정의 `device_key` 행(예: `app_first_open`·`consent_shown` 등 미연결 열람 중 쌓은 기록)은 그대로 남아 방침 4절("계정을 지우면 그 기록도 함께")과 어긋난다(14개월 보관이 끝날 때까지). 권고: 이 함수에도 `delete from public.events where device_key = public.event_device_key(v_uid)` 를 인증 계정 삭제 전에 한 줄 추가(또는 `user_delete_core` 로 위임 — 단 `account_deleted` 측정 기록을 남길지는 별도 결정), 그리고 이 경로 pgTAP 한 건 추가. 소셜 로그인 가입 흐름에서 자주 일어날 수 있는 경로라 이행 누락이 체계적이다.
- **L1 `admin_cleanup_review_family`(0025)** 도 심사 어르신 익명 계정을 직접 지우며 기록 삭제가 없다(심사 가족 이벤트는 지표에서 제외한다는 0054 결정과 별개로 device_key 행이 남음). 심사 계정이라 위험은 낮으나 같은 한 줄로 맞추는 것이 일관.
- **L2 pgTAP 8건의 공백**: 위 두 경로(discard·심사 정리), 어르신 익명 계정 **본인** 삭제(role parent 분기), 연결 후 프로필이 있는 행(family_id·profile_id 있는 이벤트)이 계정 삭제 뒤 모두 사라지는지(기존 cascade 와 합쳐서), 두 번 삭제 멱등은 단언하지 않음. 이번 변경의 핵심 분기(연결 전·연결된 자녀·가족 전체·0057·남는 것)는 8건이 직접 겨냥하고 있음.
- **L3** 재연결로 남은 옛 익명 계정(프로필 없음)의 기록은 가족을 지워도 즉시 지워지지 않고 0057 정리(90일) 때 지워진다 — 계정과 연결 고리가 없어 지금 구조에서는 불가피하며 방침 4절의 "연결하기 전에 그만두신 경우"·정리 기간 안내와 맞는지 법률 쪽 확인 문구만 유지.

## 재확인 (c2893ee) · 2026-11-20

판정: **통과**. M1·L1·L2 해소, 새 H·M 0, L 2. **정적 검토**(마이그레이션·pgTAP diff; 지시대로 공유 DB·staging 미사용, pgTAP 미실행 — 작성자가 공유 로컬 DB 롤백 트랜잭션으로 14건·전체 회귀를 확인했다고 보고).

- **M1 해소(discard)**: `discard_anonymous_session` 이 조건(익명 세션·프로필 없음, `auth.users.is_anonymous` 이중 확인)은 그대로 두고 삭제를 `user_delete_core(uid, null)` 에 위임 → 토큰·`device_key` 이용 기록·인증 계정이 한곳에서 지워짐. `p_event is null` 이면 측정 기록을 남기지 않는 분기라 소셜 전환이 `account_deleted` 로 세어지지 않음. 프로필이 생겼으면 `has_profile` 로 물러서 `discarded:false`. `create or replace` 라 ACL(authenticated) 유지.
- **L1 해소(심사 정리)**: `admin_cleanup_review_family` 가 어르신 프로필마다 `account_delete_core` 를 호출(토큰·프로필·이용 기록·인증 계정, 심사 가족이라 `account_deleted` 기록 없음, 가족·자녀·번호 비활성화 동작은 유지). 어르신 프로필은 가족 삭제 분기가 아닌 일반 분기라 가족이 남음. 이전(0025)은 익명 계정만 지웠고 공통 함수는 대상 프로필의 계정을 지우지만 어르신 기기는 항상 익명이라 같음(주석에 명시, **L1**).
- **결정적 검사**: pgTAP 이 `pg_get_functiondef` 로 실제 적용된 public 함수 정의에서 `delete from auth.users` 를 가진 것이 `account_delete_core(uuid)`·`user_delete_core(uuid,text)` 뿐임을 단언 — 마이그레이션 파일 grep(옛 정의가 남아 항상 걸림)보다 맞는 방식. 새 삭제 경로가 생기면 이 테스트가 걸림. **L2** 다만 정규식이 공백·대소문자만 허용하고 동적 SQL(`execute '…'`)·따옴표 식별자(`"auth"."users"`)는 못 잡으므로 경로를 늘릴 때 코드 리뷰가 보완해야 함.
- **L2 해소(테스트)**: 어르신 본인 삭제·discard(기록 없음)·심사 정리(`parents_removed` 1과 계정·기록 삭제)를 추가, 탈퇴 기록 수는 본인 삭제 1건이 더해져 6(discard·심사는 기록 없음으로 단언). 14건.
- 과삭제 재점검: 새 호출 경로도 모두 `device_key = sha256(삭제되는 uid)` 로 한정되고 공통 함수가 같은 트랜잭션에서 삭제하므로 다른 사람·살아 있는 계정의 기록은 건드리지 않음.
