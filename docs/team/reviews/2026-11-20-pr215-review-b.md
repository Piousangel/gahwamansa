## 하루 2개 한도와 재시도의 순서
- 순서: 인자·대상 검증 → **자녀 프로필 행 `for update`** → request_id 조회(있으면 기존 응원의 `{ok:true, cheer_id}` 반환) → 하루 한도 → insert. 재시도 확인이 한도 검사보다 먼저이므로 첫 요청이 한도의 마지막 칸(2번째)을 썼어도 재시도는 `daily_limit` 로 보이지 않는다(테스트 'c2b' 가 한도에 닿은 뒤 재시도 성공을 고정).
- 같은 자녀의 동시 전송(원 요청이 아직 처리 중일 때 도착한 재시도)은 프로필 행 잠금으로 줄 서고, 뒤 요청은 앞 요청이 커밋한 행을 보고 같은 결과를 반환. 잠금을 우회해도 `cheers_request_key (from_child, request_id)` 부분 유일 인덱스가 중복 insert 를 막는다(이중 방어).
- 한도를 우회하는 경로 없음: 같은 id 재전송은 새 행을 만들지 않고, 새 한도를 쓰려면 새 id 가 필요하며 그때는 2개 한도가 그대로 적용. 자정을 넘긴 재시도도 기존 행을 반환(새로 세지 않음).
- 실패한 요청(`daily_limit` 등)은 행을 남기지 않으므로 같은 id 재시도도 같은 사유로 거절 — 일관.
- **L1 (검증이 멱등 조회보다 앞)**: `invalid_key`·`invalid_target`·`disconnected` 검증이 request_id 조회보다 먼저라, 첫 요청이 성공한 뒤 어르신이 연결 해제(`user_id` null)된 상태에서 재시도하면 기존 성공 대신 `disconnected` 를 돌려준다(이미 보낸 응원을 실패로 보임). 드문 경합이며 응원 자체는 한 번 생겼으므로 안전한 방향이지만, 조회를 대상 검증 앞(자녀 잠금 뒤)으로 옮기면 더 정확. 또한 같은 id 로 **다른 문구·대상**을 보내면 앞의 응원을 돌려준다(클라이언트 버그가 아니면 일어나지 않음).

## 철회·삭제된 응원의 request_id 재사용
- 서버에는 응원을 철회·취소하는 RPC 가 없다(grep: 삭제는 31일 보관 파기와 프로필·가족 삭제 cascade 뿐; 앱의 4초 '취소'는 전송 전 클라이언트 동작). 삭제된 행은 유일 인덱스에서도 사라지므로(`tombstone` 없음) **삭제 후 같은 request_id 는 새 응원으로 처리**된다. 클라이언트가 버튼 한 번마다 새 uuid 를 만들고 재시도에만 같은 값을 쓰는 계약이라 실제로는 31일 뒤 재사용이 없고, 재사용해도 한도(하루 2개)가 그대로 걸리므로 남용 경로가 아님. 계약 문서(dev-server-notes)에 "요청 id 는 버튼 한 번, 재시도 시간 안에서만"이라는 한 줄을 남기면 완결(**L2**).
- 다른 자녀의 같은 id 는 `(from_child, request_id)` 라서 서로 섞이지 않고, 조회가 `from_child = v_me` 로 한정되어 남의 응원 id 를 알아내는 경로도 없음(테스트 'o1').

## 0058(계정 삭제 때 events 삭제)과 cheers 삭제 경로
- 0058 은 `events.device_key` 행만 지우고 `account_delete_core`·`user_delete_core` 에서 인증 계정을 지우기 직전에 일어난다. `cheers` 는 프로필·가족 삭제 시 FK cascade(0008: `from_child`·`to_parent` → profiles on delete cascade, `family_id` → families cascade)로 지워지고 0059 는 이 FK 를 건드리지 않으며 `request_id` 열·유일 인덱스는 같은 행과 함께 사라진다 → **충돌 없음**. 서로 다른 테이블이고 0059 가 정의를 바꾼 함수(`send_cheer`·`create_family`)는 0058 이 바꾼 함수(`account_delete_core`·`user_delete_core`·`discard_anonymous_session`·`admin_cleanup_review_family`)와 겹치지 않음.
- 개인정보 관점: `request_id` 는 클라이언트가 만든 무작위 uuid 로 식별 정보가 없고, 응원 행과 같은 수명(31일 파기·계정 삭제 cascade)을 따른다. `send_cheer` 가 `events` 를 쓰지 않으므로 device_key 삭제와 맞물리지 않음.

## 마이그레이션·계약
- `drop function send_cheer(uuid,text)` 후 3인자(기본값 null) 하나만 둠 — PostgREST 이름 인자 호출 모호성을 피하는 올바른 방식이며, 앱이 2인자(`p_parent`,`p_key`)로 불러도 기본값으로 동작(하위 호환). 권한: `revoke … from public, anon` + `grant … to authenticated` 로 원래와 같음.
- `create_family` 는 0003 정의에 재시도 분기만 더한 것으로 이후 재정의가 없어 회귀 없음(원본과 대조). 자녀 프로필이 이미 있으면 같은 `{family_id, profile_id}` 반환, 어르신 프로필이면 `already_has_profile`.
- **L3 (create_family 동시 재시도)**: 원 요청이 아직 처리 중일 때 재시도가 겹치면 둘 다 "프로필 없음"을 보고 insert 를 시도해 뒤 요청이 `profiles.user_id` 유일 제약 위반으로 실패(전체가 롤백되어 고아 가족은 없음)하고, 그 다음 재시도부터 같은 결과를 받는다. 함수 시작에 `auth.users` 의 본인 행 `for update`(또는 `pg_advisory_xact_lock`)로 줄 세우면 재시도 첫 호출부터 멱등. send_cheer 와 달리 이 경로에는 잠금이 없다.
- **L4** 다른 가족의 자녀로 초대받아 들어온 자녀(있다면)가 `create_family` 를 부르면 예외 대신 **기존 가족**을 반환 — 앱은 가족이 없을 때만 부르므로 영향 없음, 계약 표에 이미 적힘.
- remote-checks 의 "마이그레이션 최신 번호" 기준이 0059 로 올라감(문서·down 파일 포함 일치).
